Day 24: Deep Dive — SQL Windowing, Partitioning & Tree Path Optimization

1. Window Functions Internals in PostgreSQL

Window functions perform calculations across sets of table rows related to the current row without collapsing multiple rows into a single summary row (unlike GROUP BY).

1.1 The PostgreSQL WindowAgg Node

  • In an EXPLAIN (ANALYZE, BUFFERS) execution plan, window functions introduce a WindowAgg node.
  • Pre-requisite: The input rows must be sorted according to PARTITION BY and ORDER BY. If no index matches the ordering, PostgreSQL inserts an explicit Sort node.
  • Memory Impact: The sorted rows are spooled into a tuplestore in memory (work_mem). If the partition size exceeds work_mem, it spills to temporary disk files (Sort Method: external merge Disk), causing severe I/O degradation.

1.2 Window Framing: ROWS vs RANGE

  • Default Framing: When ORDER BY is specified without an explicit frame, SQL defaults to:

$$\text{RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW}$$

  • Performance Hazard: RANGE evaluates duplicate peer values (all rows with the same ORDER BY value belong to the same range). This requires looking ahead and buffering rows.
  • Best Practice: Always specify ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW (or custom bounds) if exact physical rows are desired. ROWS executes in a single streaming pass ($O(N)$), saving CPU and memory.

2. Declarative Table Partitioning Architecture

PostgreSQL declarative partitioning splits large tables into smaller physical chunks while presenting a single virtual relation to applications.

2.1 Partition Pruning Mechanics

  • Static Pruning: Occurs during query planning when query constants are known (WHERE recorded_at >= '2026-10-01'). The optimizer removes non-matching partitions from the plan before execution begins.
  • Run-Time Pruning: Occurs during execution when filters involve parameters or volatile functions (WHERE recorded_at >= CURRENT_DATE - 7). The executor evaluates bounds on the fly and skips entire sub-table scans.

2.2 Maintenance: DROP TABLE vs. DELETE

  • Why DELETE Fails on Big Data:
  • DELETE FROM sensor_readings WHERE recorded_at < '2025-01-01' writes an MVCC dead tuple marker for every deleted row.
  • Generates massive Write-Ahead Log (WAL) traffic, saturating replication bandwidth.
  • Leaves table and index disk pages bloated until costly VACUUM FULL is performed.
  • The Partitioning Advantage:
  • DROP TABLE sensor_readings_y2025m01;
  • Instantly unlinks the underlying disk file in $O(1)$ time.
  • Generates negligible WAL entries, causes zero disk fragmentation, and requires zero vacuum debt.

3. DSA: LeetCode #124 (Binary Tree Maximum Path Sum)

3.1 The Two Distinctions of a Node's Value

In a binary tree, a valid path can turn at most once at its highest peak node:

  1. The Peak Anchor Path:

$$\text{Price}_{\text{peak}} = \text{node.val} + \max(0, \text{leftGain}) + \max(0, \text{rightGain})$$

This path cannot be extended further upward to the parent because doing so would form a branch fork, violating the path constraint.

  1. The Branch Gain Contributed to Parent:

$$\text{Gain}_{\text{parent}} = \text{node.val} + \max(0, \max(\text{leftGain}, \text{rightGain}))$$

This selects at most ONE child branch so the parent can extend the path upward.

3.2 Complexity

  • Time Complexity: $O(N)$ — Each node is visited exactly once via post-order DFS.
  • Space Complexity: $O(H)$ — Recursion call stack bounded by tree height ($O(\log N)$ balanced, $O(N)$ skewed).

10 Senior / Staff-Level Interview Questions with In-Depth Answers:
Q1 What is the exact semantic difference between `ROW_NUMBER()`, `RANK()`, and `DENSE_RANK()`?
▼

Answer:

Given duplicate values in the ORDER BY clause (e.g., scores [100, 90, 90, 80]):

  • ROW_NUMBER(): Generates a strictly unique, contiguous sequence of integers (1, 2, 3, 4) regardless of value ties. The ordering among tied rows is non-deterministic unless additional tie-breaker columns are specified.
  • RANK(): Assigns identical ranks to tied rows, but skips subsequent rank numbers to match the row's 1-based ordinal position (1, 2, 2, 4). It leaves gaps in the sequence.
  • DENSE_RANK(): Assigns identical ranks to tied rows without leaving gaps in the sequence (1, 2, 2, 3).
  • Use cases:
  • Pagination / de-duplication: Use ROW_NUMBER().
  • Competition leaderboards (Olympic medal ties): Use RANK().
  • Salary bands / tier categories: Use DENSE_RANK().
Q2 How does the PostgreSQL query engine execute window functions, and how do you optimize them?
▼

Answer:

  1. Execution Steps:
  • The query planner groups rows via PARTITION BY and sorts them by ORDER BY.
  • Rows flow into a WindowAgg execution node which tracks state across the partitioned frame.
  1. Optimization Techniques:
  • Composite Index Matching: Create an index with the exact column order: CREATE INDEX idx_data ON my_table (partition_col, order_col). This allows the engine to stream rows directly into WindowAgg without an expensive Sort step.
  • work_mem Tuning: If the partition data exceeds work_mem, PostgreSQL spills sorted batches to disk (external merge Disk), multiplying query execution time. Increase work_mem specifically for analytical workloads.
  • Filter Pushdown via CTE / Subquery: Window functions cannot appear in WHERE clauses. Wrap in a subquery or CTE and filter on the outer query (e.g. WHERE row_num = 1).
Q3 Why is specifying `ROWS` instead of the default `RANGE` framing critical for window query performance?
▼

Answer:

  • The Pitfall: In SQL, specifying ORDER BY without a frame clause defaults to RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW.
  • The Problem with RANGE: RANGE groups rows with identical order values as "peers". The engine must read ahead to verify whether the next row has the same value before emitting a result. This forces buffering and prevents single-pass streaming.
  • The Fix with ROWS: Explicitly specify ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW or ROWS BETWEEN 5 PRECEDING AND CURRENT ROW. ROWS operates purely on row counts regardless of duplicates, executing in a high-speed $O(N)$ streaming pass with minimal memory overhead.
Q4 Explain the difference between Materialized and Inlined CTEs (`WITH` clauses) in PostgreSQL.
▼

Answer:

  • Prior to PostgreSQL 12: All CTEs acted as optimization fences—PostgreSQL always materialized CTE results into a temporary table in memory, preventing the optimizer from pushing outer WHERE predicates into the CTE.
  • PostgreSQL 12+ Behavior: By default, simple CTEs referenced only once are inlined into the main query plan, allowing predicate pushdown and index scans across CTE boundaries.
  • Explicit Keywords:
  • WITH data AS MATERIALIZED (...): Forces PostgreSQL to evaluate the CTE once and store the result set in memory, preventing repeated execution if referenced multiple times in union or joins.
  • WITH data AS NOT MATERIALIZED (...): Explicitly forces inlining, allowing the optimizer to push join conditions and indexes deep into the subquery.
Q5 How does declarative table partitioning work in PostgreSQL, and how does the planner perform Partition Pruning?
▼

Answer:

  • Architecture: A root parent table defines partition keys (PARTITION BY RANGE (recorded_at)), while child tables store actual physical tuples.
  • Partition Pruning:
  • Static Pruning (Plan-Time): If the query specifies literal constants (WHERE recorded_at >= '2026-10-01' AND recorded_at < '2026-11-01'), the optimizer evaluates partition constraints and excludes child tables from the generated plan.
  • Dynamic Pruning (Run-Time): If queries use parameterized values or dynamic functions (WHERE recorded_at >= $1), pruning occurs at execution time as parameters bind.
  • Impact: Transforms full table scans over multi-terabyte datasets into localized scans over a single 10 GB partition, reducing disk I/O and buffer cache churn by 99%+.
Q6 How do you perform zero-downtime data archival on high-volume tables (e.g. dropping data older than 90 days)?
▼

Answer:

  • Anti-Pattern (DELETE WHERE):
  • Executing DELETE FROM logs WHERE created_at < NOW() - INTERVAL '90 days' locks rows, writes massive dead tuples to WAL, exhausts replication bandwidth, and leaves table bloat that requires intrusive vacuum operations.
  • Partitioning Strategy (DROP TABLE):
  • Partition the table by month or week.
  • To retire data older than 90 days, run:
    ALTER TABLE logs DETACH PARTITION logs_y2025m01;
    DROP TABLE logs_y2025m01;
  • DETACH CONCURRENTLY decouples the partition without taking an exclusive lock on the parent table.
  • DROP TABLE instantaneously unlinks the underlying disk files at the filesystem level in milliseconds with zero WAL bloat.
Q7 Does PostgreSQL support global indexes across partitioned tables? How should indexes be designed?
▼

Answer:

  • No Global Indexes: Unlike Oracle, PostgreSQL does not support global indexes spanning across multiple partitions. Every index in PostgreSQL is local to its specific child partition.
  • Implications for Primary Keys:
  • Any PRIMARY KEY or UNIQUE constraint on a partitioned table must include the partition key columns (e.g. PRIMARY KEY (recorded_at, id)).
  • Without the partition key, PostgreSQL cannot enforce uniqueness across different child tables without scanning all partitions.
  • Local Index Optimization: Each child table can have specialized local indexes tailored to its data access patterns (e.g. partial indexes or BRIN indexes for older read-only archival partitions vs B-Trees for recent partitions).
Q8 How do you write an analytical query to calculate rolling 7-day moving averages and daily growth deltas on time-series data?
▼

Answer:

WITH DailyTotals AS (
    SELECT 
        account_id,
        DATE_TRUNC('day', trans_time) AS trans_day,
        SUM(amount) AS daily_amount
    FROM transactions
    WHERE trans_time >= NOW() - INTERVAL '60 days'
    GROUP BY account_id, DATE_TRUNC('day', trans_time)
)
SELECT 
    account_id,
    trans_day,
    daily_amount,
    -- 1. Day-over-day delta using LAG
    daily_amount - LAG(daily_amount, 1, 0) OVER (
        PARTITION BY account_id ORDER BY trans_day
    ) AS daily_delta,
    -- 2. 7-day moving average using frame specification
    AVG(daily_amount) OVER (
        PARTITION BY account_id 
        ORDER BY trans_day 
        ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
    ) AS rolling_7day_avg
FROM DailyTotals
ORDER BY account_id, trans_day;
Q9 Walk through LeetCode #124 (Binary Tree Maximum Path Sum). Why does a node calculate two different sums during traversal?
▼

Answer:

  • The Core Constraint: A valid tree path cannot fork; a node can only connect to at most one parent and at most one child branch when extended.
  • The Two Sums:
  1. Peak Anchor Sum (Internal Candidate):

$$\text{PathSum} = \text{node.val} + \max(0, \text{leftGain}) + \max(0, \text{rightGain})$$

Here, the path turns around node (traveling from the left child, through node, down to the right child). This path cannot be extended further up to the parent. We update the global maximum with this value.

  1. Branch Contribution (Returned to Parent):

$$\text{Gain}_{\text{return}} = \text{node.val} + \max(0, \max(\text{leftGain}, \text{rightGain}))$$

The node can extend only ONE branch to its parent. Negative branch sums are clamped to $0$ to avoid diminishing the total.

  • Complexity: $O(N)$ time visiting each node once; $O(H)$ recursion stack space.
Q10 How do you handle edge cases in LeetCode #124 when all node values in the tree are negative?
▼

Answer:

  • The Edge Case: Consider a tree where every node is negative, e.g. [-5, -10, -2].
  • Handling:
  • The problem requires a non-empty path (at least one node must be picked).
  • If we initialize maxSum = 0, the solver would erroneously return 0 instead of -2!
  • Correct Approach:
  1. Initialize maxSum = int.MinValue.
  2. Clamp subtree gains with Math.Max(0, childGain). For leaf nodes with negative values, leftGain = 0 and rightGain = 0.
  3. The peak anchor sum is node.val + 0 + 0 = node.val.
  4. The global maximum updates to Math.Max(int.MinValue, -2) = -2.
  5. The result correctly selects the single least negative node.

using System;

namespace Day24.AdvancedSql;

/// <summary>
/// Standard Binary Tree Node definition.
/// </summary>
public class TreeNode
{
    public int val;
    public TreeNode? left;
    public TreeNode? right;

    public TreeNode(int val = 0, TreeNode? left = null, TreeNode? right = null)
    {
        this.val = val;
        this.left = left;
        this.right = right;
    }
}

/// <summary>
/// LeetCode #124: Binary Tree Maximum Path Sum (Hard).
/// Solved via Post-Order DFS with bottom-up dynamic programming.
/// Computes maximum contribution gain from child subtrees while tracking the optimal peak path sum.
/// Time Complexity: O(N) | Space Complexity: O(H) recursion stack.
/// </summary>
public class MaxPathSumSolver
{
    private int _maxPathSum;

    public int MaxPathSum(TreeNode? root)
    {
        if (root == null) return 0;

        _maxPathSum = int.MinValue;
        CalculateMaxGain(root);
        return _maxPathSum;
    }

    private int CalculateMaxGain(TreeNode? node)
    {
        if (node == null) return 0;

        // Post-order: Evaluate subtrees first. Ignore negative path branches (clamp to 0).
        int leftGain = Math.Max(0, CalculateMaxGain(node.left));
        int rightGain = Math.Max(0, CalculateMaxGain(node.right));

        // Path passing through current node as the peak anchor
        int currentPathSum = node.val + leftGain + rightGain;

        // Update global maximum path sum
        _maxPathSum = Math.Max(_maxPathSum, currentPathSum);

        // Return maximum branch gain current node can contribute to its parent
        return node.val + Math.Max(leftGain, rightGain);
    }
}

/// <summary>
/// PostgreSQL Declarative Table Partitioning Architecture Simulator.
/// Models range partitioning, query planner partition pruning, and zero-downtime maintenance.
/// </summary>
public class TablePartitioningStrategy
{
    private readonly List<PartitionMetadata> _partitions = new();

    public IReadOnlyList<PartitionMetadata> Partitions => _partitions;

    public void RegisterPartition(string tableName, DateTime startUtc, DateTime endUtc, long rowCount, double sizeMb)
    {
        _partitions.Add(new PartitionMetadata(tableName, startUtc, endUtc, rowCount, sizeMb));
    }

    /// <summary>
    /// Simulates PostgreSQL EXPLAIN query plan partition pruning for a given time interval filter.
    /// </summary>
    public PartitionPruningPlan SimulatePruning(DateTime queryStartUtc, DateTime queryEndUtc)
    {
        var scanned = new List<string>();
        var pruned = new List<string>();
        double scannedMb = 0;
        double savedMb = 0;

        foreach (var p in _partitions)
        {
            // Partition overlaps query range if:
            // p.RangeStart < queryEnd AND p.RangeEnd > queryStart
            bool overlaps = p.RangeStartUtc < queryEndUtc && p.RangeEndUtc > queryStartUtc;

            if (overlaps)
            {
                scanned.Add(p.TableName);
                scannedMb += p.SizeMb;
            }
            else
            {
                pruned.Add(p.TableName);
                savedMb += p.SizeMb;
            }
        }

        return new PartitionPruningPlan(
            QueryStartUtc: queryStartUtc,
            QueryEndUtc: queryEndUtc,
            ScannedPartitions: scanned,
            PrunedPartitions: pruned,
            TotalScannedSizeMb: Math.Round(scannedMb, 2),
            TotalSavingsSizeMb: Math.Round(savedMb, 2)
        );
    }

    /// <summary>
    /// Generates DDL scripts for declarative range partitioning in PostgreSQL.
    /// </summary>
    public static string GeneratePostgreSqlDdl(int year, int month)
    {
        var nextMonthDate = new DateTime(year, month, 1).AddMonths(1);
        var partName = $"sensor_readings_y{year:0000}m{month:00}";
        var startStr = $"{year:0000}-{month:00}-01 00:00:00+00";

using System;
using System.Collections.Generic;
using System.Linq;

namespace Day24.AdvancedSql;

public record WindowRowResult<T>(
    T Item,
    long RowNumber,
    long Rank,
    long DenseRank,
    decimal RunningTotal,
    decimal MovingAverage,
    decimal? LagValue,
    decimal? LeadValue
);

/// <summary>
/// In-Memory Analytical SQL Window Functions Engine & Query Generator.
/// Implements standard SQL ANSI:2003 window function semantics:
/// - ROW_NUMBER(): Strict sequential increment per partition
/// - RANK(): Tied ranks with ordinal gap skipping
/// - DENSE_RANK(): Tied ranks without ordinal gaps
/// - LAG() / LEAD(): Inter-row comparative lookups
/// - Moving averages & cumulative running frames
/// </summary>
public static class WindowFunctionsEngine
{
    public static List<WindowRowResult<T>> EvaluateWindowFunctions<T, TKey, TOrder>(
        IEnumerable<T> source,
        Func<T, TKey> partitionSelector,
        Func<T, TOrder> orderSelector,
        Func<T, decimal> metricSelector,
        int movingAverageWindow = 3,
        bool ascending = true)
        where TKey : notnull
        where TOrder : IComparable<TOrder>
    {
        var results = new List<WindowRowResult<T>>();

        var grouped = source.GroupBy(partitionSelector);

        foreach (var group in grouped)
        {
            var orderedList = ascending
                ? group.OrderBy(orderSelector).ToList()
                : group.OrderByDescending(orderSelector).ToList();

            decimal runningSum = 0m;
            var metricHistory = new List<decimal>();

            long denseRankCounter = 0;
            TOrder? lastOrderVal = default;
            bool isFirst = true;

            for (int i = 0; i < orderedList.Count; i++)
            {
                var item = orderedList[i];
                var orderVal = orderSelector(item);
                var metric = metricSelector(item);

                // 1. ROW_NUMBER(): 1-based sequential index
                long rowNumber = i + 1;

                // 2 & 3. RANK() and DENSE_RANK()
                long rank;
                if (isFirst || !EqualityComparer<TOrder>.Default.Equals(orderVal, lastOrderVal))
                {
                    rank = i + 1;
                    denseRankCounter++;
                    lastOrderVal = orderVal;
                    isFirst = false;
                }
                else
                {
                    // Tied rank: duplicate previous rank
                    rank = results.Count > 0 ? results[^1].Rank : 1;
                }
                long denseRank = denseRankCounter;

                // 4. Running Total
                runningSum += metric;

                // 5. Moving Average (ROWS BETWEEN (windowSize-1) PRECEDING AND CURRENT ROW)
                metricHistory.Add(metric);
                var windowSlice = metricHistory.TakeLast(movingAverageWindow).ToList();
                decimal movingAvg = Math.Round(windowSlice.Average(), 4);

                // 6. LAG(1)
                decimal? lag = i > 0 ? metricSelector(orderedList[i - 1]) : null;

                // 7. LEAD(1)
                decimal? lead = i < orderedList.Count - 1 ? metricSelector(orderedList[i + 1]) : null;

                results.Add(new WindowRowResult<T>(
                    Item: item,
                    RowNumber: rowNumber,
                    Rank: rank,
                    DenseRank: denseRank,
                    RunningTotal: runningSum,
                    MovingAverage: movingAvg,
                    LagValue: lag,
                    LeadValue: lead
                ));
            }
        }

        return results;
    }

    /// <summary>
    /// Generates reference production-grade PostgreSQL analytical query featuring CTEs, Windowing, and Partitions.
    /// </summary>
    public static string GeneratePostgreSqlAnalyticalQuery()
    {
        return @"
WITH TimeSeriesDailyAggregates AS (
    SELECT 
        device_id,
        DATE_TRUNC('day', recorded_at) AS reading_day,
        AVG(temperature) AS avg_daily_temp,
        MAX(voltage) AS max_voltage
    FROM sensor_readings
    WHERE recorded_at >= NOW() - INTERVAL '30 days'
    GROUP BY device_id, DATE_TRUNC('day', recorded_at)
),
WindowRankings AS (
    SELECT
        device_id,
        reading_day,
        avg_daily_temp,
        ROW_NUMBER() OVER (PARTITION BY device_id ORDER BY reading_day ASC) AS row_num,
        RANK() OVER (PARTITION BY device_id ORDER BY avg_daily_temp DESC) AS temp_rank,
        DENSE_RANK() OVER (PARTITION BY device_id ORDER BY avg_daily_temp DESC) AS dense_temp_rank,
        LAG(avg_daily_temp, 1) OVER (PARTITION BY device_id ORDER BY reading_day ASC) AS prev_day_temp,
        LEAD(avg_daily_temp, 1) OVER (PARTITION BY device_id ORDER BY reading_day ASC) AS next_day_temp,
        AVG(avg_daily_temp) OVER (
            PARTITION BY device_id 
            ORDER BY reading_day ASC 
            ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
        ) AS seven_day_moving_avg
    FROM TimeSeriesDailyAggregates
)
SELECT 
    device_id,
    reading_day,
    avg_daily_temp,
    (avg_daily_temp - prev_day_temp) AS daily_temp_delta,
    seven_day_moving_avg,
    temp_rank,
    dense_temp_rank
FROM WindowRankings
ORDER BY device_id, reading_day;".Trim();
    }
}

📝 Part 1: Deep-Dive Architectural & Engineering Notes

Day 24: Deep Dive — SQL Windowing, Partitioning & Tree Path Optimization

1. Window Functions Internals in PostgreSQL

Window functions perform calculations across sets of table rows related to the current row without collapsing multiple rows into a single summary row (unlike GROUP BY).

1.1 The PostgreSQL WindowAgg Node

  • In an EXPLAIN (ANALYZE, BUFFERS) execution plan, window functions introduce a WindowAgg node.
  • Pre-requisite: The input rows must be sorted according to PARTITION BY and ORDER BY. If no index matches the ordering, PostgreSQL inserts an explicit Sort node.
  • Memory Impact: The sorted rows are spooled into a tuplestore in memory (work_mem). If the partition size exceeds work_mem, it spills to temporary disk files (Sort Method: external merge Disk), causing severe I/O degradation.

1.2 Window Framing: ROWS vs RANGE

  • Default Framing: When ORDER BY is specified without an explicit frame, SQL defaults to:

$$\text{RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW}$$

  • Performance Hazard: RANGE evaluates duplicate peer values (all rows with the same ORDER BY value belong to the same range). This requires looking ahead and buffering rows.
  • Best Practice: Always specify ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW (or custom bounds) if exact physical rows are desired. ROWS executes in a single streaming pass ($O(N)$), saving CPU and memory.

2. Declarative Table Partitioning Architecture

PostgreSQL declarative partitioning splits large tables into smaller physical chunks while presenting a single virtual relation to applications.

                  ┌─────────────────────────────────┐
                  │ sensor_readings (Virtual Parent)│
                  │   PARTITION BY RANGE (recorded) │
                  └────────────────┬────────────────┘
                                   │
         ┌─────────────────────────┼─────────────────────────┐
         ▼                         ▼                         ▼
┌──────────────────┐      ┌──────────────────┐      ┌──────────────────┐
│  sensor_2026_m08 │      │  sensor_2026_m09 │      │  sensor_2026_m10 │
│ [Aug 1 - Sep 1)  │      │ [Sep 1 - Oct 1)  │      │ [Oct 1 - Nov 1)  │
└──────────────────┘      └──────────────────┘      └──────────────────┘

2.1 Partition Pruning Mechanics

  • Static Pruning: Occurs during query planning when query constants are known (WHERE recorded_at >= '2026-10-01'). The optimizer removes non-matching partitions from the plan before execution begins.
  • Run-Time Pruning: Occurs during execution when filters involve parameters or volatile functions (WHERE recorded_at >= CURRENT_DATE - 7). The executor evaluates bounds on the fly and skips entire sub-table scans.

2.2 Maintenance: DROP TABLE vs. DELETE

  • Why DELETE Fails on Big Data:
  • DELETE FROM sensor_readings WHERE recorded_at < '2025-01-01' writes an MVCC dead tuple marker for every deleted row.
  • Generates massive Write-Ahead Log (WAL) traffic, saturating replication bandwidth.
  • Leaves table and index disk pages bloated until costly VACUUM FULL is performed.
  • The Partitioning Advantage:
  • DROP TABLE sensor_readings_y2025m01;
  • Instantly unlinks the underlying disk file in $O(1)$ time.
  • Generates negligible WAL entries, causes zero disk fragmentation, and requires zero vacuum debt.

3. DSA: LeetCode #124 (Binary Tree Maximum Path Sum)

3.1 The Two Distinctions of a Node's Value

In a binary tree, a valid path can turn at most once at its highest peak node:

  1. The Peak Anchor Path:

$$\text{Price}_{\text{peak}} = \text{node.val} + \max(0, \text{leftGain}) + \max(0, \text{rightGain})$$

This path cannot be extended further upward to the parent because doing so would form a branch fork, violating the path constraint.

  1. The Branch Gain Contributed to Parent:

$$\text{Gain}_{\text{parent}} = \text{node.val} + \max(0, \max(\text{leftGain}, \text{rightGain}))$$

This selects at most ONE child branch so the parent can extend the path upward.

3.2 Complexity

  • Time Complexity: $O(N)$ — Each node is visited exactly once via post-order DFS.
  • Space Complexity: $O(H)$ — Recursion call stack bounded by tree height ($O(\log N)$ balanced, $O(N)$ skewed).

Q1 What is the exact semantic difference between `ROW_NUMBER()`, `RANK()`, and `DENSE_RANK()`?
▼

Answer:

Given duplicate values in the ORDER BY clause (e.g., scores [100, 90, 90, 80]):

  • ROW_NUMBER(): Generates a strictly unique, contiguous sequence of integers (1, 2, 3, 4) regardless of value ties. The ordering among tied rows is non-deterministic unless additional tie-breaker columns are specified.
  • RANK(): Assigns identical ranks to tied rows, but skips subsequent rank numbers to match the row's 1-based ordinal position (1, 2, 2, 4). It leaves gaps in the sequence.
  • DENSE_RANK(): Assigns identical ranks to tied rows without leaving gaps in the sequence (1, 2, 2, 3).
  • Use cases:
  • Pagination / de-duplication: Use ROW_NUMBER().
  • Competition leaderboards (Olympic medal ties): Use RANK().
  • Salary bands / tier categories: Use DENSE_RANK().
Q2 How does the PostgreSQL query engine execute window functions, and how do you optimize them?
▼

Answer:

  1. Execution Steps:
  • The query planner groups rows via PARTITION BY and sorts them by ORDER BY.
  • Rows flow into a WindowAgg execution node which tracks state across the partitioned frame.
  1. Optimization Techniques:
  • Composite Index Matching: Create an index with the exact column order: CREATE INDEX idx_data ON my_table (partition_col, order_col). This allows the engine to stream rows directly into WindowAgg without an expensive Sort step.
  • work_mem Tuning: If the partition data exceeds work_mem, PostgreSQL spills sorted batches to disk (external merge Disk), multiplying query execution time. Increase work_mem specifically for analytical workloads.
  • Filter Pushdown via CTE / Subquery: Window functions cannot appear in WHERE clauses. Wrap in a subquery or CTE and filter on the outer query (e.g. WHERE row_num = 1).
Q3 Why is specifying `ROWS` instead of the default `RANGE` framing critical for window query performance?
▼

Answer:

  • The Pitfall: In SQL, specifying ORDER BY without a frame clause defaults to RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW.
  • The Problem with RANGE: RANGE groups rows with identical order values as "peers". The engine must read ahead to verify whether the next row has the same value before emitting a result. This forces buffering and prevents single-pass streaming.
  • The Fix with ROWS: Explicitly specify ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW or ROWS BETWEEN 5 PRECEDING AND CURRENT ROW. ROWS operates purely on row counts regardless of duplicates, executing in a high-speed $O(N)$ streaming pass with minimal memory overhead.
Q4 Explain the difference between Materialized and Inlined CTEs (`WITH` clauses) in PostgreSQL.
▼

Answer:

  • Prior to PostgreSQL 12: All CTEs acted as optimization fences—PostgreSQL always materialized CTE results into a temporary table in memory, preventing the optimizer from pushing outer WHERE predicates into the CTE.
  • PostgreSQL 12+ Behavior: By default, simple CTEs referenced only once are inlined into the main query plan, allowing predicate pushdown and index scans across CTE boundaries.
  • Explicit Keywords:
  • WITH data AS MATERIALIZED (...): Forces PostgreSQL to evaluate the CTE once and store the result set in memory, preventing repeated execution if referenced multiple times in union or joins.
  • WITH data AS NOT MATERIALIZED (...): Explicitly forces inlining, allowing the optimizer to push join conditions and indexes deep into the subquery.
Q5 How does declarative table partitioning work in PostgreSQL, and how does the planner perform Partition Pruning?
▼

Answer:

  • Architecture: A root parent table defines partition keys (PARTITION BY RANGE (recorded_at)), while child tables store actual physical tuples.
  • Partition Pruning:
  • Static Pruning (Plan-Time): If the query specifies literal constants (WHERE recorded_at >= '2026-10-01' AND recorded_at < '2026-11-01'), the optimizer evaluates partition constraints and excludes child tables from the generated plan.
  • Dynamic Pruning (Run-Time): If queries use parameterized values or dynamic functions (WHERE recorded_at >= $1), pruning occurs at execution time as parameters bind.
  • Impact: Transforms full table scans over multi-terabyte datasets into localized scans over a single 10 GB partition, reducing disk I/O and buffer cache churn by 99%+.
Q6 How do you perform zero-downtime data archival on high-volume tables (e.g. dropping data older than 90 days)?
▼

Answer:

  • Anti-Pattern (DELETE WHERE):
  • Executing DELETE FROM logs WHERE created_at < NOW() - INTERVAL '90 days' locks rows, writes massive dead tuples to WAL, exhausts replication bandwidth, and leaves table bloat that requires intrusive vacuum operations.
  • Partitioning Strategy (DROP TABLE):
  • Partition the table by month or week.
  • To retire data older than 90 days, run:
    ALTER TABLE logs DETACH PARTITION logs_y2025m01;
    DROP TABLE logs_y2025m01;
  • DETACH CONCURRENTLY decouples the partition without taking an exclusive lock on the parent table.
  • DROP TABLE instantaneously unlinks the underlying disk files at the filesystem level in milliseconds with zero WAL bloat.
Q7 Does PostgreSQL support global indexes across partitioned tables? How should indexes be designed?
▼

Answer:

  • No Global Indexes: Unlike Oracle, PostgreSQL does not support global indexes spanning across multiple partitions. Every index in PostgreSQL is local to its specific child partition.
  • Implications for Primary Keys:
  • Any PRIMARY KEY or UNIQUE constraint on a partitioned table must include the partition key columns (e.g. PRIMARY KEY (recorded_at, id)).
  • Without the partition key, PostgreSQL cannot enforce uniqueness across different child tables without scanning all partitions.
  • Local Index Optimization: Each child table can have specialized local indexes tailored to its data access patterns (e.g. partial indexes or BRIN indexes for older read-only archival partitions vs B-Trees for recent partitions).

Q9 Walk through LeetCode #124 (Binary Tree Maximum Path Sum). Why does a node calculate two different sums during traversal?
▼

Answer:

  • The Core Constraint: A valid tree path cannot fork; a node can only connect to at most one parent and at most one child branch when extended.
  • The Two Sums:
  1. Peak Anchor Sum (Internal Candidate):

$$\text{PathSum} = \text{node.val} + \max(0, \text{leftGain}) + \max(0, \text{rightGain})$$

Here, the path turns around node (traveling from the left child, through node, down to the right child). This path cannot be extended further up to the parent. We update the global maximum with this value.

  1. Branch Contribution (Returned to Parent):

$$\text{Gain}_{\text{return}} = \text{node.val} + \max(0, \max(\text{leftGain}, \text{rightGain}))$$

The node can extend only ONE branch to its parent. Negative branch sums are clamped to $0$ to avoid diminishing the total.

  • Complexity: $O(N)$ time visiting each node once; $O(H)$ recursion stack space.
Q10 How do you handle edge cases in LeetCode #124 when all node values in the tree are negative?
▼

Answer:

  • The Edge Case: Consider a tree where every node is negative, e.g. [-5, -10, -2].
  • Handling:
  • The problem requires a non-empty path (at least one node must be picked).
  • If we initialize maxSum = 0, the solver would erroneously return 0 instead of -2!
  • Correct Approach:
  1. Initialize maxSum = int.MinValue.
  2. Clamp subtree gains with Math.Max(0, childGain). For leaf nodes with negative values, leftGain = 0 and rightGain = 0.
  3. The peak anchor sum is node.val + 0 + 0 = node.val.
  4. The global maximum updates to Math.Max(int.MinValue, -2) = -2.
  5. The result correctly selects the single least negative node.

using System;

namespace Day24.AdvancedSql;

/// <summary>
/// Standard Binary Tree Node definition.
/// </summary>
public class TreeNode
{
    public int val;
    public TreeNode? left;
    public TreeNode? right;

    public TreeNode(int val = 0, TreeNode? left = null, TreeNode? right = null)
    {
        this.val = val;
        this.left = left;
        this.right = right;
    }
}

/// <summary>
/// LeetCode #124: Binary Tree Maximum Path Sum (Hard).
/// Solved via Post-Order DFS with bottom-up dynamic programming.
/// Computes maximum contribution gain from child subtrees while tracking the optimal peak path sum.
/// Time Complexity: O(N) | Space Complexity: O(H) recursion stack.
/// </summary>
public class MaxPathSumSolver
{
    private int _maxPathSum;

    public int MaxPathSum(TreeNode? root)
    {
        if (root == null) return 0;

        _maxPathSum = int.MinValue;
        CalculateMaxGain(root);
        return _maxPathSum;
    }

    private int CalculateMaxGain(TreeNode? node)
    {
        if (node == null) return 0;

        // Post-order: Evaluate subtrees first. Ignore negative path branches (clamp to 0).
        int leftGain = Math.Max(0, CalculateMaxGain(node.left));
        int rightGain = Math.Max(0, CalculateMaxGain(node.right));

        // Path passing through current node as the peak anchor
        int currentPathSum = node.val + leftGain + rightGain;

        // Update global maximum path sum
        _maxPathSum = Math.Max(_maxPathSum, currentPathSum);

        // Return maximum branch gain current node can contribute to its parent
        return node.val + Math.Max(leftGain, rightGain);
    }
}

using System;
using System.Collections.Generic;
using System.Linq;

namespace Day24.AdvancedSql;

public record PartitionMetadata(
    string TableName,
    DateTime RangeStartUtc,
    DateTime RangeEndUtc,
    long RowCount,
    double SizeMb
);

public record PartitionPruningPlan(
    DateTime QueryStartUtc,
    DateTime QueryEndUtc,
    List<string> ScannedPartitions,
    List<string> PrunedPartitions,
    double TotalScannedSizeMb,
    double TotalSavingsSizeMb
);

/// <summary>
/// PostgreSQL Declarative Table Partitioning Architecture Simulator.
/// Models range partitioning, query planner partition pruning, and zero-downtime maintenance.
/// </summary>
public class TablePartitioningStrategy
{
    private readonly List<PartitionMetadata> _partitions = new();

    public IReadOnlyList<PartitionMetadata> Partitions => _partitions;

    public void RegisterPartition(string tableName, DateTime startUtc, DateTime endUtc, long rowCount, double sizeMb)
    {
        _partitions.Add(new PartitionMetadata(tableName, startUtc, endUtc, rowCount, sizeMb));
    }

    /// <summary>
    /// Simulates PostgreSQL EXPLAIN query plan partition pruning for a given time interval filter.
    /// </summary>
    public PartitionPruningPlan SimulatePruning(DateTime queryStartUtc, DateTime queryEndUtc)
    {
        var scanned = new List<string>();
        var pruned = new List<string>();
        double scannedMb = 0;
        double savedMb = 0;

        foreach (var p in _partitions)
        {
            // Partition overlaps query range if:
            // p.RangeStart < queryEnd AND p.RangeEnd > queryStart
            bool overlaps = p.RangeStartUtc < queryEndUtc && p.RangeEndUtc > queryStartUtc;

            if (overlaps)
            {
                scanned.Add(p.TableName);
                scannedMb += p.SizeMb;
            }
            else
            {
                pruned.Add(p.TableName);
                savedMb += p.SizeMb;
            }
        }

        return new PartitionPruningPlan(
            QueryStartUtc: queryStartUtc,
            QueryEndUtc: queryEndUtc,
            ScannedPartitions: scanned,
            PrunedPartitions: pruned,
            TotalScannedSizeMb: Math.Round(scannedMb, 2),
            TotalSavingsSizeMb: Math.Round(savedMb, 2)
        );
    }

    /// <summary>
    /// Generates DDL scripts for declarative range partitioning in PostgreSQL.
    /// </summary>
    public static string GeneratePostgreSqlDdl(int year, int month)
    {
        var nextMonthDate = new DateTime(year, month, 1).AddMonths(1);
        var partName = $"sensor_readings_y{year:0000}m{month:00}";

using System;
using System.Collections.Generic;
using System.Linq;

namespace Day24.AdvancedSql;

public record WindowRowResult<T>(
    T Item,
    long RowNumber,
    long Rank,
    long DenseRank,
    decimal RunningTotal,
    decimal MovingAverage,
    decimal? LagValue,
    decimal? LeadValue
);

/// <summary>
/// In-Memory Analytical SQL Window Functions Engine & Query Generator.
/// Implements standard SQL ANSI:2003 window function semantics:
/// - ROW_NUMBER(): Strict sequential increment per partition
/// - RANK(): Tied ranks with ordinal gap skipping
/// - DENSE_RANK(): Tied ranks without ordinal gaps
/// - LAG() / LEAD(): Inter-row comparative lookups
/// - Moving averages & cumulative running frames
/// </summary>
public static class WindowFunctionsEngine
{
    public static List<WindowRowResult<T>> EvaluateWindowFunctions<T, TKey, TOrder>(
        IEnumerable<T> source,
        Func<T, TKey> partitionSelector,
        Func<T, TOrder> orderSelector,
        Func<T, decimal> metricSelector,
        int movingAverageWindow = 3,
        bool ascending = true)
        where TKey : notnull
        where TOrder : IComparable<TOrder>
    {
        var results = new List<WindowRowResult<T>>();

        var grouped = source.GroupBy(partitionSelector);

        foreach (var group in grouped)
        {
            var orderedList = ascending
                ? group.OrderBy(orderSelector).ToList()
                : group.OrderByDescending(orderSelector).ToList();

            decimal runningSum = 0m;
            var metricHistory = new List<decimal>();

            long denseRankCounter = 0;
            TOrder? lastOrderVal = default;
            bool isFirst = true;

            for (int i = 0; i < orderedList.Count; i++)
            {
                var item = orderedList[i];
                var orderVal = orderSelector(item);
                var metric = metricSelector(item);

                // 1. ROW_NUMBER(): 1-based sequential index
                long rowNumber = i + 1;

                // 2 & 3. RANK() and DENSE_RANK()
                long rank;
                if (isFirst || !EqualityComparer<TOrder>.Default.Equals(orderVal, lastOrderVal))
                {
                    rank = i + 1;
                    denseRankCounter++;
                    lastOrderVal = orderVal;
                    isFirst = false;
                }
                else
                {
                    // Tied rank: duplicate previous rank
                    rank = results.Count > 0 ? results[^1].Rank : 1;
                }
                long denseRank = denseRankCounter;

                // 4. Running Total
                runningSum += metric;

                // 5. Moving Average (ROWS BETWEEN (windowSize-1) PRECEDING AND CURRENT ROW)
                metricHistory.Add(metric);
                var windowSlice = metricHistory.TakeLast(movingAverageWindow).ToList();
                decimal movingAvg = Math.Round(windowSlice.Average(), 4);

                // 6. LAG(1)
                decimal? lag = i > 0 ? metricSelector(orderedList[i - 1]) : null;

                // 7. LEAD(1)
                decimal? lead = i < orderedList.Count - 1 ? metricSelector(orderedList[i + 1]) : null;

                results.Add(new WindowRowResult<T>(
                    Item: item,
                    RowNumber: rowNumber,
                    Rank: rank,
                    DenseRank: denseRank,
                    RunningTotal: runningSum,
                    MovingAverage: movingAvg,
                    LagValue: lag,
                    LeadValue: lead
                ));
            }
        }

        return results;
    }

    /// <summary>
    /// Generates reference production-grade PostgreSQL analytical query featuring CTEs, Windowing, and Partitions.
    /// </summary>
    public static string GeneratePostgreSqlAnalyticalQuery()
    {
        return @"
WITH TimeSeriesDailyAggregates AS (
    SELECT 
        device_id,
        DATE_TRUNC('day', recorded_at) AS reading_day,
        AVG(temperature) AS avg_daily_temp,
        MAX(voltage) AS max_voltage
    FROM sensor_readings
    WHERE recorded_at >= NOW() - INTERVAL '30 days'
    GROUP BY device_id, DATE_TRUNC('day', recorded_at)
),
WindowRankings AS (
    SELECT
        device_id,
        reading_day,
        avg_daily_temp,
        ROW_NUMBER() OVER (PARTITION BY device_id ORDER BY reading_day ASC) AS row_num,
        RANK() OVER (PARTITION BY device_id ORDER BY avg_daily_temp DESC) AS temp_rank,
        DENSE_RANK() OVER (PARTITION BY device_id ORDER BY avg_daily_temp DESC) AS dense_temp_rank,
        LAG(avg_daily_temp, 1) OVER (PARTITION BY device_id ORDER BY reading_day ASC) AS prev_day_temp,
        LEAD(avg_daily_temp, 1) OVER (PARTITION BY device_id ORDER BY reading_day ASC) AS next_day_temp,
        AVG(avg_daily_temp) OVER (
            PARTITION BY device_id 
            ORDER BY reading_day ASC 
            ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
        ) AS seven_day_moving_avg
    FROM TimeSeriesDailyAggregates
)
SELECT 
    device_id,
    reading_day,
    avg_daily_temp,
    (avg_daily_temp - prev_day_temp) AS daily_temp_delta,
    seven_day_moving_avg,
    temp_rank,
    dense_temp_rank
FROM WindowRankings
ORDER BY device_id, reading_day;".Trim();
    }
}
