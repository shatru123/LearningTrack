1. AMQP Dead-Letter Protocol & Wire Semantics

The AMQP Dead-Letter Specification

Under the AMQP 0-9-1 specification, a message entering an AMQP queue can be transitioned to dead-letter status under three exact conditions:

  1. Explicit Negative Acknowledgment:
  • basic.reject(deliveryTag, requeue = false)
  • basic.nack(deliveryTag, multiple = false, requeue = false)

When requeue = true, the broker places the message back into its original position in the queue. When requeue = false, if x-dead-letter-exchange is declared, the message is immediately routed to that exchange; otherwise, it is silently dropped into the ether.

  1. Time-To-Live (TTL) Expiration:
  • Queue-level TTL (x-message-ttl): Automatically configured on queue declaration.
  • Message-level TTL (expiration header): Declared per publication.
  1. Queue Length Overflow:
  • x-max-length: Maximum count of ready messages.
  • x-max-length-bytes: Maximum total payload size in bytes.
  • x-overflow: Determines behavior when full (drop-head, reject-publish, or reject-publish-dlx).

The x-death Header Architecture

When RabbitMQ dead-letters a message, it modifies the message headers by prepending a hash to the x-death array:

{
  "x-death": [
    {
      "count": 1,
      "exchange": "orders.direct",
      "queue": "orders.work",
      "reason": "rejected",
      "routing-keys": ["orders.work"],
      "time": 1729000000
    }
  ]
}

Critical Production Gotcha: If a message transitions through multiple dead-letter hops (e.g. work $\to$ retry.5s $\to$ work $\to$ retry.30s $\to$ dlq), RabbitMQ updates the count for existing queue entries or inserts a new element at index 0. To calculate total historical retries across multiple queues, your inspection tool must sum the count fields across all elements matching the root processing queue.

2. RabbitMQ TTL Retry Pitfalls: Head-of-Line Blocking

Why Variable Per-Message TTL Causes Head-of-Line Blocking

A common architectural mistake is using a single retry queue with variable per-message expiration headers:

// ANTI-PATTERN:
await channel.BasicPublishAsync(exchange: "", routingKey: "orders.retry", mandatory: true, basicProperties: new BasicProperties { Expiration = "30000" }, body: body1);
await channel.BasicPublishAsync(exchange: "", routingKey: "orders.retry", mandatory: true, basicProperties: new BasicProperties { Expiration = "5000" }, body: body2);

Why this fails: In standard RabbitMQ classic and quorum queues, messages are evaluated for expiration only when they reach the head of the queue. If message 1 has a 30-second TTL and message 2 has a 5-second TTL, message 2 will NOT expire and dead-letter after 5 seconds! It remains trapped behind message 1 for the full 30 seconds.

The Correct Production Solution: Multi-Stage Discrete Delay Queues

Create discrete queues with fixed queue-level x-message-ttl:

  • orders.retry.5s: x-message-ttl = 5000, DLX $\to$ orders.work
  • orders.retry.30s: x-message-ttl = 30000, DLX $\to$ orders.work
  • orders.retry.2m: x-message-ttl = 120000, DLX $\to$ orders.work
  • orders.dlq: Final poison holding queue (retained for manual inspection and replay).

Because all messages in a given queue have identical TTL, messages always expire in strict FIFO order, preventing Head-of-Line blocking entirely.

3. MassTransit Architecture & Saga State Machines

The MassTransit Pipeline Engine

MassTransit builds an asynchronous message pipeline inspired by the Russian Doll middleware pattern (GreenPipes):

Transport (RabbitMQ) 
  ---> DeserializationFilter 
    ---> ScopedFilter (DI Scope per message) 
      ---> RetryFilter (In-memory backoff) 
        ---> RedeliveryFilter (Delayed exchange) 
          ---> OutboxFilter (Transactional Outbox) 
            ---> Consumer / Saga State Machine

Saga Orchestration vs Choreography

  • Choreography: Each service listens to domain events and decides its own local action without centralized coordination. Works well for simple 2-3 step workflows, but becomes impossible to debug and trace in complex flows.
  • Orchestration (MassTransit Saga State Machine): A centralized state coordinator (OrderStateMachine) listens to events, tracks global state in a persistent instance table, and dispatches direct commands (ReserveInventory, AuthorizePayment).

Concurrency & Locking in Sagas

When concurrent events arrive for the same saga instance (e.g. PaymentCompleted and InventoryUnavailable dispatched simultaneously):

  1. Optimistic Concurrency: MassTransit tracks a RowVersion or Version property. If two threads attempt to commit state transitions simultaneously, one commits and the second throws DbUpdateConcurrencyException. MassTransit's retry middleware automatically catches the concurrency exception and re-reads the updated saga state.
  2. Pessimistic Concurrency: Acquires a database row lock (SELECT ... FOR UPDATE) before executing saga activity.

4. DSA Deep Dive: Topological Sorting

Directed Acyclic Graph (DAG) Foundations

A Topological Sort of a directed graph $G = (V, E)$ is a linear ordering of its vertices such that for every directed edge $(u, v)$, node $u$ comes before $v$ in the ordering.

A graph admits a topological sort if and only if it is a Directed Acyclic Graph (DAG).

  • Space Complexity: $\mathcal{O}(V + E)$ to store the adjacency list representation, plus $\mathcal{O}(V)$ for in-degree array / state array and queue/stack.

Day 30: RabbitMQ Dead-Letter Queues & MassTransit

Architectural Overview

In high-throughput microservices architectures, unhandled message processing failures, transient downstream outages, and poison messages (malformed or unprocessable payloads) pose catastrophic risks to system availability. Without robust dead-lettering and progressive retry policies, failed messages either trigger infinite retry storms that starve healthy messages (Head-of-Line blocking) or are dropped silently resulting in data loss.

This module provides a production-grade implementation of AMQP Dead-Letter Exchanges (DLX), TTL-based Exponential Delayed Retry Queues, and MassTransit Saga State Machine Orchestration in .NET 8.

Key Architectural Concepts

1. AMQP Dead-Letter Exchange (DLX) Mechanics

A queue declares dead-letter routing via standard AMQP 0-9-1 arguments:

  • x-dead-letter-exchange: The exchange that receives dead-lettered messages.
  • x-dead-letter-routing-key: Optional replacement routing key for dead-lettered routing.
  • x-message-ttl: Per-message or per-queue time-to-live in milliseconds.
  • x-max-length: Maximum message capacity; overflowing messages are diverted to DLX instead of dropped.

A message is dead-lettered under three specific conditions:

  1. Explicit Rejection: Consumer issues basic.reject or basic.nack with requeue = false.
  2. TTL Expiration: Message resides in a queue past its x-message-ttl expiration without being consumed.
  3. Queue Max-Length Overflow: Queue exceeds its declared capacity limit.

2. Progressive Delayed Retry Topology (Zero-Consumer DLX Loop)

Instead of blocking worker threads with Task.Delay() inside consumers:

  1. On failure (attempt $N < \text{Max}$), the consumer rejects the message into a delayed queue (orders.retry.5s).
  2. The delay queue has NO consumers attached and is configured with x-message-ttl: 5000 and x-dead-letter-exchange: dlx.direct, x-dead-letter-routing-key: orders.work.
  3. When the TTL expires, the broker automatically re-routes the message back into the active processing queue (orders.work).
  4. If failures persist beyond threshold ($N \ge \text{Max}$), the message routes directly to the poison DLQ (orders.dlq) with full x-death diagnosis headers.
[Publisher] ---> [orders.work] ---> [Consumer] (Fails attempt 1)
                     ^                    |
                     | (TTL expires)      v (Reject to DLX)
              [orders.retry.5s] <--- [dlx.direct]
                     (No consumers)
                                          | (Fails attempt 3)
                                          v
                                    [orders.dlq] (Poison Triage)

3. MassTransit State Machine Saga Coordination

Distributed transactions spanning multiple bounded contexts (Order, Inventory, Payment) require compensating choreographies or orchestrations. MassTransitStateMachine<TInstance> correlates events by CorrelationId and provides:

  • State transitions: Initial $\to$ Submitted $\to$ InventoryReserved $\to$ Completed.
  • Fault handling: Any unexpected fault routes to Faulted state triggering compensating commands.

Data Structures & Algorithms: Topological Sorting

LeetCode #207: Course Schedule (Medium)

  • Problem: Given numCourses and directed prerequisite pairs [a, b] ($b \to a$), determine if it is possible to finish all courses.
  • Kahn's Algorithm (BFS):
  • Calculate in-degrees for all $V$ courses.
  • Enqueue all courses with in-degree 0.
  • Dequeue node $u$, decrement neighbors' in-degrees, enqueue when in-degree hits 0.
  • If processed count equals $numCourses$, graph is a DAG (no cycles).
  • Complexity: $\mathcal{O}(V + E)$ time, $\mathcal{O}(V + E)$ space.

LeetCode #210: Course Schedule II (Medium)

  • Problem: Return the ordering of courses you should take to finish all courses. If impossible due to cycles, return empty array.
  • Algorithm: Kahn's BFS records each dequeued node into the output array. If output size is $numCourses$, the valid topological order is returned; otherwise, an empty array is returned.

10 Senior / Staff-Level Interview Questions with In-Depth Answers:
Q1 What is the exact mechanical difference between `basic.reject(requeue: true)` and `basic.reject(requeue: false)` with an AMQP Dead-Letter Exchange configured?
▼

Answer:

  • When a consumer calls basic.reject(deliveryTag, requeue: true), RabbitMQ immediately re-inserts the unacknowledged message back into the head of the same queue (or its original position). If the consumer failure was caused by a persistent software bug or malformed payload, this triggers an infinite immediate retry loop (retry storm) that consumes 100% CPU and completely blocks all subsequent messages from processing (Head-of-Line blocking).
  • When a consumer calls basic.reject(deliveryTag, requeue: false), RabbitMQ checks if the queue has an x-dead-letter-exchange argument declared. If yes, the broker intercepts the message, injects an entry into its x-death diagnostic header, modifies its exchange/routing key as configured, and publishes it to the dead-letter exchange. If no DLX is configured, the message is permanently destroyed and discarded. In production, unhandled exceptions must always reject with requeue: false towards a configured DLX.
Q2 Explain Head-of-Line blocking in RabbitMQ when using per-message TTL for delayed retries. How do you prevent it?
▼

Answer:

RabbitMQ evaluates message expiration only when a message reaches the head of the queue. If a worker queue publishes message A with a 60-second TTL (expiration: "60000") followed immediately by message B with a 5-second TTL (expiration: "5000"), message B will NOT dead-letter after 5 seconds. It is physically blocked behind message A. Only when message A's 60 seconds expire will message A dead-letter, at which point the broker inspects message B and discovers it has already expired.

To prevent this:

  1. Discrete Queue-Level TTL: Do NOT use per-message TTL on a shared queue. Declare distinct queues with fixed queue-level x-message-ttl arguments (retry.5s, retry.30s, retry.2m). All messages in a given queue share the identical TTL and therefore expire in exact FIFO order.
  2. RabbitMQ Delayed Message Plugin: Use the x-delayed-message exchange plugin, which stores delayed messages in an internal Erlang Mnesia database table and routes them only when their specific timer elapses.
Q3 What is the operational difference between the RabbitMQ Delayed Message Exchange plugin and the DLX/TTL loop pattern?
▼

Answer:

  • DLX/TTL Loop (Native AMQP): Requires zero plugins and runs on standard, unmodified RabbitMQ clusters. Messages sit in regular queues with no consumers. When TTL expires, the broker moves them via DLX. However, it requires predefined discrete delay intervals (e.g. 5s, 30s, 5m), and creating arbitrary per-message delay intervals is impossible without risking Head-of-Line blocking.
  • Delayed Message Plugin (x-delayed-message): Allows arbitrary per-message delay via the x-delay header (in milliseconds). The exchange stores messages in an internal Mnesia database on disk, bypassing queues entirely until expiration. However, because it relies on Mnesia, it does not scale well past ~100,000 delayed messages, does not support Quorum Queues directly at the exchange level, and complicates node replication and cluster upgrades.
Q4 How does MassTransit differentiate between transient exceptions and poison messages? Explain `UseMessageRetry` vs `UseDelayedRedelivery`.
▼

Answer:

  • UseMessageRetry (In-Memory Retry): Catches exceptions inside the consumer's executing scope without acknowledging or rejecting the message on the broker. The thread or task waits using in-memory timers (e.g. exponential backoff: 100ms, 200ms, 500ms). This is ideal for short, transient glitches (e.g., brief database deadlocks or network socket resets). However, holding the message in memory locks the consumer thread/prefetch slot.
  • UseDelayedRedelivery (Broker Delayed Retry): When in-memory retries are exhausted, UseDelayedRedelivery acknowledges or moves the message out of the main queue into a delayed queue (via RabbitMQ delayed-message exchange or quartz/hangfire). This releases the consumer thread and prefetch buffer to process subsequent messages. The message is republished to the consumer queue minutes or hours later.
  • If delayed redelivery also exhausts its maximum attempts, MassTransit routes the poison message to a designated _error queue with serialized exception details in message headers.
Q5 How does MassTransit solve concurrent saga state transitions when two asynchronous events arrive simultaneously for the same `CorrelationId`?
▼

Answer:

In an asynchronous distributed architecture, multiple events (such as InventoryReserved and PaymentCompleted) may arrive concurrently at different consumer instances for the exact same saga instance.

MassTransit solves this via:

  1. Optimistic Concurrency Control: The saga instance table includes a Version or RowVersion integer column. MassTransit issues an atomic update: UPDATE SagaTable SET State = @NewState, Version = Version + 1 WHERE Id = @Id AND Version = @ExpectedVersion. If a concurrent worker updated the version first, the second worker's update affects 0 rows, throwing a DbUpdateConcurrencyException. MassTransit's saga repository middleware catches this concurrency exception and automatically retries loading the fresh saga state and applying the second event.
  2. Pessimistic Locking: Configured via UseRowLock() in EF Core (e.g. SELECT ... FOR UPDATE), which serializes event processing at the database transaction boundary.
Q6 What is the structure of the `x-death` AMQP header in RabbitMQ, and how do you extract the root failure reason?
▼

Answer:

When RabbitMQ dead-letters a message, it adds an x-death array of dictionary objects to the message's AMQP headers. Each element contains:

  • queue: Name of the queue where the message died.
  • reason: String enum: "rejected", "expired", or "maxlen".
  • count: How many times the message died in that specific queue.
  • exchange: The original exchange the message was published to.
  • time: Unix timestamp when the dead-lettering occurred.

If a message travels through multiple retry queues, x-death contains multiple entries. To find the root queue where failure first started, inspect the last element in the array or match the non-retry queue name. To get the total number of retries across a specific queue, read the count property.

Q7 When should you choose Orchestration (Saga State Machine) over Choreography in microservices?
▼

Answer:

  • Choose Choreography when:
  • The workflow is short and simple (2 to 3 bounded contexts).
  • There are no complex branching logic, timeout deadlines, or multi-step compensating actions.
  • Services are loosely coupled and publish generic domain events (OrderPlaced, CustomerBilled).
  • Choose Orchestration (State Machine) when:
  • The business process involves 4+ services, conditional branching, or time-based escalation (e.g., "if payment not received within 15 minutes, cancel order and release inventory").
  • Compensating transactions are required upon failure (rolling back steps 2 and 1 if step 3 fails).
  • Centralized visibility, auditability, and operational tracking of workflow state are mandatory for compliance or customer support.
Q8 How do you safely implement DLQ re-drive (replaying dead-lettered messages back to production) without triggering duplicate processing?
▼

Answer:

  1. Fix Root Cause First: Never re-drive messages while the underlying bug, schema incompatibility, or downstream outage exists.
  2. Consumer Idempotency: All consumers must implement the Idempotent Consumer / Inbox pattern using a unique MessageId or business deduplication key stored in an atomic database table.
  3. Strip Diagnostic Headers: When transferring messages from orders.dlq back to orders.work, strip or reset the x-death and retry count headers so the message starts with a clean retry budget.
  4. Controlled Rate / Shovel: Use RabbitMQ Shovel or a rate-limited re-drive worker rather than a bulk instantaneous dump to prevent overwhelming downstream databases.
Q9 Explain Kahn's algorithm for topological sorting. Why does an unprocessed vertex count prove the existence of a directed cycle?
▼

Answer:

Kahn's algorithm operates on the topological property that in any Directed Acyclic Graph (DAG), there must be at least one vertex with an in-degree of 0 (no dependencies).

  1. Compute the in-degree of all vertices.
  2. Enqueue all vertices with inDegree == 0.
  3. Repeatedly dequeue a vertex $u$, add it to the topological order, and decrement the in-degree of all its outbound neighbors $(u, v)$.
  4. Whenever a neighbor's in-degree drops to 0, enqueue it.
  5. Cycle Proof: If the graph contains a directed cycle (e.g. $A \to B \to C \to A$), every node in that cycle has an in-degree $\ge 1$ from within the cycle. Therefore, none of the vertices in the cycle can ever reach an in-degree of 0, and none will ever be enqueued. If the total count of processed vertices is less than the total vertices $|V|$, the graph strictly contains at least one directed cycle.
Q10 How do you handle a partial failure during a Saga compensation (e.g. inventory rollback succeeds, but payment refund API fails)?
▼

Answer:

This is the fundamental reality of distributed systems: compensating actions can themselves fail.

  1. Exponential Retry with DLQ: The compensation command (RefundPayment) is published through the same reliable messaging pipeline with exponential backoff and a dedicated dead-letter queue.
  2. Idempotent Compensations: Compensation endpoints must be idempotent. If the compensation retry executes three times, the customer must only be refunded once.
  3. Escalation to Human Workflow (Manual Triage): If automated compensation fails after reaching maximum retries, the saga instance enters a NeedsManualIntervention state, publishes a critical P1 telemetry alert to Ops, and logs the saga CorrelationId and transaction IDs to an administrative console for human reconciliation. Distributed systems cannot guarantee 100% automated recovery for non-idempotent external third-party failures; automated retries combined with human escalation queues ensure no funds or data are silently lost.

namespace Day30.RabbitMQDLQMassTransit;

public static class CourseScheduleSolver
{
    /// <summary>
    /// LeetCode #207: Course Schedule (Medium) using Kahn's Algorithm (BFS in-degree topological sort).
    /// Time Complexity: O(V + E), Space Complexity: O(V + E)
    /// </summary>
    public static bool CanFinishKahn(int numCourses, int[][] prerequisites)
    {
        if (numCourses <= 0) return true;

        var adj = new List<int>[numCourses];
        var inDegree = new int[numCourses];
        for (int i = 0; i < numCourses; i++)
        {
            adj[i] = new List<int>();
        }

        foreach (var pair in prerequisites)
        {
            int course = pair[0];
            int prereq = pair[1];
            adj[prereq].Add(course);
            inDegree[course]++;
        }

        var queue = new Queue<int>();
        for (int i = 0; i < numCourses; i++)
        {
            if (inDegree[i] == 0)
            {
                queue.Enqueue(i);
            }
        }

        int visitedCount = 0;
        while (queue.Count > 0)
        {
            int u = queue.Dequeue();
            visitedCount++;

            foreach (int v in adj[u])
            {
                inDegree[v]--;
                if (inDegree[v] == 0)
                {
                    queue.Enqueue(v);
                }
            }
        }

        return visitedCount == numCourses;
    }

    /// <summary>
    /// LeetCode #207: Course Schedule (Medium) using 3-Coloring DFS Cycle Detection.
    /// 0 = Unvisited, 1 = Visiting (in recursion stack), 2 = Visited.
    /// Time Complexity: O(V + E), Space Complexity: O(V + E)
    /// </summary>
    public static bool CanFinishDfs(int numCourses, int[][] prerequisites)
    {
        if (numCourses <= 0) return true;

        var adj = new List<int>[numCourses];
        for (int i = 0; i < numCourses; i++)
        {
            adj[i] = new List<int>();
        }

        foreach (var pair in prerequisites)
        {
            int course = pair[0];
            int prereq = pair[1];
            adj[prereq].Add(course);
        }

        var state = new int[numCourses]; // 0=White, 1=Gray, 2=Black

        for (int i = 0; i < numCourses; i++)
        {
            if (state[i] == 0)
            {
                if (HasCycleDfs(i, adj, state))
                {
                    return false;
                }
            }
        }

        return true;
    }

    private static bool HasCycleDfs(int u, List<int>[] adj, int[] state)
    {
        state[u] = 1; // Mark as visiting

        foreach (int v in adj[u])
        {
            if (state[v] == 1) return true; // Directed back-edge -> Cycle!
            if (state[v] == 0 && HasCycleDfs(v, adj, state)) return true;
        }

        state[u] = 2; // Mark as visited
        return false;
    }

    /// <summary>
    /// LeetCode #210: Course Schedule II (Medium) using Kahn's Algorithm.
    /// Returns valid topological order, or empty array if cycle detected.
    /// Time Complexity: O(V + E), Space Complexity: O(V + E)
    /// </summary>
    public static int[] FindOrderKahn(int numCourses, int[][] prerequisites)
    {
        if (numCourses <= 0) return Array.Empty<int>();

        var adj = new List<int>[numCourses];
        var inDegree = new int[numCourses];
        for (int i = 0; i < numCourses; i++)
        {
            adj[i] = new List<int>();
        }

        foreach (var pair in prerequisites)
        {
            int course = pair[0];
            int prereq = pair[1];
            adj[prereq].Add(course);
            inDegree[course]++;
        }

        var queue = new Queue<int>();
        for (int i = 0; i < numCourses; i++)
        {
            if (inDegree[i] == 0)
            {
                queue.Enqueue(i);
            }
        }

        var order = new int[numCourses];
        int index = 0;

        while (queue.Count > 0)
        {
            int u = queue.Dequeue();
            order[index++] = u;

            foreach (int v in adj[u])
            {
                inDegree[v]--;
                if (inDegree[v] == 0)
                {
                    queue.Enqueue(v);
                }
            }
        }

        return index == numCourses ? order : Array.Empty<int>();
    }

    /// <summary>
    /// LeetCode #210: Course Schedule II (Medium) using DFS Post-order reversal.
    /// Time Complexity: O(V + E), Space Complexity: O(V + E)
    /// </summary>
    public static int[] FindOrderDfs(int numCourses, int[][] prerequisites)
    {
        if (numCourses <= 0) return Array.Empty<int>();

        var adj = new List<int>[numCourses];
        for (int i = 0; i < numCourses; i++)
        {
            adj[i] = new List<int>();
        }

        foreach (var pair in prerequisites)
        {
            int course = pair[0];
            int prereq = pair[1];
            adj[prereq].Add(course);
        }

        var state = new int[numCourses];
        var orderStack = new Stack<int>();

        for (int i = 0; i < numCourses; i++)
        {
            if (state[i] == 0)
            {
                if (DfsTopological(i, adj, state, orderStack))
                {
                    return Array.Empty<int>(); // Cycle detected
                }
            }
        }

        var result = new int[numCourses];
        int index = 0;
        while (orderStack.Count > 0)
        {
            result[index++] = orderStack.Pop();
        }

        return result;
    }

    private static bool DfsTopological(int u, List<int>[] adj, int[] state, Stack<int> orderStack)
    {
        state[u] = 1;

        foreach (int v in adj[u])
        {
            if (state[v] == 1) return true; // Cycle!
            if (state[v] == 0 && DfsTopological(v, adj, state, orderStack)) return true;
        }

        state[u] = 2;
        orderStack.Push(u);
        return false;
    }
}

public class DlqRetrySimulator
{
    private readonly ConcurrentDictionary<string, QueueArguments> _queueConfigs = new();
    private readonly ConcurrentDictionary<string, List<AmqpMessage>> _queues = new();
    private readonly ConcurrentDictionary<string, Action<AmqpMessage>> _consumers = new();

    public void DeclareQueue(string queueName, QueueArguments? arguments = null)
    {

    public void RegisterConsumer(string queueName, Action<AmqpMessage> consumer)
    {
        _consumers[queueName] = consumer;
    }

    public void Publish(string queueName, AmqpMessage message)
    {
        lock (_lock)
        {
            if (!_queues.ContainsKey(queueName))
            {
                DeclareQueue(queueName);
            }

            var queue = _queues[queueName];
            var config = _queueConfigs.GetValueOrDefault(queueName, new QueueArguments());

            // Check MaxLength dead-lettering
            if (config.MaxLength.HasValue && queue.Count >= config.MaxLength.Value)
            {
                if (!string.IsNullOrEmpty(config.DeadLetterExchange))
                {
                    var targetQueue = config.DeadLetterRoutingKey ?? config.DeadLetterExchange;
                    DeadLetter(message, queueName, targetQueue, DeadLetterReason.MaxLengthExceeded, "Queue reached max-length capacity");
                    return;
                }
            }

            queue.Add(message);
        }
    }

    public void Reject(string currentQueue, AmqpMessage message, Exception reason, bool requeue = false)
    {
        lock (_lock)
        {
            if (_queues.TryGetValue(currentQueue, out var list))
            {
                list.Remove(message);
            }

            if (requeue)
            {
                Publish(currentQueue, message);
                return;
            }

            var config = _queueConfigs.GetValueOrDefault(currentQueue, new QueueArguments());
            if (string.IsNullOrEmpty(config.DeadLetterExchange))
            {
                throw new InvalidOperationException($"Queue '{currentQueue}' has no dead-letter exchange configured.");
            }

            var nextRetry = message.RetryCount + 1;
            var targetQueue = config.DeadLetterRoutingKey ?? config.DeadLetterExchange;

            var updatedMessage = message with
            {
                RetryCount = nextRetry
            };

            DeadLetter(updatedMessage, currentQueue, targetQueue, DeadLetterReason.Rejected, reason.Message, reason.GetType().Name);
        }
    }

    public void ExpireTtl(string delayQueueName, string messageId)
    {
        lock (_lock)
        {
            if (!_queues.TryGetValue(delayQueueName, out var list)) return;
            var msg = list.FirstOrDefault(m => m.MessageId == messageId);
            if (msg == null) return;

            list.Remove(msg);
            var config = _queueConfigs.GetValueOrDefault(delayQueueName, new QueueArguments());
            if (!string.IsNullOrEmpty(config.DeadLetterExchange))
            {
                var targetQueue = config.DeadLetterRoutingKey ?? config.DeadLetterExchange;
                DeadLetter(msg, delayQueueName, targetQueue, DeadLetterReason.Expired, "Message TTL expired in delayed retry queue");
            }
        }
    }

    private void DeadLetter(
        AmqpMessage message,
        string sourceQueue,
        string targetQueue,
        DeadLetterReason reason,
        string? details = null,
        string? exceptionType = null)
    {
        var deathEntry = new XDeathEntry(
            Queue: sourceQueue,
            Reason: reason,
            Count: message.RetryCount,
            Exchange: "dlx.direct",
            Timestamp: DateTime.UtcNow,
            ExceptionMessage: details,
            ExceptionType: exceptionType
        );

        var updatedHistory = new List<XDeathEntry>(message.DeathHistory) { deathEntry };
        var deadLetteredMsg = message with { DeathHistory = updatedHistory };

        Publish(targetQueue, deadLetteredMsg);
    }

    public IReadOnlyList<AmqpMessage> GetQueueMessages(string queueName)
    {
        lock (_lock)
        {
            return _queues.TryGetValue(queueName, out var list) ? list.ToList() : Array.Empty<AmqpMessage>();
        }
    }

    public void DispatchNext(string queueName)
    {
        AmqpMessage? msg = null;
        Action<AmqpMessage>? consumer = null;

        lock (_lock)
        {
            if (_queues.TryGetValue(queueName, out var list) && list.Count > 0)
            {
                msg = list[0];
            }
            _consumers.TryGetValue(queueName, out consumer);
        }

        if (msg != null && consumer != null)
        {
            consumer(msg);
        }
    }
}

📝 Part 1: Deep-Dive Architectural & Engineering Notes

Day 30 Deep Dive Notes: RabbitMQ DLQ, TTL Retry Topology & MassTransit Sagas

1. AMQP Dead-Letter Protocol & Wire Semantics

The AMQP Dead-Letter Specification

Under the AMQP 0-9-1 specification, a message entering an AMQP queue can be transitioned to dead-letter status under three exact conditions:

  1. Explicit Negative Acknowledgment:
  • basic.reject(deliveryTag, requeue = false)
  • basic.nack(deliveryTag, multiple = false, requeue = false)

When requeue = true, the broker places the message back into its original position in the queue. When requeue = false, if x-dead-letter-exchange is declared, the message is immediately routed to that exchange; otherwise, it is silently dropped into the ether.

  1. Time-To-Live (TTL) Expiration:
  • Queue-level TTL (x-message-ttl): Automatically configured on queue declaration.
  • Message-level TTL (expiration header): Declared per publication.
  1. Queue Length Overflow:
  • x-max-length: Maximum count of ready messages.
  • x-max-length-bytes: Maximum total payload size in bytes.
  • x-overflow: Determines behavior when full (drop-head, reject-publish, or reject-publish-dlx).

The x-death Header Architecture

When RabbitMQ dead-letters a message, it modifies the message headers by prepending a hash to the x-death array:

{
  "x-death": [
    {
      "count": 1,
      "exchange": "orders.direct",
      "queue": "orders.work",
      "reason": "rejected",
      "routing-keys": ["orders.work"],
      "time": 1729000000
    }
  ]
}

Critical Production Gotcha: If a message transitions through multiple dead-letter hops (e.g. work $\to$ retry.5s $\to$ work $\to$ retry.30s $\to$ dlq), RabbitMQ updates the count for existing queue entries or inserts a new element at index 0. To calculate total historical retries across multiple queues, your inspection tool must sum the count fields across all elements matching the root processing queue.

2. RabbitMQ TTL Retry Pitfalls: Head-of-Line Blocking

Why Variable Per-Message TTL Causes Head-of-Line Blocking

A common architectural mistake is using a single retry queue with variable per-message expiration headers:

// ANTI-PATTERN:
await channel.BasicPublishAsync(exchange: "", routingKey: "orders.retry", mandatory: true, basicProperties: new BasicProperties { Expiration = "30000" }, body: body1);
await channel.BasicPublishAsync(exchange: "", routingKey: "orders.retry", mandatory: true, basicProperties: new BasicProperties { Expiration = "5000" }, body: body2);

Why this fails: In standard RabbitMQ classic and quorum queues, messages are evaluated for expiration only when they reach the head of the queue. If message 1 has a 30-second TTL and message 2 has a 5-second TTL, message 2 will NOT expire and dead-letter after 5 seconds! It remains trapped behind message 1 for the full 30 seconds.

The Correct Production Solution: Multi-Stage Discrete Delay Queues

Create discrete queues with fixed queue-level x-message-ttl:

  • orders.retry.5s: x-message-ttl = 5000, DLX $\to$ orders.work
  • orders.retry.30s: x-message-ttl = 30000, DLX $\to$ orders.work
  • orders.retry.2m: x-message-ttl = 120000, DLX $\to$ orders.work
  • orders.dlq: Final poison holding queue (retained for manual inspection and replay).

Because all messages in a given queue have identical TTL, messages always expire in strict FIFO order, preventing Head-of-Line blocking entirely.

3. MassTransit Architecture & Saga State Machines

The MassTransit Pipeline Engine

MassTransit builds an asynchronous message pipeline inspired by the Russian Doll middleware pattern (GreenPipes):

Transport (RabbitMQ) 
  ---> DeserializationFilter 
    ---> ScopedFilter (DI Scope per message) 
      ---> RetryFilter (In-memory backoff) 
        ---> RedeliveryFilter (Delayed exchange) 
          ---> OutboxFilter (Transactional Outbox) 
            ---> Consumer / Saga State Machine

Saga Orchestration vs Choreography

  • Choreography: Each service listens to domain events and decides its own local action without centralized coordination. Works well for simple 2-3 step workflows, but becomes impossible to debug and trace in complex flows.
  • Orchestration (MassTransit Saga State Machine): A centralized state coordinator (OrderStateMachine) listens to events, tracks global state in a persistent instance table, and dispatches direct commands (ReserveInventory, AuthorizePayment).

Concurrency & Locking in Sagas

When concurrent events arrive for the same saga instance (e.g. PaymentCompleted and InventoryUnavailable dispatched simultaneously):

  1. Optimistic Concurrency: MassTransit tracks a RowVersion or Version property. If two threads attempt to commit state transitions simultaneously, one commits and the second throws DbUpdateConcurrencyException. MassTransit's retry middleware automatically catches the concurrency exception and re-reads the updated saga state.
  2. Pessimistic Concurrency: Acquires a database row lock (SELECT ... FOR UPDATE) before executing saga activity.

4. DSA Deep Dive: Topological Sorting

Directed Acyclic Graph (DAG) Foundations

A Topological Sort of a directed graph $G = (V, E)$ is a linear ordering of its vertices such that for every directed edge $(u, v)$, node $u$ comes before $v$ in the ordering.

A graph admits a topological sort if and only if it is a Directed Acyclic Graph (DAG).

Kahn's Algorithm vs DFS 3-Coloring

Characteristic Kahn's Algorithm (BFS) 3-Coloring (DFS)
Underlying Mechanism In-degree queue Post-order reversal via recursion stack
Cycle Detection Count of dequeued nodes $< \ V\ $ Directed back-edge to a node currently in state 1 (Visiting)
Memory Footprint In-degree array + FIFO queue Recursion stack ($\mathcal{O}(H)$ call stack)
Output Order Forward direct topological order Reverse post-order (must reverse or stack pop)
Cycle Path Extraction Harder to extract cycle loop Trivial to extract cycle path by tracing gray nodes

Complexity Analysis

  • Time Complexity: $\mathcal{O}(V + E)$ where $V$ is numCourses and $E$ is the number of prerequisites. Every vertex is enqueued/visited once, and every directed edge is decremented/traversed exactly once.
  • Space Complexity: $\mathcal{O}(V + E)$ to store the adjacency list representation, plus $\mathcal{O}(V)$ for in-degree array / state array and queue/stack.

📑 Part 2: Module Overview & Practical Walkthrough

Day 30: RabbitMQ Dead-Letter Queues & MassTransit

Architectural Overview

In high-throughput microservices architectures, unhandled message processing failures, transient downstream outages, and poison messages (malformed or unprocessable payloads) pose catastrophic risks to system availability. Without robust dead-lettering and progressive retry policies, failed messages either trigger infinite retry storms that starve healthy messages (Head-of-Line blocking) or are dropped silently resulting in data loss.

This module provides a production-grade implementation of AMQP Dead-Letter Exchanges (DLX), TTL-based Exponential Delayed Retry Queues, and MassTransit Saga State Machine Orchestration in .NET 8.

Key Architectural Concepts

1. AMQP Dead-Letter Exchange (DLX) Mechanics

A queue declares dead-letter routing via standard AMQP 0-9-1 arguments:

  • x-dead-letter-exchange: The exchange that receives dead-lettered messages.
  • x-dead-letter-routing-key: Optional replacement routing key for dead-lettered routing.
  • x-message-ttl: Per-message or per-queue time-to-live in milliseconds.
  • x-max-length: Maximum message capacity; overflowing messages are diverted to DLX instead of dropped.

A message is dead-lettered under three specific conditions:

  1. Explicit Rejection: Consumer issues basic.reject or basic.nack with requeue = false.
  2. TTL Expiration: Message resides in a queue past its x-message-ttl expiration without being consumed.
  3. Queue Max-Length Overflow: Queue exceeds its declared capacity limit.

2. Progressive Delayed Retry Topology (Zero-Consumer DLX Loop)

Instead of blocking worker threads with Task.Delay() inside consumers:

  1. On failure (attempt $N < \text{Max}$), the consumer rejects the message into a delayed queue (orders.retry.5s).
  2. The delay queue has NO consumers attached and is configured with x-message-ttl: 5000 and x-dead-letter-exchange: dlx.direct, x-dead-letter-routing-key: orders.work.
  3. When the TTL expires, the broker automatically re-routes the message back into the active processing queue (orders.work).
  4. If failures persist beyond threshold ($N \ge \text{Max}$), the message routes directly to the poison DLQ (orders.dlq) with full x-death diagnosis headers.
[Publisher] ---> [orders.work] ---> [Consumer] (Fails attempt 1)
                     ^                    |
                     | (TTL expires)      v (Reject to DLX)
              [orders.retry.5s] <--- [dlx.direct]
                     (No consumers)
                                          | (Fails attempt 3)
                                          v
                                    [orders.dlq] (Poison Triage)

3. MassTransit State Machine Saga Coordination

Distributed transactions spanning multiple bounded contexts (Order, Inventory, Payment) require compensating choreographies or orchestrations. MassTransitStateMachine<TInstance> correlates events by CorrelationId and provides:

Q1 What is the exact mechanical difference between `basic.reject(requeue: true)` and `basic.reject(requeue: false)` with an AMQP Dead-Letter Exchange configured?
▼

Answer:

  • When a consumer calls basic.reject(deliveryTag, requeue: true), RabbitMQ immediately re-inserts the unacknowledged message back into the head of the same queue (or its original position). If the consumer failure was caused by a persistent software bug or malformed payload, this triggers an infinite immediate retry loop (retry storm) that consumes 100% CPU and completely blocks all subsequent messages from processing (Head-of-Line blocking).
  • When a consumer calls basic.reject(deliveryTag, requeue: false), RabbitMQ checks if the queue has an x-dead-letter-exchange argument declared. If yes, the broker intercepts the message, injects an entry into its x-death diagnostic header, modifies its exchange/routing key as configured, and publishes it to the dead-letter exchange. If no DLX is configured, the message is permanently destroyed and discarded. In production, unhandled exceptions must always reject with requeue: false towards a configured DLX.
Q2 Explain Head-of-Line blocking in RabbitMQ when using per-message TTL for delayed retries. How do you prevent it?
▼

Answer:

RabbitMQ evaluates message expiration only when a message reaches the head of the queue. If a worker queue publishes message A with a 60-second TTL (expiration: "60000") followed immediately by message B with a 5-second TTL (expiration: "5000"), message B will NOT dead-letter after 5 seconds. It is physically blocked behind message A. Only when message A's 60 seconds expire will message A dead-letter, at which point the broker inspects message B and discovers it has already expired.

To prevent this:

  1. Discrete Queue-Level TTL: Do NOT use per-message TTL on a shared queue. Declare distinct queues with fixed queue-level x-message-ttl arguments (retry.5s, retry.30s, retry.2m). All messages in a given queue share the identical TTL and therefore expire in exact FIFO order.
  2. RabbitMQ Delayed Message Plugin: Use the x-delayed-message exchange plugin, which stores delayed messages in an internal Erlang Mnesia database table and routes them only when their specific timer elapses.
Q3 What is the operational difference between the RabbitMQ Delayed Message Exchange plugin and the DLX/TTL loop pattern?
▼

Answer:

  • DLX/TTL Loop (Native AMQP): Requires zero plugins and runs on standard, unmodified RabbitMQ clusters. Messages sit in regular queues with no consumers. When TTL expires, the broker moves them via DLX. However, it requires predefined discrete delay intervals (e.g. 5s, 30s, 5m), and creating arbitrary per-message delay intervals is impossible without risking Head-of-Line blocking.
  • Delayed Message Plugin (x-delayed-message): Allows arbitrary per-message delay via the x-delay header (in milliseconds). The exchange stores messages in an internal Mnesia database on disk, bypassing queues entirely until expiration. However, because it relies on Mnesia, it does not scale well past ~100,000 delayed messages, does not support Quorum Queues directly at the exchange level, and complicates node replication and cluster upgrades.
Q4 How does MassTransit differentiate between transient exceptions and poison messages? Explain `UseMessageRetry` vs `UseDelayedRedelivery`.
▼

Answer:

  • UseMessageRetry (In-Memory Retry): Catches exceptions inside the consumer's executing scope without acknowledging or rejecting the message on the broker. The thread or task waits using in-memory timers (e.g. exponential backoff: 100ms, 200ms, 500ms). This is ideal for short, transient glitches (e.g., brief database deadlocks or network socket resets). However, holding the message in memory locks the consumer thread/prefetch slot.
  • UseDelayedRedelivery (Broker Delayed Retry): When in-memory retries are exhausted, UseDelayedRedelivery acknowledges or moves the message out of the main queue into a delayed queue (via RabbitMQ delayed-message exchange or quartz/hangfire). This releases the consumer thread and prefetch buffer to process subsequent messages. The message is republished to the consumer queue minutes or hours later.
  • If delayed redelivery also exhausts its maximum attempts, MassTransit routes the poison message to a designated _error queue with serialized exception details in message headers.
Q5 How does MassTransit solve concurrent saga state transitions when two asynchronous events arrive simultaneously for the same `CorrelationId`?
▼

Answer:

In an asynchronous distributed architecture, multiple events (such as InventoryReserved and PaymentCompleted) may arrive concurrently at different consumer instances for the exact same saga instance.

MassTransit solves this via:

  1. Optimistic Concurrency Control: The saga instance table includes a Version or RowVersion integer column. MassTransit issues an atomic update: UPDATE SagaTable SET State = @NewState, Version = Version + 1 WHERE Id = @Id AND Version = @ExpectedVersion. If a concurrent worker updated the version first, the second worker's update affects 0 rows, throwing a DbUpdateConcurrencyException. MassTransit's saga repository middleware catches this concurrency exception and automatically retries loading the fresh saga state and applying the second event.
  2. Pessimistic Locking: Configured via UseRowLock() in EF Core (e.g. SELECT ... FOR UPDATE), which serializes event processing at the database transaction boundary.
Q6 What is the structure of the `x-death` AMQP header in RabbitMQ, and how do you extract the root failure reason?
▼

Answer:

When RabbitMQ dead-letters a message, it adds an x-death array of dictionary objects to the message's AMQP headers. Each element contains:

  • queue: Name of the queue where the message died.
  • reason: String enum: "rejected", "expired", or "maxlen".
  • count: How many times the message died in that specific queue.
  • exchange: The original exchange the message was published to.
  • time: Unix timestamp when the dead-lettering occurred.

If a message travels through multiple retry queues, x-death contains multiple entries. To find the root queue where failure first started, inspect the last element in the array or match the non-retry queue name. To get the total number of retries across a specific queue, read the count property.

Q7 When should you choose Orchestration (Saga State Machine) over Choreography in microservices?
▼

Answer:

  • Choose Choreography when:
  • The workflow is short and simple (2 to 3 bounded contexts).
  • There are no complex branching logic, timeout deadlines, or multi-step compensating actions.
  • Services are loosely coupled and publish generic domain events (OrderPlaced, CustomerBilled).
  • Choose Orchestration (State Machine) when:
  • The business process involves 4+ services, conditional branching, or time-based escalation (e.g., "if payment not received within 15 minutes, cancel order and release inventory").
  • Compensating transactions are required upon failure (rolling back steps 2 and 1 if step 3 fails).
  • Centralized visibility, auditability, and operational tracking of workflow state are mandatory for compliance or customer support.
Q8 How do you safely implement DLQ re-drive (replaying dead-lettered messages back to production) without triggering duplicate processing?
▼

Answer:

  1. Fix Root Cause First: Never re-drive messages while the underlying bug, schema incompatibility, or downstream outage exists.
  2. Consumer Idempotency: All consumers must implement the Idempotent Consumer / Inbox pattern using a unique MessageId or business deduplication key stored in an atomic database table.
  3. Strip Diagnostic Headers: When transferring messages from orders.dlq back to orders.work, strip or reset the x-death and retry count headers so the message starts with a clean retry budget.
  4. Controlled Rate / Shovel: Use RabbitMQ Shovel or a rate-limited re-drive worker rather than a bulk instantaneous dump to prevent overwhelming downstream databases.
Q9 Explain Kahn's algorithm for topological sorting. Why does an unprocessed vertex count prove the existence of a directed cycle?
▼

Answer:

Kahn's algorithm operates on the topological property that in any Directed Acyclic Graph (DAG), there must be at least one vertex with an in-degree of 0 (no dependencies).

  1. Compute the in-degree of all vertices.
  2. Enqueue all vertices with inDegree == 0.
  3. Repeatedly dequeue a vertex $u$, add it to the topological order, and decrement the in-degree of all its outbound neighbors $(u, v)$.
  4. Whenever a neighbor's in-degree drops to 0, enqueue it.
  5. Cycle Proof: If the graph contains a directed cycle (e.g. $A \to B \to C \to A$), every node in that cycle has an in-degree $\ge 1$ from within the cycle. Therefore, none of the vertices in the cycle can ever reach an in-degree of 0, and none will ever be enqueued. If the total count of processed vertices is less than the total vertices $|V|$, the graph strictly contains at least one directed cycle.
Q10 How do you handle a partial failure during a Saga compensation (e.g. inventory rollback succeeds, but payment refund API fails)?
▼

Answer:

This is the fundamental reality of distributed systems: compensating actions can themselves fail.

  1. Exponential Retry with DLQ: The compensation command (RefundPayment) is published through the same reliable messaging pipeline with exponential backoff and a dedicated dead-letter queue.
  2. Idempotent Compensations: Compensation endpoints must be idempotent. If the compensation retry executes three times, the customer must only be refunded once.
  3. Escalation to Human Workflow (Manual Triage): If automated compensation fails after reaching maximum retries, the saga instance enters a NeedsManualIntervention state, publishes a critical P1 telemetry alert to Ops, and logs the saga CorrelationId and transaction IDs to an administrative console for human reconciliation. Distributed systems cannot guarantee 100% automated recovery for non-idempotent external third-party failures; automated retries combined with human escalation queues ensure no funds or data are silently lost.

public static class CourseScheduleSolver
{
    /// <summary>
    /// LeetCode #207: Course Schedule (Medium) using Kahn's Algorithm (BFS in-degree topological sort).
    /// Time Complexity: O(V + E), Space Complexity: O(V + E)
    /// </summary>
    public static bool CanFinishKahn(int numCourses, int[][] prerequisites)
    {
        if (numCourses <= 0) return true;

        var adj = new List<int>[numCourses];
        var inDegree = new int[numCourses];
        for (int i = 0; i < numCourses; i++)
        {
            adj[i] = new List<int>();
        }

        foreach (var pair in prerequisites)
        {
            int course = pair[0];
            int prereq = pair[1];
            adj[prereq].Add(course);
            inDegree[course]++;
        }

        var queue = new Queue<int>();
        for (int i = 0; i < numCourses; i++)
        {
            if (inDegree[i] == 0)
            {
                queue.Enqueue(i);
            }
        }

        int visitedCount = 0;
        while (queue.Count > 0)
        {
            int u = queue.Dequeue();
            visitedCount++;

            foreach (int v in adj[u])
            {
                inDegree[v]--;
                if (inDegree[v] == 0)
                {
                    queue.Enqueue(v);
                }
            }
        }

        return visitedCount == numCourses;
    }

    /// <summary>
    /// LeetCode #207: Course Schedule (Medium) using 3-Coloring DFS Cycle Detection.
    /// 0 = Unvisited, 1 = Visiting (in recursion stack), 2 = Visited.
    /// Time Complexity: O(V + E), Space Complexity: O(V + E)
    /// </summary>
    public static bool CanFinishDfs(int numCourses, int[][] prerequisites)
    {
        if (numCourses <= 0) return true;

        var adj = new List<int>[numCourses];
        for (int i = 0; i < numCourses; i++)
        {
            adj[i] = new List<int>();
        }

        foreach (var pair in prerequisites)
        {
            int course = pair[0];
            int prereq = pair[1];
            adj[prereq].Add(course);
        }

        var state = new int[numCourses]; // 0=White, 1=Gray, 2=Black

        for (int i = 0; i < numCourses; i++)
        {
            if (state[i] == 0)
            {
                if (HasCycleDfs(i, adj, state))
                {
                    return false;
                }
            }
        }

        return true;
    }

    private static bool HasCycleDfs(int u, List<int>[] adj, int[] state)
    {
        state[u] = 1; // Mark as visiting

        foreach (int v in adj[u])
        {
            if (state[v] == 1) return true; // Directed back-edge -> Cycle!
            if (state[v] == 0 && HasCycleDfs(v, adj, state)) return true;
        }

        state[u] = 2; // Mark as visited
        return false;
    }

    /// <summary>
    /// LeetCode #210: Course Schedule II (Medium) using Kahn's Algorithm.
    /// Returns valid topological order, or empty array if cycle detected.
    /// Time Complexity: O(V + E), Space Complexity: O(V + E)
    /// </summary>
    public static int[] FindOrderKahn(int numCourses, int[][] prerequisites)
    {
        if (numCourses <= 0) return Array.Empty<int>();

        var adj = new List<int>[numCourses];
        var inDegree = new int[numCourses];
        for (int i = 0; i < numCourses; i++)
        {
            adj[i] = new List<int>();
        }

        foreach (var pair in prerequisites)
        {
            int course = pair[0];
            int prereq = pair[1];
            adj[prereq].Add(course);
            inDegree[course]++;
        }

        var queue = new Queue<int>();
        for (int i = 0; i < numCourses; i++)
        {
            if (inDegree[i] == 0)
            {
                queue.Enqueue(i);
            }
        }

        var order = new int[numCourses];
        int index = 0;

        while (queue.Count > 0)
        {
            int u = queue.Dequeue();
            order[index++] = u;

            foreach (int v in adj[u])
            {
                inDegree[v]--;
                if (inDegree[v] == 0)
                {
                    queue.Enqueue(v);
                }
            }
        }

        return index == numCourses ? order : Array.Empty<int>();
    }

    /// <summary>
    /// LeetCode #210: Course Schedule II (Medium) using DFS Post-order reversal.
    /// Time Complexity: O(V + E), Space Complexity: O(V + E)
    /// </summary>
    public static int[] FindOrderDfs(int numCourses, int[][] prerequisites)
    {
        if (numCourses <= 0) return Array.Empty<int>();

        var adj = new List<int>[numCourses];
        for (int i = 0; i < numCourses; i++)
        {
            adj[i] = new List<int>();
        }

        foreach (var pair in prerequisites)
        {
            int course = pair[0];
            int prereq = pair[1];
            adj[prereq].Add(course);
        }

        var state = new int[numCourses];
        var orderStack = new Stack<int>();

        for (int i = 0; i < numCourses; i++)
        {
            if (state[i] == 0)
            {
                if (DfsTopological(i, adj, state, orderStack))
                {
                    return Array.Empty<int>(); // Cycle detected
                }
            }
        }

        var result = new int[numCourses];
        int index = 0;
        while (orderStack.Count > 0)
        {
            result[index++] = orderStack.Pop();
        }

        return result;
    }

    private static bool DfsTopological(int u, List<int>[] adj, int[] state, Stack<int> orderStack)
    {
        state[u] = 1;

        foreach (int v in adj[u])
        {
            if (state[v] == 1) return true; // Cycle!
            if (state[v] == 0 && DfsTopological(v, adj, state, orderStack)) return true;
        }

        state[u] = 2;
        orderStack.Push(u);
        return false;
    }

public class DlqRetrySimulator
{
    private readonly ConcurrentDictionary<string, QueueArguments> _queueConfigs = new();
    private readonly ConcurrentDictionary<string, List<AmqpMessage>> _queues = new();
    private readonly ConcurrentDictionary<string, Action<AmqpMessage>> _consumers = new();
    private readonly object _lock = new();

    public int MaxRetries { get; set; } = 3;

    public void DeclareQueue(string queueName, QueueArguments? arguments = null)
    {
        _queueConfigs[queueName] = arguments ?? new QueueArguments();
        _queues.GetOrAdd(queueName, _ => new List<AmqpMessage>());
    }

    public void RegisterConsumer(string queueName, Action<AmqpMessage> consumer)
    {
        _consumers[queueName] = consumer;
    }

    public void Publish(string queueName, AmqpMessage message)
    {
        lock (_lock)
        {
            if (!_queues.ContainsKey(queueName))
            {
                DeclareQueue(queueName);
            }

            var queue = _queues[queueName];
            var config = _queueConfigs.GetValueOrDefault(queueName, new QueueArguments());

            // Check MaxLength dead-lettering
            if (config.MaxLength.HasValue && queue.Count >= config.MaxLength.Value)
            {
                if (!string.IsNullOrEmpty(config.DeadLetterExchange))
                {
                    var targetQueue = config.DeadLetterRoutingKey ?? config.DeadLetterExchange;
                    DeadLetter(message, queueName, targetQueue, DeadLetterReason.MaxLengthExceeded, "Queue reached max-length capacity");
                    return;
                }
            }

            queue.Add(message);
        }
    }

    public void Reject(string currentQueue, AmqpMessage message, Exception reason, bool requeue = false)
    {
        lock (_lock)
        {
            if (_queues.TryGetValue(currentQueue, out var list))
            {
                list.Remove(message);
            }

            if (requeue)
            {
                Publish(currentQueue, message);
                return;
            }

            var config = _queueConfigs.GetValueOrDefault(currentQueue, new QueueArguments());
            if (string.IsNullOrEmpty(config.DeadLetterExchange))
            {
                throw new InvalidOperationException($"Queue '{currentQueue}' has no dead-letter exchange configured.");
            }

            var nextRetry = message.RetryCount + 1;
            var targetQueue = config.DeadLetterRoutingKey ?? config.DeadLetterExchange;

            var updatedMessage = message with
            {
                RetryCount = nextRetry
            };

            DeadLetter(updatedMessage, currentQueue, targetQueue, DeadLetterReason.Rejected, reason.Message, reason.GetType().Name);
        }
    }

    public void ExpireTtl(string delayQueueName, string messageId)
    {
        lock (_lock)
        {
            if (!_queues.TryGetValue(delayQueueName, out var list)) return;
            var msg = list.FirstOrDefault(m => m.MessageId == messageId);
            if (msg == null) return;

            list.Remove(msg);
            var config = _queueConfigs.GetValueOrDefault(delayQueueName, new QueueArguments());
            if (!string.IsNullOrEmpty(config.DeadLetterExchange))
            {
                var targetQueue = config.DeadLetterRoutingKey ?? config.DeadLetterExchange;
                DeadLetter(msg, delayQueueName, targetQueue, DeadLetterReason.Expired, "Message TTL expired in delayed retry queue");
            }
        }
    }

    private void DeadLetter(
        AmqpMessage message,
        string sourceQueue,
        string targetQueue,
        DeadLetterReason reason,
        string? details = null,
        string? exceptionType = null)
    {
        var deathEntry = new XDeathEntry(
            Queue: sourceQueue,
            Reason: reason,
            Count: message.RetryCount,
            Exchange: "dlx.direct",
            Timestamp: DateTime.UtcNow,
            ExceptionMessage: details,
            ExceptionType: exceptionType
        );

        var updatedHistory = new List<XDeathEntry>(message.DeathHistory) { deathEntry };
        var deadLetteredMsg = message with { DeathHistory = updatedHistory };

        Publish(targetQueue, deadLetteredMsg);
    }

    public IReadOnlyList<AmqpMessage> GetQueueMessages(string queueName)
    {
        lock (_lock)
        {
            return _queues.TryGetValue(queueName, out var list) ? list.ToList() : Array.Empty<AmqpMessage>();
        }
    }

    public void DispatchNext(string queueName)
    {
        AmqpMessage? msg = null;
        Action<AmqpMessage>? consumer = null;

        lock (_lock)
        {
            if (_queues.TryGetValue(queueName, out var list) && list.Count > 0)
            {
                msg = list[0];
            }
            _consumers.TryGetValue(queueName, out consumer);
        }

        if (msg != null && consumer != null)
        {
            consumer(msg);
        }
    }
}
