Day 31 Deep Dive Notes: Transactional Outbox, Polling, CDC & Union-Find

1. The Dual-Write Problem & The Fallacy of Distributed Transactions

The Problem Formulated

Consider a microservice executing a business command:

// FATAL ANTI-PATTERN:
await dbContext.Orders.AddAsync(order);
await dbContext.SaveChangesAsync(); // Step 1: Database Commit

await messageBus.PublishAsync(new OrderCreatedEvent(order)); // Step 2: Broker Publish

There are three points of failure:

  1. Network Partition or Broker Crash after Step 1: The database has permanently committed the order, but the event is never published. Upstream callers see a successful order, but shipping, billing, and inventory never execute.
  2. Crash between Step 1 and Step 2: The process dies (OOM, container restart, host termination). The event is lost forever.
  3. Publishing before Step 1:
   await messageBus.PublishAsync(new OrderCreatedEvent(order));
   await dbContext.SaveChangesAsync(); // Throws DbUpdateConcurrencyException or UniqueKeyViolation!

Now the broker received the event and consumers reserved stock or billed a customer for an order that does not exist in the database.

Why 2-Phase Commit (2PC) Fails in Microservices

Two-Phase Commit (XA protocol) introduces:

  • Synchronous Blocking: Every participating resource holds locks until the coordinator sends commit. If the coordinator crashes during the prepare phase, resources remain locked indefinitely.
  • Extreme Latency: Multiple network round-trips over WAN dramatically throttle transaction throughput ($\le 50 \text{ ops/sec}$).
  • Heterogeneity Incompatibility: Modern cloud message brokers (RabbitMQ, Apache Kafka, AWS SQS) do NOT implement XA/2PC transactions with relational databases.

The Transactional Outbox Pattern circumvents 2PC by trading synchronous distributed consistency for Eventual Consistency guaranteed by local ACID transactions.

2. Polling Publisher Mechanics & Database Locking

High-Concurrency Polling with SKIP LOCKED

In high-throughput environments with multiple app instances, naive polling causes catastrophic database lock contention:

-- ANTI-PATTERN:
SELECT * FROM OutboxMessages WHERE ProcessedOnUtc IS NULL LIMIT 50;

If 10 workers run this simultaneously, they all fetch the exact same 50 rows and attempt to process and update them, causing deadlocks.

The Solution: Non-Blocking Row-Level Reservation (FOR UPDATE SKIP LOCKED):

SELECT Id, EventType, Payload 
FROM OutboxMessages 
WHERE ProcessedOnUtc IS NULL 
ORDER BY OccurredOnUtc ASC 
LIMIT 50 
FOR UPDATE SKIP LOCKED;
  • FOR UPDATE: Locks the selected rows for the duration of the transaction.
  • SKIP LOCKED: Informs the query planner to immediately skip any rows that are already locked by another concurrent transaction, without waiting.
  • This allows 10 worker threads to each acquire 50 mutually exclusive messages with zero blocking and zero deadlock contention!

3. Change Data Capture (CDC) via Debezium & Write-Ahead Logs

The CDC Architecture

Instead of application workers polling the database via SQL queries:

  1. When the business transaction commits, PostgreSQL appends the row change to its Write-Ahead Log (WAL).
  2. Debezium (running as a Kafka Connect source connector) streams the raw WAL replication stream via PostgreSQL logical decoding (e.g. pgoutput).
  3. Debezium extracts the INSERT on OutboxMessages and converts it into a Kafka/RabbitMQ message in real-time ($< 10\text{ms}$ latency).
  4. An automated connector or outbox cleanup job deletes processed outbox rows or truncates aged partitions.

4. DSA Deep Dive: Disjoint Set Union (Union-Find)

Mathematical Foundations

A Disjoint Set Union (DSU) maintains a partition of a set $S = \{1, 2, \dots, n\}$ into non-overlapping subsets. It supports two primary operations:

  1. $\text{Find}(x)$: Returns the representative/root of the subset containing $x$.
  2. $\text{Union}(u, v)$: Merges the subsets containing $u$ and $v$.

Optimizations

  1. Path Compression:

During $\text{Find}(x)$, every visited node's parent pointer is flattened directly to the set's root:

   if (parent[x] != x) parent[x] = Find(parent[x]);
   return parent[x];
  1. Union by Rank / Size:

Always attach the root of the tree with smaller depth (rank) to the root of the tree with larger depth. This bounds the maximum tree height to $\mathcal{O}(\log N)$ without path compression, and $\mathcal{O}(\alpha(N))$ with path compression.

Inverse Ackermann Function $\alpha(N)$

The Ackermann function $A(m, n)$ grows at an astronomical rate:

  • $A(1, 1) = 3$
  • $A(2, 2) = 7$
  • $A(3, 3) = 61$
  • $A(4, 4) = 2^{2^{2^{65536}}} - 3$ (greater than the number of atoms in the observable universe!)

The Inverse Ackermann function $\alpha(N)$ is the value of $k$ such that $A(k, k) \ge N$.

For all practical input sizes ($N \le 10^{80}$):

$$\alpha(N) < 5$$

Thus, DSU operations run in effective amortized constant time $\mathcal{O}(1)$.

Day 31: The Transactional Outbox Pattern

Architectural Overview

In distributed architectures, microservices must frequently perform two critical actions:

  1. Mutate operational state in an ACID relational database (e.g. insert an Order).
  2. Publish an event to an asynchronous message broker (e.g. OrderCreatedEvent to RabbitMQ/Kafka).

Executing these two operations as separate, uncoordinated steps leads to the classic Dual-Write Problem:

  • If the database commits but the network call to the message broker fails or times out, downstream consumers never learn of the new order (silent data inconsistency).
  • If the message broker publication succeeds first but the subsequent database transaction rolls back, downstream services process phantom events for state that was never committed.

Two-Phase Commit (2PC / XA Transactions) across heterogeneous storage engines is non-viable in cloud microservices due to extreme latency overhead, locking, and lack of support in modern brokers.

The Transactional Outbox Pattern solves this problem by guaranteeing At-Least-Once event delivery without distributed transactions, relying strictly on the local database's native ACID transaction boundary.

Key Architectural Concepts

1. Atomic Local Database Persistence

Instead of publishing directly to the broker inside the business transaction:

  1. The business mutation (Order) and the outgoing message (OutboxMessage) are written to the database within the same local ACID transaction.
  2. If the transaction commits, both records persist. If the transaction aborts, both roll back. Dual-write inconsistency is mathematically eliminated.
+--------------------------------------------------------------+
|                     Local ACID Transaction                   |
|                                                              |
|   1. INSERT INTO Orders (...)                                |
|   2. INSERT INTO OutboxMessages (Payload, EventType, ...)    |
|   COMMIT                                                     |
+--------------------------------------------------------------+

3. Worker Leasing & Concurrency

When multiple outbox background workers run across scale-out instances:

  • A worker leases pending rows using an expiration timestamp (LockedUntilUtc) and instance ID (LockId).
  • Relational engines utilize SELECT ... FOR UPDATE SKIP LOCKED to allow parallel workers to process non-overlapping partitions without contention or deadlock.

4. At-Least-Once Delivery & The Idempotent Consumer (Inbox Pattern)

Because outbox publishers may crash after dispatching a message to the broker but before marking ProcessedOnUtc in the database, message re-delivery is guaranteed to happen occasionally.

Downstream consumers must implement the Inbox Pattern:

  1. Check InboxMessages table for the unique MessageId.
  2. If found, safely ACK and discard without re-running business side-effects.
  3. If not found, execute the side-effect and record the MessageId atomically.

Data Structures & Algorithms: Disjoint Set Union (Union-Find)

LeetCode #684: Redundant Connection (Medium)

  • Problem: Given a graph that started as a tree of $N$ nodes labeled $1$ to $N$, with one additional edge added, find the edge that can be removed so the resulting graph is a tree. If multiple answers, return the edge that occurs last in the input.
  • Algorithm (Disjoint Set Union with Path Compression and Union by Rank):
  • Initialize each node as its own parent with rank 1.
  • For each edge $(u, v)$:
  • Find root representatives: $R_u = \text{Find}(u)$ and $R_v = \text{Find}(v)$.
  • If $R_u == R_v$, vertices $u$ and $v$ are already connected in the same component. Adding this edge closes a cycle; return $(u, v)$ immediately.
  • Otherwise, merge sets using $\text{Union}(u, v)$ by attaching the smaller rank tree under the larger rank tree.
  • Complexity:
  • Time Complexity: $\mathcal{O}(N \cdot \alpha(N)) \approx \mathcal{O}(N)$, where $\alpha$ is the Inverse Ackermann function ($\alpha(N) < 5$).
  • Space Complexity: $\mathcal{O}(N)$ for the parent and rank arrays.

10 Senior / Staff-Level Interview Questions with In-Depth Answers:
Q1 What is the Dual-Write Problem in microservices, and why can't it be solved by wrapping database commits and message publication in a standard `try-catch` block?
▼

Answer:

The Dual-Write Problem arises whenever an application attempts to update two separate stateful systems (e.g., commit an SQL database transaction and publish an AMQP/Kafka message) without a distributed consensus coordinator.

Wrapping them in a try-catch block fails due to the physical realities of network failures:

  1. Database first, broker second: If context.SaveChangesAsync() succeeds, the local database state is durable. If the process crashes or network partitions before bus.PublishAsync() succeeds, the try-catch may catch an error or crash completely, but the database transaction cannot be rolled back because it has already committed and other transactions may have built on it. The event is permanently lost.
  2. Broker first, database second: If bus.PublishAsync() succeeds, the broker delivers the event to downstream consumers immediately. If context.SaveChangesAsync() subsequently throws an optimistic concurrency violation, unique constraint error, or disk failure, downstream services have already reacted to phantom data that never existed.

Distributed transactions (2PC) are not supported by modern cloud brokers; therefore, dual-writes cannot be solved with application-level try-catch blocks.

Q2 Explain the Transactional Outbox Pattern. What exact guarantees does it provide, and what trade-offs does it introduce?
▼

Answer:

The Transactional Outbox Pattern eliminates dual-writes by leveraging the local ACID transaction boundary of the database.

  • Mechanism: Instead of publishing directly to the broker, the service writes both the business entity (e.g. Order) and an OutboxMessage record inside the same local database transaction. A separate background process (polling worker or CDC log tailer) reads the outbox table and publishes events to the broker.
  • Guarantees:
  • Atomicity: An event is guaranteed to be saved if and only if the business data is saved.
  • At-Least-Once Delivery: Every event will eventually be published to the broker at least once.
  • Trade-offs:
  • Eventual Consistency: There is a latency gap (milliseconds to seconds) between database commit and event consumption.
  • Duplicate Messages: The publisher may crash after sending to the broker but before updating the outbox table, requiring downstream consumers to be idempotent.
  • Database Storage Growth: The outbox table requires indexing and continuous cleanup/purging.
Q3 How do you implement high-throughput outbox message polling without running into database deadlocks and worker contention?
▼

Answer:

When scaling out microservice instances (e.g. 10 Kubernetes pods running the same outbox background worker), multiple workers polling the same OutboxMessages table will compete for the same rows.

To eliminate contention:

  1. SELECT ... FOR UPDATE SKIP LOCKED: In PostgreSQL, MySQL 8+, and Oracle (or WITH (UPDLOCK, READPAST) in SQL Server), workers query:
   SELECT * FROM OutboxMessages 
   WHERE ProcessedOnUtc IS NULL 
   ORDER BY OccurredOnUtc ASC 
   LIMIT @BatchSize 
   FOR UPDATE SKIP LOCKED;

SKIP LOCKED instructs the engine to immediately bypass any rows currently locked by another worker. Workers never wait for each other, preventing lock contention and eliminating deadlocks completely.

  1. Lease/Heartbeat Pattern: For database engines without native SKIP LOCKED, use an optimistic lease: update LockedUntilUtc = NOW() + INTERVAL '30 SECONDS', LockId = @WorkerId with an atomic UPDATE ... WHERE LockedUntilUtc < NOW().
Q4 How does Change Data Capture (CDC) via Debezium compare to application-level outbox polling? When should you switch?
▼

Answer:

  • Polling Publisher:
  • An application background worker queries the database every $N$ milliseconds.
  • Pros: Zero infrastructure overhead; pure C#/.NET code; easy to maintain and test.
  • Cons: Periodic polling adds CPU/IO load to the database; introduces poll interval latency ($200\text{ms} - 2\text{s}$).
  • Change Data Capture (CDC / Debezium):
  • Debezium connects as a replication follower to the database Write-Ahead Log (PostgreSQL WAL or MySQL binlog). It streams committed transactions to Kafka in real time.
  • Pros: Sub-second latency ($< 10\text{ms}$); zero polling queries against database indexes; eliminates all lock contention.
  • Cons: High operational complexity; requires Kafka Connect, Kafka cluster, schema registries, and replication slot monitoring to prevent WAL disk blowouts.
  • When to switch: Stay with application polling for modest throughput ($< 500 \text{ msgs/sec}$). Switch to CDC when outbox polling overhead degrades primary database performance or when sub-100ms end-to-end event propagation is mandatory.
Q5 Why does the Transactional Outbox Pattern guarantee At-Least-Once delivery instead of Exactly-Once delivery?
▼

Answer:

In any distributed system, the Two Generals' Problem dictates that reliable message delivery across an unreliable network cannot achieve exactly-once execution natively at the transport layer.

Consider an outbox publisher:

  1. It fetches an outbox message.
  2. It calls broker.PublishAsync(msg).
  3. The broker receives and persists the message, and sends an ACK over TCP.
  4. Failure point: A network hiccup drops the TCP ACK, or the worker process crashes (OOM, SIGKILL) right before executing UPDATE OutboxMessages SET ProcessedOnUtc = NOW().

When the worker restarts or another worker acquires the lease, it re-reads the un-processed outbox row and publishes it to the broker a second time.

Therefore, the outbox pattern guarantees At-Least-Once Delivery. Exactly-Once processing can only be achieved at the consumer end through Idempotent Consumers (Inbox Pattern).

Q6 Describe the Idempotent Consumer (Inbox Pattern). How do you design it for high-throughput scale?
▼

Answer:

The Inbox Pattern guarantees that re-delivered messages do not trigger duplicate side-effects (e.g. charging a credit card twice or double-incrementing inventory).

  • Mechanism:
  1. The consumer receives a message containing a globally unique MessageId (UUID) or business deduplication key.
  2. Inside the consumer's local database transaction, it queries the InboxMessages table.
  3. If MessageId exists, the message has already been processed: the consumer immediately ACKs the broker and exits without executing side-effects.
  4. If MessageId does not exist, the consumer executes the business logic and inserts INSERT INTO InboxMessages (Id, ProcessedAtUtc) within the same database transaction.
  • High-Throughput Optimization:
  • Insert a high-speed Redis filter (e.g., SETNX message:{id} 1 EX 86400) before querying the database to absorb 99.9% of duplicate checks without hitting disk.
  • Ensure the database InboxMessages table has a primary key on MessageId and is partitioned by date with automated partition truncation.
Q7 How should you manage long-term data cleanup for the `OutboxMessages` table in high-throughput production environments?
▼

Answer:

In systems publishing millions of events daily, an outbox table will rapidly bloat to hundreds of gigabytes, severely degrading index efficiency (VACUUM overhead in PostgreSQL).

Three production cleanup strategies:

  1. Immediate Delete on Publish: Instead of UPDATE OutboxMessages SET ProcessedOnUtc = NOW(), execute DELETE FROM OutboxMessages WHERE Id = @Id. This keeps the table size near zero. However, it removes historical auditing.
  2. Range Partitioning by Day/Month: Partition the outbox table by OccurredOnUtc. When a day's partition has all messages processed, drop the entire table partition (DROP TABLE outbox_messages_2026_10_14). Dropping a partition is an $\mathcal{O}(1)$ metadata operation with zero WAL bloat and zero vacuum lock contention.
  3. Background Chunked Purge: Run an asynchronous scheduled worker executing DELETE FROM OutboxMessages WHERE ProcessedOnUtc < NOW() - INTERVAL '7 DAYS' LIMIT 5000 to prevent holding long table locks.
Q8 What happens if an outbox publisher crashes mid-batch? How does this impact message ordering?
▼

Answer:

If a worker crashes while publishing a batch of 50 messages (e.g. after publishing message 20):

  • Messages 1 to 20 are already in the broker.
  • Messages 21 to 50 are not yet in the broker.
  • When the worker lease expires, a new worker leases all 50 messages (since the database transaction marking them processed never committed).
  • The new worker publishes messages 1 to 50.
  • Consequence: Messages 1 to 20 are published twice, and can arrive interleaved with messages 21 to 50.
  • Strict Ordering Guarantee: The Transactional Outbox cannot guarantee strict global message ordering across worker crashes without partitioning messages by aggregate key (e.g. Kafka PartitionKey / RabbitMQ Consistent Hash) and processing keys sequentially.
Q9 Explain how Union-Find (Disjoint Set Union) detects cycles in an undirected graph. Why is it preferred over DFS/BFS for dynamic edge streams?
▼

Answer:

  • Cycle Detection Mechanism:

A tree on $N$ vertices has exactly $N - 1$ edges and contains no cycles. For every edge $(u, v)$, we query $\text{Find}(u)$ and $\text{Find}(v)$. If they have different root representatives, they belong to disjoint connected components; we execute $\text{Union}(u, v)$ to connect them. If $\text{Find}(u) == \text{Find}(v)$, $u$ and $v$ are already connected via an existing path. Adding the edge $(u, v)$ creates an alternate path between them, which by definition forms a cycle.

  • Why DSU over DFS/BFS for Dynamic Streams:
  • In a static graph, DFS/BFS can detect cycles in $\mathcal{O}(V + E)$.
  • In a dynamic graph where edges are streamed incrementally (online edge additions), running DFS/BFS after each added edge takes $\mathcal{O}(E \times (V + E)) = \mathcal{O}(E^2)$, which is $\mathcal{O}(N^2)$.
  • DSU processes each edge in near $\mathcal{O}(1)$ amortized time ($\mathcal{O}(\alpha(N))$), allowing the entire stream of $N$ edges to be evaluated in $\mathcal{O}(N \cdot \alpha(N)) \approx \mathcal{O}(N)$ total time.
Q10 What is the difference between Union by Rank and Union by Size in DSU? Why does combining path compression with union by rank achieve $\mathcal{O}(\alpha(N))$ time?
▼

Answer:

  • Union by Rank: The rank represents an upper bound on the tree depth. When uniting roots $R_u$ and $R_v$, the root with smaller rank is attached as a child to the root with larger rank. If ranks are equal, one is chosen as parent and its rank is incremented by 1.
  • Union by Size: The size represents the total count of elements in the subtree. The root with smaller size is always attached under the root with larger size.
  • Why $\mathcal{O}(\alpha(N))$:
  • Without optimizations, a naive Union-Find can degenerate into a linear linked list of depth $N$, resulting in $\mathcal{O}(N)$ per operation ($\mathcal{O}(N^2)$ overall).
  • Union by rank alone guarantees the tree height never exceeds $\lfloor \log_2 N \rfloor$, ensuring $\mathcal{O}(\log N)$ per operation.
  • Path compression flattens the tree so that subsequent operations take $\mathcal{O}(1)$.
  • Combining both prevents pathological re-deepening of paths. Tarjan mathematically proved that doing both path compression and union by rank reduces the amortized cost per operation to $\mathcal{O}(\alpha(N))$, where $\alpha$ is the Inverse Ackermann function.

namespace Day31.TransactionalOutbox;

public class DisjointSetUnion
{
    private readonly int[] _parent;
    private readonly int[] _rank;

    public DisjointSetUnion(int size)
    {
        _parent = new int[size + 1];
        _rank = new int[size + 1];
        for (int i = 0; i <= size; i++)
        {
            _parent[i] = i;
            _rank[i] = 1;
        }
    }

    /// <summary>
    /// Finds the canonical representative of the set containing element x with Path Compression.
    /// Amortized Time Complexity: O(alpha(N))
    /// </summary>
    public int Find(int x)
    {
        if (_parent[x] != x)
        {
            _parent[x] = Find(_parent[x]); // Path compression
        }
        return _parent[x];
    }

    /// <summary>
    /// Unites the sets containing u and v using Union by Rank.
    /// Returns false if u and v are already in the same set (cycle detected); otherwise true.
    /// </summary>
    public bool Union(int u, int v)
    {
        int rootU = Find(u);
        int rootV = Find(v);

        if (rootU == rootV)
        {
            return false; // Cycle detected!
        }

        // Union by rank: attach smaller tree under root of larger tree
        if (_rank[rootU] < _rank[rootV])
        {
            _parent[rootU] = rootV;
        }
        else if (_rank[rootU] > _rank[rootV])
        {
            _parent[rootV] = rootU;
        }
        else
        {
            _parent[rootV] = rootU;
            _rank[rootU]++;
        }

        return true;
    }

    public bool IsConnected(int u, int v) => Find(u) == Find(v);
}

public static class RedundantConnectionSolver
{
    /// <summary>
    /// LeetCode #684: Redundant Connection (Medium).
    /// Identifies the edge that can be removed so the graph becomes a tree.
    /// Time Complexity: O(N * alpha(N)) approx O(N), Space Complexity: O(N)
    /// </summary>
    public static int[] FindRedundantConnection(int[][] edges)
    {
        if (edges == null || edges.Length == 0) return Array.Empty<int>();

        int n = edges.Length;
        var dsu = new DisjointSetUnion(n);

        foreach (var edge in edges)
        {
            int u = edge[0];
            int v = edge[1];

            // If u and v already share the same root, adding (u, v) creates a cycle
            if (!dsu.Union(u, v))
            {
                return edge;
            }
        }

        return Array.Empty<int>();
    }
}

    }

public class OutboxPublisherWorker
{
    private readonly OutboxDbContext _dbContext;
    private readonly IMessageBroker _messageBroker;

    public int MaxRetries { get; set; } = 3;

    public OutboxPublisherWorker(OutboxDbContext dbContext, IMessageBroker messageBroker)
    {
        _dbContext = dbContext;
        _messageBroker = messageBroker;
    }

    /// <summary>
    /// Polls pending outbox messages, leases rows, publishes to message broker, and marks processed.
    /// </summary>
    public async Task<int> ProcessOutboxMessagesAsync(int batchSize = 10, string? workerId = null, CancellationToken cancellationToken = default)
    {
        workerId ??= Guid.NewGuid().ToString("N");
        var now = DateTime.UtcNow;

        // 1. Fetch unleased, unprocessed, non-dead-lettered messages
        var pending = await _dbContext.OutboxMessages
            .Where(m => m.ProcessedOnUtc == null &&
                        !m.IsDeadLettered &&
                        (m.LockedUntilUtc == null || m.LockedUntilUtc < now))
            .OrderBy(m => m.OccurredOnUtc)
            .Take(batchSize)
            .ToListAsync(cancellationToken);

        if (pending.Count == 0) return 0;

        // 2. Acquire lease (optimistic concurrency / lock window)
        var leaseDuration = TimeSpan.FromSeconds(30);
        foreach (var msg in pending)
        {
            msg.LockedUntilUtc = now.Add(leaseDuration);
            msg.LockId = workerId;
        }
        await _dbContext.SaveChangesAsync(cancellationToken);

        int processedCount = 0;

        // 3. Dispatch each leased message to the broker
        foreach (var msg in pending)
        {
            try
            {
                await _messageBroker.PublishAsync(msg.EventType, msg.Payload, cancellationToken);

                // Publication confirmed -> mark processed and clear lock
                msg.ProcessedOnUtc = DateTime.UtcNow;
                msg.LockedUntilUtc = null;
                msg.LockId = null;
                msg.Error = null;
                processedCount++;
            }
            catch (Exception ex)
            {
                msg.RetryCount++;
                msg.Error = ex.Message;

                if (msg.RetryCount >= MaxRetries)
                {
                    // Move to dead-letter state
                    msg.IsDeadLettered = true;
                    msg.LockedUntilUtc = null;
                    msg.LockId = null;
                }
                else
                {
                    // Exponential backoff lease delay: 2^retry seconds
                    var backoffDelay = TimeSpan.FromSeconds(Math.Pow(2, msg.RetryCount));
                    msg.LockedUntilUtc = DateTime.UtcNow.Add(backoffDelay);
                    msg.LockId = null;
                }
            }
        }

        await _dbContext.SaveChangesAsync(cancellationToken);
        return processedCount;
    }
}

public class IdempotentConsumer
{
    private readonly OutboxDbContext _dbContext;

    public IdempotentConsumer(OutboxDbContext dbContext)
    {
        _dbContext = dbContext;
    }

    /// <summary>
    /// Processes an incoming event with Inbox deduplication to guarantee exactly-once side-effects.
    /// </summary>
    public async Task<bool> HandleEventAsync(Guid messageId, string eventType, Func<Task> handleAction, string handlerName = "OrderConsumer")
    {
        // 1. Check if already processed
        var alreadyProcessed = await _dbContext.InboxMessages.AnyAsync(i => i.Id == messageId);
        if (alreadyProcessed)
        {
            // Duplicate detected: acknowledge without re-executing side-effects
            return false;
        }

        // 2. Execute business side effect
        await handleAction();

        // 3. Atomically record message in Inbox
        _dbContext.InboxMessages.Add(new InboxMessage
        {
            Id = messageId,
            EventType = eventType,
            ProcessedAtUtc = DateTime.UtcNow,
            HandlerName = handlerName
        });

        await _dbContext.SaveChangesAsync();
        return true;
    }
}

📝 Part 1: Deep-Dive Architectural & Engineering Notes

Day 31 Deep Dive Notes: Transactional Outbox, Polling, CDC & Union-Find

1. The Dual-Write Problem & The Fallacy of Distributed Transactions

The Problem Formulated

Consider a microservice executing a business command:

// FATAL ANTI-PATTERN:
await dbContext.Orders.AddAsync(order);
await dbContext.SaveChangesAsync(); // Step 1: Database Commit

await messageBus.PublishAsync(new OrderCreatedEvent(order)); // Step 2: Broker Publish

There are three points of failure:

  1. Network Partition or Broker Crash after Step 1: The database has permanently committed the order, but the event is never published. Upstream callers see a successful order, but shipping, billing, and inventory never execute.
  2. Crash between Step 1 and Step 2: The process dies (OOM, container restart, host termination). The event is lost forever.
  3. Publishing before Step 1:
   await messageBus.PublishAsync(new OrderCreatedEvent(order));
   await dbContext.SaveChangesAsync(); // Throws DbUpdateConcurrencyException or UniqueKeyViolation!

Now the broker received the event and consumers reserved stock or billed a customer for an order that does not exist in the database.

Why 2-Phase Commit (2PC) Fails in Microservices

Two-Phase Commit (XA protocol) introduces:

  • Synchronous Blocking: Every participating resource holds locks until the coordinator sends commit. If the coordinator crashes during the prepare phase, resources remain locked indefinitely.
  • Extreme Latency: Multiple network round-trips over WAN dramatically throttle transaction throughput ($\le 50 \text{ ops/sec}$).
  • Heterogeneity Incompatibility: Modern cloud message brokers (RabbitMQ, Apache Kafka, AWS SQS) do NOT implement XA/2PC transactions with relational databases.

The Transactional Outbox Pattern circumvents 2PC by trading synchronous distributed consistency for Eventual Consistency guaranteed by local ACID transactions.

2. Polling Publisher Mechanics & Database Locking

High-Concurrency Polling with SKIP LOCKED

In high-throughput environments with multiple app instances, naive polling causes catastrophic database lock contention:

-- ANTI-PATTERN:
SELECT * FROM OutboxMessages WHERE ProcessedOnUtc IS NULL LIMIT 50;

If 10 workers run this simultaneously, they all fetch the exact same 50 rows and attempt to process and update them, causing deadlocks.

The Solution: Non-Blocking Row-Level Reservation (FOR UPDATE SKIP LOCKED):

SELECT Id, EventType, Payload 
FROM OutboxMessages 
WHERE ProcessedOnUtc IS NULL 
ORDER BY OccurredOnUtc ASC 
LIMIT 50 
FOR UPDATE SKIP LOCKED;
  • FOR UPDATE: Locks the selected rows for the duration of the transaction.
  • SKIP LOCKED: Informs the query planner to immediately skip any rows that are already locked by another concurrent transaction, without waiting.
  • This allows 10 worker threads to each acquire 50 mutually exclusive messages with zero blocking and zero deadlock contention!

3. Change Data Capture (CDC) via Debezium & Write-Ahead Logs

The CDC Architecture

Instead of application workers polling the database via SQL queries:

  1. When the business transaction commits, PostgreSQL appends the row change to its Write-Ahead Log (WAL).
  2. Debezium (running as a Kafka Connect source connector) streams the raw WAL replication stream via PostgreSQL logical decoding (e.g. pgoutput).
  3. Debezium extracts the INSERT on OutboxMessages and converts it into a Kafka/RabbitMQ message in real-time ($< 10\text{ms}$ latency).
  4. An automated connector or outbox cleanup job deletes processed outbox rows or truncates aged partitions.

4. DSA Deep Dive: Disjoint Set Union (Union-Find)

Mathematical Foundations

A Disjoint Set Union (DSU) maintains a partition of a set $S = \{1, 2, \dots, n\}$ into non-overlapping subsets. It supports two primary operations:

  1. $\text{Find}(x)$: Returns the representative/root of the subset containing $x$.
  2. $\text{Union}(u, v)$: Merges the subsets containing $u$ and $v$.

Optimizations

  1. Path Compression:

During $\text{Find}(x)$, every visited node's parent pointer is flattened directly to the set's root:

   if (parent[x] != x) parent[x] = Find(parent[x]);
   return parent[x];
  1. Union by Rank / Size:

Always attach the root of the tree with smaller depth (rank) to the root of the tree with larger depth. This bounds the maximum tree height to $\mathcal{O}(\log N)$ without path compression, and $\mathcal{O}(\alpha(N))$ with path compression.

Inverse Ackermann Function $\alpha(N)$

The Ackermann function $A(m, n)$ grows at an astronomical rate:

  • $A(1, 1) = 3$
  • $A(2, 2) = 7$
  • $A(3, 3) = 61$
  • $A(4, 4) = 2^{2^{2^{65536}}} - 3$ (greater than the number of atoms in the observable universe!)

The Inverse Ackermann function $\alpha(N)$ is the value of $k$ such that $A(k, k) \ge N$.

For all practical input sizes ($N \le 10^{80}$):

$$\alpha(N) < 5$$

Thus, DSU operations run in effective amortized constant time $\mathcal{O}(1)$.

📑 Part 2: Module Overview & Practical Walkthrough

Day 31: The Transactional Outbox Pattern

Architectural Overview

In distributed architectures, microservices must frequently perform two critical actions:

  1. Mutate operational state in an ACID relational database (e.g. insert an Order).
  2. Publish an event to an asynchronous message broker (e.g. OrderCreatedEvent to RabbitMQ/Kafka).

Executing these two operations as separate, uncoordinated steps leads to the classic Dual-Write Problem:

  • If the database commits but the network call to the message broker fails or times out, downstream consumers never learn of the new order (silent data inconsistency).
  • If the message broker publication succeeds first but the subsequent database transaction rolls back, downstream services process phantom events for state that was never committed.

Two-Phase Commit (2PC / XA Transactions) across heterogeneous storage engines is non-viable in cloud microservices due to extreme latency overhead, locking, and lack of support in modern brokers.

The Transactional Outbox Pattern solves this problem by guaranteeing At-Least-Once event delivery without distributed transactions, relying strictly on the local database's native ACID transaction boundary.

Key Architectural Concepts

1. Atomic Local Database Persistence

Instead of publishing directly to the broker inside the business transaction:

  1. The business mutation (Order) and the outgoing message (OutboxMessage) are written to the database within the same local ACID transaction.
  2. If the transaction commits, both records persist. If the transaction aborts, both roll back. Dual-write inconsistency is mathematically eliminated.
+--------------------------------------------------------------+
|                     Local ACID Transaction                   |
|                                                              |
|   1. INSERT INTO Orders (...)                                |
|   2. INSERT INTO OutboxMessages (Payload, EventType, ...)    |
|   COMMIT                                                     |
+--------------------------------------------------------------+

2. Outbox Dispatch Strategies: Polling vs Change Data Capture (CDC)

Characteristic Polling Publisher Change Data Capture (CDC / Debezium)
Mechanism Background worker queries OutboxMessages with leasing Tails database write-ahead log (WAL)
Database Overhead Regular SELECT ... FOR UPDATE SKIP LOCKED polling queries Minimal; reads the sequential append-only WAL stream
Latency Polling interval delay (e.g., 200ms–2s) Real-time / sub-second streaming
Operational Complexity Low; runs as standard ASP.NET Core IHostedService High; requires Kafka Connect, Debezium, ZooKeeper/KRaft

3. Worker Leasing & Concurrency

When multiple outbox background workers run across scale-out instances:

  • A worker leases pending rows using an expiration timestamp (LockedUntilUtc) and instance ID (LockId).
  • Relational engines utilize SELECT ... FOR UPDATE SKIP LOCKED to allow parallel workers to process non-overlapping partitions without contention or deadlock.

4. At-Least-Once Delivery & The Idempotent Consumer (Inbox Pattern)

Because outbox publishers may crash after dispatching a message to the broker but before marking ProcessedOnUtc in the database, message re-delivery is guaranteed to happen occasionally.

Downstream consumers must implement the Inbox Pattern:

  1. Check InboxMessages table for the unique MessageId.
  2. If found, safely ACK and discard without re-running business side-effects.
  3. If not found, execute the side-effect and record the MessageId atomically.

Data Structures & Algorithms: Disjoint Set Union (Union-Find)

LeetCode #684: Redundant Connection (Medium)

  • Problem: Given a graph that started as a tree of $N$ nodes labeled $1$ to $N$, with one additional edge added, find the edge that can be removed so the resulting graph is a tree. If multiple answers, return the edge that occurs last in the input.
  • Algorithm (Disjoint Set Union with Path Compression and Union by Rank):
  • Initialize each node as its own parent with rank 1.
  • For each edge $(u, v)$:
  • Find root representatives: $R_u = \text{Find}(u)$ and $R_v = \text{Find}(v)$.
  • If $R_u == R_v$, vertices $u$ and $v$ are already connected in the same component. Adding this edge closes a cycle; return $(u, v)$ immediately.
  • Otherwise, merge sets using $\text{Union}(u, v)$ by attaching the smaller rank tree under the larger rank tree.
  • Complexity:
  • Time Complexity: $\mathcal{O}(N \cdot \alpha(N)) \approx \mathcal{O}(N)$, where $\alpha$ is the Inverse Ackermann function ($\alpha(N) < 5$).
  • Space Complexity: $\mathcal{O}(N)$ for the parent and rank arrays.

💡 Part 3: Senior & Staff-Level Interview Scenarios (10 Questions)

Q1 What is the Dual-Write Problem in microservices, and why can't it be solved by wrapping database commits and message publication in a standard `try-catch` block?
▼

Answer:

The Dual-Write Problem arises whenever an application attempts to update two separate stateful systems (e.g., commit an SQL database transaction and publish an AMQP/Kafka message) without a distributed consensus coordinator.

Wrapping them in a try-catch block fails due to the physical realities of network failures:

  1. Database first, broker second: If context.SaveChangesAsync() succeeds, the local database state is durable. If the process crashes or network partitions before bus.PublishAsync() succeeds, the try-catch may catch an error or crash completely, but the database transaction cannot be rolled back because it has already committed and other transactions may have built on it. The event is permanently lost.
  2. Broker first, database second: If bus.PublishAsync() succeeds, the broker delivers the event to downstream consumers immediately. If context.SaveChangesAsync() subsequently throws an optimistic concurrency violation, unique constraint error, or disk failure, downstream services have already reacted to phantom data that never existed.

Distributed transactions (2PC) are not supported by modern cloud brokers; therefore, dual-writes cannot be solved with application-level try-catch blocks.

Q2 Explain the Transactional Outbox Pattern. What exact guarantees does it provide, and what trade-offs does it introduce?
▼

Answer:

The Transactional Outbox Pattern eliminates dual-writes by leveraging the local ACID transaction boundary of the database.

  • Mechanism: Instead of publishing directly to the broker, the service writes both the business entity (e.g. Order) and an OutboxMessage record inside the same local database transaction. A separate background process (polling worker or CDC log tailer) reads the outbox table and publishes events to the broker.
  • Guarantees:
  • Atomicity: An event is guaranteed to be saved if and only if the business data is saved.
  • At-Least-Once Delivery: Every event will eventually be published to the broker at least once.
  • Trade-offs:
  • Eventual Consistency: There is a latency gap (milliseconds to seconds) between database commit and event consumption.
  • Duplicate Messages: The publisher may crash after sending to the broker but before updating the outbox table, requiring downstream consumers to be idempotent.
  • Database Storage Growth: The outbox table requires indexing and continuous cleanup/purging.
Q3 How do you implement high-throughput outbox message polling without running into database deadlocks and worker contention?
▼

Answer:

When scaling out microservice instances (e.g. 10 Kubernetes pods running the same outbox background worker), multiple workers polling the same OutboxMessages table will compete for the same rows.

To eliminate contention:

  1. SELECT ... FOR UPDATE SKIP LOCKED: In PostgreSQL, MySQL 8+, and Oracle (or WITH (UPDLOCK, READPAST) in SQL Server), workers query:
   SELECT * FROM OutboxMessages 
   WHERE ProcessedOnUtc IS NULL 
   ORDER BY OccurredOnUtc ASC 
   LIMIT @BatchSize 
   FOR UPDATE SKIP LOCKED;

SKIP LOCKED instructs the engine to immediately bypass any rows currently locked by another worker. Workers never wait for each other, preventing lock contention and eliminating deadlocks completely.

  1. Lease/Heartbeat Pattern: For database engines without native SKIP LOCKED, use an optimistic lease: update LockedUntilUtc = NOW() + INTERVAL '30 SECONDS', LockId = @WorkerId with an atomic UPDATE ... WHERE LockedUntilUtc < NOW().
Q4 How does Change Data Capture (CDC) via Debezium compare to application-level outbox polling? When should you switch?
▼

Answer:

  • Polling Publisher:
  • An application background worker queries the database every $N$ milliseconds.
  • Pros: Zero infrastructure overhead; pure C#/.NET code; easy to maintain and test.
  • Cons: Periodic polling adds CPU/IO load to the database; introduces poll interval latency ($200\text{ms} - 2\text{s}$).
  • Change Data Capture (CDC / Debezium):
  • Debezium connects as a replication follower to the database Write-Ahead Log (PostgreSQL WAL or MySQL binlog). It streams committed transactions to Kafka in real time.
  • Pros: Sub-second latency ($< 10\text{ms}$); zero polling queries against database indexes; eliminates all lock contention.
  • Cons: High operational complexity; requires Kafka Connect, Kafka cluster, schema registries, and replication slot monitoring to prevent WAL disk blowouts.
  • When to switch: Stay with application polling for modest throughput ($< 500 \text{ msgs/sec}$). Switch to CDC when outbox polling overhead degrades primary database performance or when sub-100ms end-to-end event propagation is mandatory.
Q5 Why does the Transactional Outbox Pattern guarantee At-Least-Once delivery instead of Exactly-Once delivery?
▼

Answer:

In any distributed system, the Two Generals' Problem dictates that reliable message delivery across an unreliable network cannot achieve exactly-once execution natively at the transport layer.

Consider an outbox publisher:

  1. It fetches an outbox message.
  2. It calls broker.PublishAsync(msg).
  3. The broker receives and persists the message, and sends an ACK over TCP.
  4. Failure point: A network hiccup drops the TCP ACK, or the worker process crashes (OOM, SIGKILL) right before executing UPDATE OutboxMessages SET ProcessedOnUtc = NOW().

When the worker restarts or another worker acquires the lease, it re-reads the un-processed outbox row and publishes it to the broker a second time.

Therefore, the outbox pattern guarantees At-Least-Once Delivery. Exactly-Once processing can only be achieved at the consumer end through Idempotent Consumers (Inbox Pattern).

Q6 Describe the Idempotent Consumer (Inbox Pattern). How do you design it for high-throughput scale?
▼

Answer:

The Inbox Pattern guarantees that re-delivered messages do not trigger duplicate side-effects (e.g. charging a credit card twice or double-incrementing inventory).

  • Mechanism:
  1. The consumer receives a message containing a globally unique MessageId (UUID) or business deduplication key.
  2. Inside the consumer's local database transaction, it queries the InboxMessages table.
  3. If MessageId exists, the message has already been processed: the consumer immediately ACKs the broker and exits without executing side-effects.
  4. If MessageId does not exist, the consumer executes the business logic and inserts INSERT INTO InboxMessages (Id, ProcessedAtUtc) within the same database transaction.
  • High-Throughput Optimization:
  • Insert a high-speed Redis filter (e.g., SETNX message:{id} 1 EX 86400) before querying the database to absorb 99.9% of duplicate checks without hitting disk.
  • Ensure the database InboxMessages table has a primary key on MessageId and is partitioned by date with automated partition truncation.
Q7 How should you manage long-term data cleanup for the `OutboxMessages` table in high-throughput production environments?
▼

Answer:

In systems publishing millions of events daily, an outbox table will rapidly bloat to hundreds of gigabytes, severely degrading index efficiency (VACUUM overhead in PostgreSQL).

Three production cleanup strategies:

  1. Immediate Delete on Publish: Instead of UPDATE OutboxMessages SET ProcessedOnUtc = NOW(), execute DELETE FROM OutboxMessages WHERE Id = @Id. This keeps the table size near zero. However, it removes historical auditing.
  2. Range Partitioning by Day/Month: Partition the outbox table by OccurredOnUtc. When a day's partition has all messages processed, drop the entire table partition (DROP TABLE outbox_messages_2026_10_14). Dropping a partition is an $\mathcal{O}(1)$ metadata operation with zero WAL bloat and zero vacuum lock contention.
  3. Background Chunked Purge: Run an asynchronous scheduled worker executing DELETE FROM OutboxMessages WHERE ProcessedOnUtc < NOW() - INTERVAL '7 DAYS' LIMIT 5000 to prevent holding long table locks.
Q8 What happens if an outbox publisher crashes mid-batch? How does this impact message ordering?
▼

Answer:

If a worker crashes while publishing a batch of 50 messages (e.g. after publishing message 20):

  • Messages 1 to 20 are already in the broker.
  • Messages 21 to 50 are not yet in the broker.
  • When the worker lease expires, a new worker leases all 50 messages (since the database transaction marking them processed never committed).
  • The new worker publishes messages 1 to 50.
  • Consequence: Messages 1 to 20 are published twice, and can arrive interleaved with messages 21 to 50.
  • Strict Ordering Guarantee: The Transactional Outbox cannot guarantee strict global message ordering across worker crashes without partitioning messages by aggregate key (e.g. Kafka PartitionKey / RabbitMQ Consistent Hash) and processing keys sequentially.
Q9 Explain how Union-Find (Disjoint Set Union) detects cycles in an undirected graph. Why is it preferred over DFS/BFS for dynamic edge streams?
▼

Answer:

  • Cycle Detection Mechanism:

A tree on $N$ vertices has exactly $N - 1$ edges and contains no cycles. For every edge $(u, v)$, we query $\text{Find}(u)$ and $\text{Find}(v)$. If they have different root representatives, they belong to disjoint connected components; we execute $\text{Union}(u, v)$ to connect them. If $\text{Find}(u) == \text{Find}(v)$, $u$ and $v$ are already connected via an existing path. Adding the edge $(u, v)$ creates an alternate path between them, which by definition forms a cycle.

  • Why DSU over DFS/BFS for Dynamic Streams:
  • In a static graph, DFS/BFS can detect cycles in $\mathcal{O}(V + E)$.
  • In a dynamic graph where edges are streamed incrementally (online edge additions), running DFS/BFS after each added edge takes $\mathcal{O}(E \times (V + E)) = \mathcal{O}(E^2)$, which is $\mathcal{O}(N^2)$.
  • DSU processes each edge in near $\mathcal{O}(1)$ amortized time ($\mathcal{O}(\alpha(N))$), allowing the entire stream of $N$ edges to be evaluated in $\mathcal{O}(N \cdot \alpha(N)) \approx \mathcal{O}(N)$ total time.
Q10 What is the difference between Union by Rank and Union by Size in DSU? Why does combining path compression with union by rank achieve $\mathcal{O}(\alpha(N))$ time?
▼

Answer:

  • Union by Rank: The rank represents an upper bound on the tree depth. When uniting roots $R_u$ and $R_v$, the root with smaller rank is attached as a child to the root with larger rank. If ranks are equal, one is chosen as parent and its rank is incremented by 1.
  • Union by Size: The size represents the total count of elements in the subtree. The root with smaller size is always attached under the root with larger size.
  • Why $\mathcal{O}(\alpha(N))$:
  • Without optimizations, a naive Union-Find can degenerate into a linear linked list of depth $N$, resulting in $\mathcal{O}(N)$ per operation ($\mathcal{O}(N^2)$ overall).
  • Union by rank alone guarantees the tree height never exceeds $\lfloor \log_2 N \rfloor$, ensuring $\mathcal{O}(\log N)$ per operation.
  • Path compression flattens the tree so that subsequent operations take $\mathcal{O}(1)$.
  • Combining both prevents pathological re-deepening of paths. Tarjan mathematically proved that doing both path compression and union by rank reduces the amortized cost per operation to $\mathcal{O}(\alpha(N))$, where $\alpha$ is the Inverse Ackermann function.

public class DisjointSetUnion
{
    private readonly int[] _parent;
    private readonly int[] _rank;

    public DisjointSetUnion(int size)
    {
        _parent = new int[size + 1];
        _rank = new int[size + 1];
        for (int i = 0; i <= size; i++)
        {
            _parent[i] = i;
            _rank[i] = 1;
        }
    }

    /// <summary>
    /// Finds the canonical representative of the set containing element x with Path Compression.
    /// Amortized Time Complexity: O(alpha(N))
    /// </summary>
    public int Find(int x)
    {
        if (_parent[x] != x)
        {
            _parent[x] = Find(_parent[x]); // Path compression
        }
        return _parent[x];
    }

    /// <summary>
    /// Unites the sets containing u and v using Union by Rank.
    /// Returns false if u and v are already in the same set (cycle detected); otherwise true.
    /// </summary>
    public bool Union(int u, int v)
    {
        int rootU = Find(u);
        int rootV = Find(v);

        if (rootU == rootV)
        {
            return false; // Cycle detected!
        }

        // Union by rank: attach smaller tree under root of larger tree
        if (_rank[rootU] < _rank[rootV])
        {
            _parent[rootU] = rootV;
        }
        else if (_rank[rootU] > _rank[rootV])
        {
            _parent[rootV] = rootU;
        }
        else
        {
            _parent[rootV] = rootU;
            _rank[rootU]++;
        }

        return true;
    }

    public bool IsConnected(int u, int v) => Find(u) == Find(v);
}

public static class RedundantConnectionSolver
{
    /// <summary>
    /// LeetCode #684: Redundant Connection (Medium).
    /// Identifies the edge that can be removed so the graph becomes a tree.
    /// Time Complexity: O(N * alpha(N)) approx O(N), Space Complexity: O(N)
    /// </summary>
    public static int[] FindRedundantConnection(int[][] edges)
    {
        if (edges == null || edges.Length == 0) return Array.Empty<int>();

        int n = edges.Length;
        var dsu = new DisjointSetUnion(n);

        foreach (var edge in edges)
        {
            int u = edge[0];
            int v = edge[1];

            // If u and v already share the same root, adding (u, v) creates a cycle
            if (!dsu.Union(u, v))
            {
                return edge;
            }
        }

        return Array.Empty<int>();
    }
}

public class OutboxPublisherWorker
{
    private readonly OutboxDbContext _dbContext;
    private readonly IMessageBroker _messageBroker;

    public int MaxRetries { get; set; } = 3;

    public OutboxPublisherWorker(OutboxDbContext dbContext, IMessageBroker messageBroker)
    {
        _dbContext = dbContext;
        _messageBroker = messageBroker;
    }

    /// <summary>
    /// Polls pending outbox messages, leases rows, publishes to message broker, and marks processed.
    /// </summary>
    public async Task<int> ProcessOutboxMessagesAsync(int batchSize = 10, string? workerId = null, CancellationToken cancellationToken = default)
    {
        workerId ??= Guid.NewGuid().ToString("N");
        var now = DateTime.UtcNow;

        // 1. Fetch unleased, unprocessed, non-dead-lettered messages
        var pending = await _dbContext.OutboxMessages
            .Where(m => m.ProcessedOnUtc == null &&
                        !m.IsDeadLettered &&
                        (m.LockedUntilUtc == null || m.LockedUntilUtc < now))
            .OrderBy(m => m.OccurredOnUtc)
            .Take(batchSize)
            .ToListAsync(cancellationToken);

        if (pending.Count == 0) return 0;

        // 2. Acquire lease (optimistic concurrency / lock window)
        var leaseDuration = TimeSpan.FromSeconds(30);
        foreach (var msg in pending)
        {
            msg.LockedUntilUtc = now.Add(leaseDuration);
            msg.LockId = workerId;
        }
        await _dbContext.SaveChangesAsync(cancellationToken);

        int processedCount = 0;

        // 3. Dispatch each leased message to the broker
        foreach (var msg in pending)
        {
            try
            {
                await _messageBroker.PublishAsync(msg.EventType, msg.Payload, cancellationToken);

                // Publication confirmed -> mark processed and clear lock
                msg.ProcessedOnUtc = DateTime.UtcNow;
                msg.LockedUntilUtc = null;
                msg.LockId = null;
                msg.Error = null;
                processedCount++;
            }
            catch (Exception ex)
            {
                msg.RetryCount++;
                msg.Error = ex.Message;

                if (msg.RetryCount >= MaxRetries)
                {
                    // Move to dead-letter state
                    msg.IsDeadLettered = true;
                    msg.LockedUntilUtc = null;
                    msg.LockId = null;
                }
                else
                {
                    // Exponential backoff lease delay: 2^retry seconds
                    var backoffDelay = TimeSpan.FromSeconds(Math.Pow(2, msg.RetryCount));
                    msg.LockedUntilUtc = DateTime.UtcNow.Add(backoffDelay);
                    msg.LockId = null;
                }
            }
        }

        await _dbContext.SaveChangesAsync(cancellationToken);
        return processedCount;
    }
}

public class IdempotentConsumer
{
    private readonly OutboxDbContext _dbContext;

    public IdempotentConsumer(OutboxDbContext dbContext)
    {
        _dbContext = dbContext;
    }

    /// <summary>
    /// Processes an incoming event with Inbox deduplication to guarantee exactly-once side-effects.
    /// </summary>
    public async Task<bool> HandleEventAsync(Guid messageId, string eventType, Func<Task> handleAction, string handlerName = "OrderConsumer")
    {
        // 1. Check if already processed
        var alreadyProcessed = await _dbContext.InboxMessages.AnyAsync(i => i.Id == messageId);
        if (alreadyProcessed)
        {
            // Duplicate detected: acknowledge without re-executing side-effects
            return false;
        }

        // 2. Execute business side effect
        await handleAction();

        // 3. Atomically record message in Inbox
        _dbContext.InboxMessages.Add(new InboxMessage
        {
            Id = messageId,
            EventType = eventType,
            ProcessedAtUtc = DateTime.UtcNow,
            HandlerName = handlerName
        });

        await _dbContext.SaveChangesAsync();
        return true;
    }
}
