Deep Dive Notes: Distributed Idempotency & De-duplication

1. Idempotency Key Semantics in Distributed REST & Messaging

In high-concurrency microservices, idempotency guarantees that making the same request multiple times has the exact same side effects on system state as making it once:

$$f(f(x)) = f(x)$$

The IETF Idempotency-Key HTTP Header Specification

The IETF draft standard defines the Idempotency-Key header sent by HTTP clients. When processing:

  1. Fingerprint Validation: Compute a cryptographic digest (SHA-256) of the HTTP method, request path, and body. If a request arrives with an existing key but a different digest, the server MUST return HTTP 422 Unprocessable Entity or 400 Bad Request.
  2. Lock State: If the key is currently locked (processing) and the lock has not expired, return HTTP 409 Conflict with a Retry-After header.
  3. Completed State: If the key has completed, replay the exact response payload, headers, and status code (typically HTTP 200/201) along with an Idempotent-Replay: true header.

2. Distributed Storage & Lease Strategies

  • Relational DB with Unique Constraints:
  • INSERT INTO idempotency_keys (key, hash, status, locked_until) VALUES (...) ON CONFLICT DO NOTHING;
  • Guarantees ACID atomicity across application clusters.
  • Redis with Redlock or SET NX PX:
  • SET key:idempotency lock_token NX PX 30000
  • High throughput (sub-millisecond), but requires fallback or write-through persistence to a permanent store for long-lived cached results.
  • Worker Crash Handling & Lease Expiration:
  • Never hold a lock without a finite lease timeout (TTL). If node crashes mid-operation, the unreleased lock must expire after a configurable duration (e.g. 30–60s) allowing safe automated recovery.

3. LeetCode #215: Quickselect vs Min-Heap Analysis

  • Quickselect:
  • Partition array around a random pivot.
  • If pivot index equals target index $N - k$, return value.
  • If pivot index $< N - k$, recurse/iterate on the right subarray.
  • If pivot index $> N - k$, recurse/iterate on the left subarray.
  • Recurrence: $T(N) = T(N/2) + O(N) = O(N)$ average time.
  • Worst case: $O(N^2)$ if worst-case pivot selection occurs repeatedly, mitigated via randomized pivot.
  • Min-Heap:
  • Uses System.Collections.Generic.PriorityQueue<int, int> in .NET.
  • Push each element with value as priority. When size exceeds $k$, dequeue smallest element.
  • The heap retains the $k$ largest elements seen so far; top of heap is the $k$-th largest.
  • Time: $O(N \log K)$, Space: $O(K)$. Ideal for streaming data where total size $N$ is unknown or unbounded.

Day 33: Distributed Idempotency & De-duplication

Architectural Overview

In distributed systems, network partitions, client retries, and message broker at-least-once delivery guarantees inevitably produce duplicate requests. Without strict idempotency controls, duplicate submissions result in double-billing, corrupted inventory reserves, or inconsistent ledger entries.

This implementation demonstrates an enterprise-grade distributed idempotency pattern in .NET 8 / C# featuring:

  1. Idempotency Key Protocol: Clients supply a unique idempotency key (e.g., UUID or deterministic hash) via HTTP header or message metadata.
  2. Cryptographic Payload Verification: Computes a SHA-256 digest of the request payload to prevent payload tampering under an existing idempotency key. If payloads differ, an IdempotencyPayloadMismatchException (HTTP 422 Unprocessable Entity) is thrown.
  3. Optimistic Locking & Lease Management: Prevents race conditions during concurrent in-flight requests by reserving a lock with a lease expiration (LockedUntilUtc). If a second request arrives while the first is processing, it receives an IdempotencyConflictException (HTTP 409 Conflict).
  4. Crash Fault Recovery: If a worker node crashes mid-flight, subsequent requests after the lease window automatically reclaim the processing lock instead of deadlocking indefinitely.
  5. Response Caching: Successful responses are stored alongside their HTTP status codes and returned immediately with FromCache = true for subsequent idempotent replays.

LeetCode #215: Kth Largest Element in an Array (Medium)

Finding the $k$-th largest element in an unsorted array efficiently:

  • Quickselect (Hoare's Selection): $O(N)$ average time complexity, $O(1)$ auxiliary space. Uses randomized pivot partitioning to prune half the search space iteratively. Target index is $N - k$.
  • Min-Heap (PriorityQueue<int, int>): $O(N \log K)$ time complexity, $O(K)$ space complexity. Maintains a min-heap of size $k$; the root element is always the $k$-th largest element.

10 Senior / Staff-Level Interview Questions with In-Depth Answers:
Q1 What is the semantic difference between safe, idempotent, and non-idempotent HTTP methods according to RFC 9110?
▼

Answer:

  • Safe Methods (GET, HEAD, OPTIONS, TRACE): Do not modify server resource state. A client can execute them without expectation of mutation or side effects.
  • Idempotent Methods (PUT, DELETE, GET, HEAD): Executing the operation once yields the exact same server resource state as executing it multiple times ($f(f(x)) = f(x)$). For example, DELETE /orders/42 sets the status or deletes the record; subsequent calls yield resource not found or already deleted, but resource state remains deleted.
  • Non-Idempotent Methods (POST, PATCH in some contexts): Submitting repeated requests produces cumulative side effects (e.g. repeated POST /payments creates multiple charge records and bills the credit card multiple times). Applying distributed idempotency mechanisms converts non-idempotent operations into functionally idempotent operations.
Q2 How does an Idempotency Key architecture prevent double-charging in payment gateways like Stripe or Adyen?
▼

Answer:

When an end-user submits a payment checkout:

  1. The frontend or client generates an unguessable UUIDv4 or client-derived transaction token as the Idempotency-Key HTTP header.
  2. The payment gateway intercepts the request and verifies the key in an atomic fast-path datastore (e.g. PostgreSQL or Redis with SET NX EX).
  3. If the key exists in Processing state and lock is unexpired, the gateway returns HTTP 409 Conflict (or waits on a distributed promise/future), preventing concurrent race charges.
  4. If the key exists in Completed state, the stored receipt is returned without touching the card network rails.
  5. If the key is new, the gateway creates a Processing record, contacts Visa/Mastercard, records Completed with the transaction result, and returns HTTP 200/201.
Q3 Why is request payload hashing (SHA-256) critical when using client-supplied idempotency keys?
▼

Answer:

A client bug or malicious actor might reuse an idempotency key across different semantic operations (e.g., re-using key tx-001 originally used to purchase \$10 goods for a \$1,000 withdrawal). Without payload validation:

  • The system would treat the \$1,000 request as a duplicate replay of the \$10 request, returning the old cached response and ignoring the new intent, or vice-versa.

Computing a SHA-256 fingerprint over the method, URL path, and serialized request body allows the server to verify whether the incoming payload matches the original. If mismatched, the server rejects the request with HTTP 422 Unprocessable Entity or 400 Bad Request ("Idempotency key payload mismatch").

Q4 How do you handle distributed worker crashes when processing an idempotent request under a lease lock?
▼

Answer:

If a worker acquires a processing lock (Status = "Processing") and dies due to an OOM crash or unhandled SIGKILL, the key could remain permanently stuck. To solve this:

  1. Time-Bound Leases (TTL): Processing records include a LockedUntilUtc timestamp (e.g. DateTime.UtcNow.AddSeconds(30)).
  2. Heartbeating: For long operations, the worker periodically extends the lease.
  3. Automated Recovery: When another request arrives and finds Status == "Processing" but LockedUntilUtc < DateTime.UtcNow, it detects that the previous worker crashed. It atomically updates LockedUntilUtc to a new expiration and re-executes the operation safely.
Q5 How do you implement distributed idempotency in asynchronous message-driven architectures (e.g. RabbitMQ, Kafka)?
▼

Answer:

Message brokers deliver messages with at-least-once semantics. To ensure idempotency:

  1. Message Deduplication Table: The consumer inserts the incoming MessageId or domain deduplication key into a relational table within the same database transaction as the business state mutation.
  2. Outbox / Inbox Pattern: Use the transactional Inbox pattern. If the unique constraint on (ConsumerName, MessageId) throws a unique constraint violation, the message is recognized as duplicate and acknowledged (ack) immediately without re-executing domain actions.
  3. Natural Idempotency: Design message mutations to be commutative or state-based (UPDATE account SET balance = 500 WHERE account_id = 1 AND version = 2) rather than incremental delta-based (UPDATE account SET balance = balance + 100).
Q6 What are the trade-offs between Redis and a Relational Database (PostgreSQL) for storing idempotency state?
▼

Answer:

  • Redis:
  • Pros: Extremely high throughput (sub-millisecond latency), built-in TTL eviction, SETNX atomic primitives.
  • Cons: Memory capacity limits, potential data loss during cluster failover (asynchronous replication), lack of distributed two-phase commit across Redis and domain database.
  • Relational Database (PostgreSQL):
  • Pros: Full ACID compliance; the idempotency record can be inserted in the exact same database transaction as the entity updates, guaranteeing 100% consistency with zero dual-write vulnerabilities.
  • Cons: Higher storage overhead and latency; requires background cleanup jobs or table partitioning to purge expired records over time.
  • Best Practice: Use PostgreSQL for critical financial/ledger operations; use Redis for high-throughput, low-risk telemetry/notification rate-limiting.
Q7 In Quickselect, why is randomized pivot selection superior to deterministic pivot selection (e.g., choosing `nums[0]`)?
▼

Answer:

If a deterministic pivot selection (like picking nums[left] or nums[right]) is used on an already sorted or reverse-sorted array, each partition step only eliminates a single element ($N - 1$ remaining).

  • This degrades time complexity from the expected $O(N)$ to the worst-case $O(N^2)$, exceeding stack limits or timing out.
  • By selecting a pivot uniformly at random from [left, right], the probability of repeatedly choosing extremal elements becomes astronomically small, guaranteeing expected $O(N)$ runtime across all input distributions.
Q8 Compare Quickselect and Min-Heap for finding the Kth largest element in terms of streaming data and memory constraints.
▼

Answer:

  • Quickselect:
  • In-place algorithm ($O(1)$ space).
  • Requires the entire dataset to reside in random-access memory (RAM).
  • Mutates the original array in place. Cannot process streaming or unbounded data.
  • Min-Heap (PriorityQueue<TElement, TPriority>):
  • Operates on streaming/unbounded data where total count $N$ is unknown in advance.
  • Maintains a sliding window of the top $k$ elements in $O(K)$ auxiliary memory.
  • Time complexity is $O(N \log K)$. When $K \ll N$, this is practically linear and highly cache-efficient.
Q9 How should downstream API calls to third-party providers (e.g. Stripe, SendGrid) be coordinated within an idempotent workflow?
▼

Answer:

A dual-write problem exists: the internal DB transaction can commit, but the external API call might fail or time out, or vice versa.

  1. Generate a deterministic downstream idempotency key derived from the upstream key: downstreamKey = Hash(upstreamKey + "-stripe").
  2. Save the pending downstream intent before calling the third party.
  3. Pass downstreamKey in the external HTTP request header.
  4. If a network timeout occurs, retrying the operation with the same downstreamKey ensures the external provider does not duplicate the charge or email.
Q10 What is the optimal retention and cleanup policy for an idempotency store?
▼

Answer:

Indefinite retention causes unbound table growth. The retention window should match the maximum client retry window:

  • For user-facing web/mobile APIs, clients typically stop retrying after 24 to 72 hours.
  • A sliding TTL of 24–48 hours is standard.
  • Implementation: Use PostgreSQL partitioned tables (e.g., daily partitions dropped via pg_partman or cron DROP TABLE) or Redis key TTLs. Dropping partitions is an $O(1)$ catalog metadata operation with zero table bloat compared to costly DELETE FROM WHERE created_at < NOW() - INTERVAL '3 days'.

    public IdempotencyPayloadMismatchException(string message) : base(message) { }

public sealed record IdempotentResult(int StatusCode, string ResponseBody, bool FromCache = false);

public sealed class IdempotencyRecord
{
    public string IdempotencyKey { get; set; } = string.Empty;
    public string RequestPayloadHash { get; set; } = string.Empty;
    public string Status { get; set; } = "Processing"; // Processing, Completed, Failed
    public int? ResponseStatusCode { get; set; }
    public string? ResponseBody { get; set; }
    public DateTime CreatedAtUtc { get; set; } = DateTime.UtcNow;
    public DateTime? LockedUntilUtc { get; set; }
}

#endregion

#region DbContext

public class IdempotencyDbContext : DbContext
{
    public DbSet<IdempotencyRecord> IdempotencyRecords => Set<IdempotencyRecord>();

    public IdempotencyDbContext(DbContextOptions<IdempotencyDbContext> options) : base(options) { }

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        base.OnModelCreating(modelBuilder);
        modelBuilder.Entity<IdempotencyRecord>(b =>
        {
            b.HasKey(x => x.IdempotencyKey);
            b.Property(x => x.IdempotencyKey).IsRequired().HasMaxLength(128);
            b.Property(x => x.RequestPayloadHash).IsRequired().HasMaxLength(64);
            b.Property(x => x.Status).IsRequired().HasMaxLength(32);
        });
    }
}

#endregion

#region Idempotency Manager

public class IdempotencyManager
{
    private readonly IdempotencyDbContext _dbContext;

    public IdempotencyManager(IdempotencyDbContext dbContext)
    {
        _dbContext = dbContext;
    }

    public static string ComputeSha256(string input)
    {
        var bytes = SHA256.HashData(Encoding.UTF8.GetBytes(input ?? string.Empty));
        return Convert.ToHexString(bytes).ToLowerInvariant();
    }

    /// <summary>
    /// Executes an operation with full distributed idempotency semantics.
    /// Handles in-flight concurrency, payload verification, and cached response returns.
    /// </summary>
    public async Task<IdempotentResult> ExecuteAsync(
        string idempotencyKey,
        string requestPayload,
        Func<Task<IdempotentResult>> operation,
        TimeSpan? leaseDuration = null)
    {
        if (string.IsNullOrWhiteSpace(idempotencyKey))
        {
            return await operation();
        }

        var lease = leaseDuration ?? TimeSpan.FromSeconds(30);
        var payloadHash = ComputeSha256(requestPayload);
        var now = DateTime.UtcNow;

        var existing = await _dbContext.IdempotencyRecords
            .FirstOrDefaultAsync(r => r.IdempotencyKey == idempotencyKey);

        if (existing != null)
        {
            // 1. Verify payload integrity: same key cannot be used with different payload
            if (existing.RequestPayloadHash != payloadHash)
            {
                throw new IdempotencyPayloadMismatchException(
                    $"Idempotency key '{idempotencyKey}' was already used with a different request payload.");
            }

            // 2. If already completed, return cached response
            if (existing.Status == "Completed")
            {
                return new IdempotentResult(
                    existing.ResponseStatusCode ?? 200,
                    existing.ResponseBody ?? string.Empty,
                    FromCache: true
                );
            }

            // 3. If currently processing and lease has NOT expired, return 409 Conflict
            if (existing.Status == "Processing" && existing.LockedUntilUtc > now)
            {
                throw new IdempotencyConflictException(
                    $"A request with idempotency key '{idempotencyKey}' is currently in progress.");
            }

            // 4. Lease expired (prior worker crashed) -> re-lease
            existing.Status = "Processing";
            existing.LockedUntilUtc = now.Add(lease);
            await _dbContext.SaveChangesAsync();
        }
        else
        {
            // Atomically reserve in-flight state
            existing = new IdempotencyRecord
            {
                IdempotencyKey = idempotencyKey,
                RequestPayloadHash = payloadHash,
                Status = "Processing",
                CreatedAtUtc = now,
                LockedUntilUtc = now.Add(lease)
            };
            _dbContext.IdempotencyRecords.Add(existing);
            await _dbContext.SaveChangesAsync();
        }

        // Execute target business operation
        try
        {
            var result = await operation();

            existing.Status = "Completed";
            existing.ResponseStatusCode = result.StatusCode;
            existing.ResponseBody = result.ResponseBody;
            existing.LockedUntilUtc = null;

            await _dbContext.SaveChangesAsync();
            return result with { FromCache = false };
        }
        catch (Exception)
        {
            existing.Status = "Failed";
            existing.LockedUntilUtc = null;
            await _dbContext.SaveChangesAsync();
            throw;
        }
    }
}

namespace Day33.DistributedIdempotency;

public static class KthLargestSolver
{
    private static readonly Random _random = new();

    /// <summary>
    /// LeetCode #215: Kth Largest Element in an Array (Medium).
    /// Quickselect Algorithm (Hoare's selection algorithm) with randomized pivot.
    /// Average Time Complexity: O(N), Worst Case: O(N^2), Space Complexity: O(1) iterative.
    /// </summary>
    public static int FindKthLargestQuickselect(int[] nums, int k)
    {
        if (nums == null || nums.Length == 0 || k <= 0 || k > nums.Length)
            throw new ArgumentException("Invalid arguments for Quickselect");

        // The Kth largest element is at index (nums.Length - k) in sorted ascending order
        int targetIndex = nums.Length - k;
        int left = 0;
        int right = nums.Length - 1;

        while (left <= right)
        {
            int pivotIndex = Partition(nums, left, right);

            if (pivotIndex == targetIndex)
            {
                return nums[pivotIndex];
            }
            else if (pivotIndex < targetIndex)
            {
                left = pivotIndex + 1;
            }
            else
            {
                right = pivotIndex - 1;
            }
        }

        return nums[targetIndex];
    }

    private static int Partition(int[] nums, int left, int right)
    {
        // Randomized pivot to avoid worst-case O(N^2) on sorted/reverse-sorted inputs
        int randomIndex = _random.Next(left, right + 1);
        Swap(nums, randomIndex, right);

        int pivotValue = nums[right];
        int storeIndex = left;

        for (int i = left; i < right; i++)
        {
            if (nums[i] <= pivotValue)
            {
                Swap(nums, storeIndex, i);
                storeIndex++;
            }
        }

        Swap(nums, storeIndex, right);
        return storeIndex;
    }

    private static void Swap(int[] nums, int i, int j)
    {
        int temp = nums[i];
        nums[i] = nums[j];
        nums[j] = temp;
    }

    /// <summary>
    /// LeetCode #215: Kth Largest Element using a Min-Heap (PriorityQueue in .NET 6+).
    /// Time Complexity: O(N * log K), Space Complexity: O(K).
    /// </summary>
    public static int FindKthLargestMinHeap(int[] nums, int k)
    {
        if (nums == null || nums.Length == 0 || k <= 0 || k > nums.Length)
            throw new ArgumentException("Invalid arguments for Min-Heap");

        var minHeap = new PriorityQueue<int, int>();

        foreach (var num in nums)
        {
            minHeap.Enqueue(num, num);
            if (minHeap.Count > k)
            {
                minHeap.Dequeue();
            }
        }

        return minHeap.Peek();
    }
}

📝 Part 1: Deep-Dive Architectural & Engineering Notes

Deep Dive Notes: Distributed Idempotency & De-duplication

1. Idempotency Key Semantics in Distributed REST & Messaging

In high-concurrency microservices, idempotency guarantees that making the same request multiple times has the exact same side effects on system state as making it once:

$$f(f(x)) = f(x)$$

The IETF Idempotency-Key HTTP Header Specification

The IETF draft standard defines the Idempotency-Key header sent by HTTP clients. When processing:

  1. Fingerprint Validation: Compute a cryptographic digest (SHA-256) of the HTTP method, request path, and body. If a request arrives with an existing key but a different digest, the server MUST return HTTP 422 Unprocessable Entity or 400 Bad Request.
  2. Lock State: If the key is currently locked (processing) and the lock has not expired, return HTTP 409 Conflict with a Retry-After header.
  3. Completed State: If the key has completed, replay the exact response payload, headers, and status code (typically HTTP 200/201) along with an Idempotent-Replay: true header.

2. Distributed Storage & Lease Strategies

  • Relational DB with Unique Constraints:
  • INSERT INTO idempotency_keys (key, hash, status, locked_until) VALUES (...) ON CONFLICT DO NOTHING;
  • Guarantees ACID atomicity across application clusters.
  • Redis with Redlock or SET NX PX:
  • SET key:idempotency lock_token NX PX 30000
  • High throughput (sub-millisecond), but requires fallback or write-through persistence to a permanent store for long-lived cached results.
  • Worker Crash Handling & Lease Expiration:
  • Never hold a lock without a finite lease timeout (TTL). If node crashes mid-operation, the unreleased lock must expire after a configurable duration (e.g. 30–60s) allowing safe automated recovery.

3. LeetCode #215: Quickselect vs Min-Heap Analysis

  • Quickselect:
  • Partition array around a random pivot.
  • If pivot index equals target index $N - k$, return value.
  • If pivot index $< N - k$, recurse/iterate on the right subarray.
  • If pivot index $> N - k$, recurse/iterate on the left subarray.
  • Recurrence: $T(N) = T(N/2) + O(N) = O(N)$ average time.
  • Worst case: $O(N^2)$ if worst-case pivot selection occurs repeatedly, mitigated via randomized pivot.
  • Min-Heap:
  • Uses System.Collections.Generic.PriorityQueue<int, int> in .NET.
  • Push each element with value as priority. When size exceeds $k$, dequeue smallest element.
  • The heap retains the $k$ largest elements seen so far; top of heap is the $k$-th largest.
  • Time: $O(N \log K)$, Space: $O(K)$. Ideal for streaming data where total size $N$ is unknown or unbounded.

Day 33: Distributed Idempotency & De-duplication

Architectural Overview

In distributed systems, network partitions, client retries, and message broker at-least-once delivery guarantees inevitably produce duplicate requests. Without strict idempotency controls, duplicate submissions result in double-billing, corrupted inventory reserves, or inconsistent ledger entries.

This implementation demonstrates an enterprise-grade distributed idempotency pattern in .NET 8 / C# featuring:

  1. Idempotency Key Protocol: Clients supply a unique idempotency key (e.g., UUID or deterministic hash) via HTTP header or message metadata.
  2. Cryptographic Payload Verification: Computes a SHA-256 digest of the request payload to prevent payload tampering under an existing idempotency key. If payloads differ, an IdempotencyPayloadMismatchException (HTTP 422 Unprocessable Entity) is thrown.
  3. Optimistic Locking & Lease Management: Prevents race conditions during concurrent in-flight requests by reserving a lock with a lease expiration (LockedUntilUtc). If a second request arrives while the first is processing, it receives an IdempotencyConflictException (HTTP 409 Conflict).
  4. Crash Fault Recovery: If a worker node crashes mid-flight, subsequent requests after the lease window automatically reclaim the processing lock instead of deadlocking indefinitely.
  5. Response Caching: Successful responses are stored alongside their HTTP status codes and returned immediately with FromCache = true for subsequent idempotent replays.

💡 Part 3: Senior & Staff-Level Interview Scenarios (10 Questions)

Q1 What is the semantic difference between safe, idempotent, and non-idempotent HTTP methods according to RFC 9110?
▼

Answer:

  • Safe Methods (GET, HEAD, OPTIONS, TRACE): Do not modify server resource state. A client can execute them without expectation of mutation or side effects.
  • Idempotent Methods (PUT, DELETE, GET, HEAD): Executing the operation once yields the exact same server resource state as executing it multiple times ($f(f(x)) = f(x)$). For example, DELETE /orders/42 sets the status or deletes the record; subsequent calls yield resource not found or already deleted, but resource state remains deleted.
  • Non-Idempotent Methods (POST, PATCH in some contexts): Submitting repeated requests produces cumulative side effects (e.g. repeated POST /payments creates multiple charge records and bills the credit card multiple times). Applying distributed idempotency mechanisms converts non-idempotent operations into functionally idempotent operations.
Q2 How does an Idempotency Key architecture prevent double-charging in payment gateways like Stripe or Adyen?
▼

Answer:

When an end-user submits a payment checkout:

  1. The frontend or client generates an unguessable UUIDv4 or client-derived transaction token as the Idempotency-Key HTTP header.
  2. The payment gateway intercepts the request and verifies the key in an atomic fast-path datastore (e.g. PostgreSQL or Redis with SET NX EX).
  3. If the key exists in Processing state and lock is unexpired, the gateway returns HTTP 409 Conflict (or waits on a distributed promise/future), preventing concurrent race charges.
  4. If the key exists in Completed state, the stored receipt is returned without touching the card network rails.
  5. If the key is new, the gateway creates a Processing record, contacts Visa/Mastercard, records Completed with the transaction result, and returns HTTP 200/201.
Q3 Why is request payload hashing (SHA-256) critical when using client-supplied idempotency keys?
▼

Answer:

A client bug or malicious actor might reuse an idempotency key across different semantic operations (e.g., re-using key tx-001 originally used to purchase \$10 goods for a \$1,000 withdrawal). Without payload validation:

  • The system would treat the \$1,000 request as a duplicate replay of the \$10 request, returning the old cached response and ignoring the new intent, or vice-versa.

Computing a SHA-256 fingerprint over the method, URL path, and serialized request body allows the server to verify whether the incoming payload matches the original. If mismatched, the server rejects the request with HTTP 422 Unprocessable Entity or 400 Bad Request ("Idempotency key payload mismatch").

Q4 How do you handle distributed worker crashes when processing an idempotent request under a lease lock?
▼

Answer:

If a worker acquires a processing lock (Status = "Processing") and dies due to an OOM crash or unhandled SIGKILL, the key could remain permanently stuck. To solve this:

  1. Time-Bound Leases (TTL): Processing records include a LockedUntilUtc timestamp (e.g. DateTime.UtcNow.AddSeconds(30)).
  2. Heartbeating: For long operations, the worker periodically extends the lease.
  3. Automated Recovery: When another request arrives and finds Status == "Processing" but LockedUntilUtc < DateTime.UtcNow, it detects that the previous worker crashed. It atomically updates LockedUntilUtc to a new expiration and re-executes the operation safely.
Q5 How do you implement distributed idempotency in asynchronous message-driven architectures (e.g. RabbitMQ, Kafka)?
▼

Answer:

Message brokers deliver messages with at-least-once semantics. To ensure idempotency:

  1. Message Deduplication Table: The consumer inserts the incoming MessageId or domain deduplication key into a relational table within the same database transaction as the business state mutation.
  2. Outbox / Inbox Pattern: Use the transactional Inbox pattern. If the unique constraint on (ConsumerName, MessageId) throws a unique constraint violation, the message is recognized as duplicate and acknowledged (ack) immediately without re-executing domain actions.
  3. Natural Idempotency: Design message mutations to be commutative or state-based (UPDATE account SET balance = 500 WHERE account_id = 1 AND version = 2) rather than incremental delta-based (UPDATE account SET balance = balance + 100).
Q6 What are the trade-offs between Redis and a Relational Database (PostgreSQL) for storing idempotency state?
▼

Answer:

  • Redis:
  • Pros: Extremely high throughput (sub-millisecond latency), built-in TTL eviction, SETNX atomic primitives.
  • Cons: Memory capacity limits, potential data loss during cluster failover (asynchronous replication), lack of distributed two-phase commit across Redis and domain database.
  • Relational Database (PostgreSQL):
  • Pros: Full ACID compliance; the idempotency record can be inserted in the exact same database transaction as the entity updates, guaranteeing 100% consistency with zero dual-write vulnerabilities.
  • Cons: Higher storage overhead and latency; requires background cleanup jobs or table partitioning to purge expired records over time.
  • Best Practice: Use PostgreSQL for critical financial/ledger operations; use Redis for high-throughput, low-risk telemetry/notification rate-limiting.
Q7 In Quickselect, why is randomized pivot selection superior to deterministic pivot selection (e.g., choosing `nums[0]`)?
▼

Answer:

If a deterministic pivot selection (like picking nums[left] or nums[right]) is used on an already sorted or reverse-sorted array, each partition step only eliminates a single element ($N - 1$ remaining).

  • This degrades time complexity from the expected $O(N)$ to the worst-case $O(N^2)$, exceeding stack limits or timing out.
  • By selecting a pivot uniformly at random from [left, right], the probability of repeatedly choosing extremal elements becomes astronomically small, guaranteeing expected $O(N)$ runtime across all input distributions.
Q8 Compare Quickselect and Min-Heap for finding the Kth largest element in terms of streaming data and memory constraints.
▼

Answer:

  • Quickselect:
  • In-place algorithm ($O(1)$ space).
  • Requires the entire dataset to reside in random-access memory (RAM).
  • Mutates the original array in place. Cannot process streaming or unbounded data.
  • Min-Heap (PriorityQueue<TElement, TPriority>):
  • Operates on streaming/unbounded data where total count $N$ is unknown in advance.
  • Maintains a sliding window of the top $k$ elements in $O(K)$ auxiliary memory.
  • Time complexity is $O(N \log K)$. When $K \ll N$, this is practically linear and highly cache-efficient.
Q9 How should downstream API calls to third-party providers (e.g. Stripe, SendGrid) be coordinated within an idempotent workflow?
▼

Answer:

A dual-write problem exists: the internal DB transaction can commit, but the external API call might fail or time out, or vice versa.

  1. Generate a deterministic downstream idempotency key derived from the upstream key: downstreamKey = Hash(upstreamKey + "-stripe").
  2. Save the pending downstream intent before calling the third party.
  3. Pass downstreamKey in the external HTTP request header.
  4. If a network timeout occurs, retrying the operation with the same downstreamKey ensures the external provider does not duplicate the charge or email.
Q10 What is the optimal retention and cleanup policy for an idempotency store?
▼

Answer:

Indefinite retention causes unbound table growth. The retention window should match the maximum client retry window:

  • For user-facing web/mobile APIs, clients typically stop retrying after 24 to 72 hours.
  • A sliding TTL of 24–48 hours is standard.
  • Implementation: Use PostgreSQL partitioned tables (e.g., daily partitions dropped via pg_partman or cron DROP TABLE) or Redis key TTLs. Dropping partitions is an $O(1)$ catalog metadata operation with zero table bloat compared to costly DELETE FROM WHERE created_at < NOW() - INTERVAL '3 days'.

public class IdempotencyManager
{
    private readonly IdempotencyDbContext _dbContext;

    public IdempotencyManager(IdempotencyDbContext dbContext)
    {
        _dbContext = dbContext;
    }

    public static string ComputeSha256(string input)
    {
        var bytes = SHA256.HashData(Encoding.UTF8.GetBytes(input ?? string.Empty));
        return Convert.ToHexString(bytes).ToLowerInvariant();
    }

    /// <summary>
    /// Executes an operation with full distributed idempotency semantics.
    /// Handles in-flight concurrency, payload verification, and cached response returns.
    /// </summary>
    public async Task<IdempotentResult> ExecuteAsync(
        string idempotencyKey,
        string requestPayload,
        Func<Task<IdempotentResult>> operation,
        TimeSpan? leaseDuration = null)
    {
        if (string.IsNullOrWhiteSpace(idempotencyKey))
        {
            return await operation();
        }

        var lease = leaseDuration ?? TimeSpan.FromSeconds(30);
        var payloadHash = ComputeSha256(requestPayload);
        var now = DateTime.UtcNow;

        var existing = await _dbContext.IdempotencyRecords
            .FirstOrDefaultAsync(r => r.IdempotencyKey == idempotencyKey);

        if (existing != null)
        {
            // 1. Verify payload integrity: same key cannot be used with different payload
            if (existing.RequestPayloadHash != payloadHash)
            {
                throw new IdempotencyPayloadMismatchException(
                    $"Idempotency key '{idempotencyKey}' was already used with a different request payload.");
            }

            // 2. If already completed, return cached response
            if (existing.Status == "Completed")
            {
                return new IdempotentResult(
                    existing.ResponseStatusCode ?? 200,
                    existing.ResponseBody ?? string.Empty,
                    FromCache: true
                );
            }

            // 3. If currently processing and lease has NOT expired, return 409 Conflict
            if (existing.Status == "Processing" && existing.LockedUntilUtc > now)
            {
                throw new IdempotencyConflictException(
                    $"A request with idempotency key '{idempotencyKey}' is currently in progress.");
            }

            // 4. Lease expired (prior worker crashed) -> re-lease
            existing.Status = "Processing";
            existing.LockedUntilUtc = now.Add(lease);
            await _dbContext.SaveChangesAsync();
        }
        else
        {
            // Atomically reserve in-flight state
            existing = new IdempotencyRecord
            {
                IdempotencyKey = idempotencyKey,
                RequestPayloadHash = payloadHash,
                Status = "Processing",
                CreatedAtUtc = now,
                LockedUntilUtc = now.Add(lease)
            };
            _dbContext.IdempotencyRecords.Add(existing);
            await _dbContext.SaveChangesAsync();
        }

        // Execute target business operation
        try
        {
            var result = await operation();

            existing.Status = "Completed";
            existing.ResponseStatusCode = result.StatusCode;
            existing.ResponseBody = result.ResponseBody;
            existing.LockedUntilUtc = null;

            await _dbContext.SaveChangesAsync();
            return result with { FromCache = false };
        }
        catch (Exception)
        {
            existing.Status = "Failed";
            existing.LockedUntilUtc = null;
            await _dbContext.SaveChangesAsync();
            throw;
        }
    }
}

namespace Day33.DistributedIdempotency;

public static class KthLargestSolver
{
    private static readonly Random _random = new();

    /// <summary>
    /// LeetCode #215: Kth Largest Element in an Array (Medium).
    /// Quickselect Algorithm (Hoare's selection algorithm) with randomized pivot.
    /// Average Time Complexity: O(N), Worst Case: O(N^2), Space Complexity: O(1) iterative.
    /// </summary>
    public static int FindKthLargestQuickselect(int[] nums, int k)
    {
        if (nums == null || nums.Length == 0 || k <= 0 || k > nums.Length)
            throw new ArgumentException("Invalid arguments for Quickselect");

        // The Kth largest element is at index (nums.Length - k) in sorted ascending order
        int targetIndex = nums.Length - k;
        int left = 0;
        int right = nums.Length - 1;

        while (left <= right)
        {
            int pivotIndex = Partition(nums, left, right);

            if (pivotIndex == targetIndex)
            {
                return nums[pivotIndex];
            }
            else if (pivotIndex < targetIndex)
            {
                left = pivotIndex + 1;
            }
            else
            {
                right = pivotIndex - 1;
            }
        }

        return nums[targetIndex];
    }

    private static int Partition(int[] nums, int left, int right)
    {
        // Randomized pivot to avoid worst-case O(N^2) on sorted/reverse-sorted inputs
        int randomIndex = _random.Next(left, right + 1);
        Swap(nums, randomIndex, right);

        int pivotValue = nums[right];
        int storeIndex = left;

        for (int i = left; i < right; i++)
        {
            if (nums[i] <= pivotValue)
            {
                Swap(nums, storeIndex, i);
                storeIndex++;
            }
        }

        Swap(nums, storeIndex, right);
        return storeIndex;
    }

    private static void Swap(int[] nums, int i, int j)
    {
        int temp = nums[i];
        nums[i] = nums[j];
        nums[j] = temp;
    }

    /// <summary>
    /// LeetCode #215: Kth Largest Element using a Min-Heap (PriorityQueue in .NET 6+).
    /// Time Complexity: O(N * log K), Space Complexity: O(K).
    /// </summary>
    public static int FindKthLargestMinHeap(int[] nums, int k)
    {
        if (nums == null || nums.Length == 0 || k <= 0 || k > nums.Length)
            throw new ArgumentException("Invalid arguments for Min-Heap");

        var minHeap = new PriorityQueue<int, int>();

        foreach (var num in nums)
        {
            minHeap.Enqueue(num, num);
            if (minHeap.Count > k)
            {
                minHeap.Dequeue();
            }
        }

        return minHeap.Peek();
    }
}
