Deep Dive Notes: Observability Stack & Metric Architectures

1. RED vs USE Methodologies

  • RED Method (Tom Wilkie):
  • Focused on Services (Request-driven architectures, HTTP / gRPC).
  • Rate: Number of requests per second.
  • Errors: Number of failing requests per second.
  • Duration: Distribution of time taken by requests.
  • USE Method (Brendan Gregg):
  • Focused on Resources (Hardware, OS, CPUs, Disks, Network interfaces, ThreadPools).
  • Utilization: The average time that the resource was busy servicing work (e.g., 85% CPU).
  • Saturation: The degree to which extra work is queued waiting for the resource (e.g., Run Queue length > Core count).
  • Errors: Count of error events (e.g., dropped packets, disk drive I/O retries).

2. Percentiles & Histogram Quantile Math

Averages (means) are dangerously misleading in distributed systems due to multimodal distributions and long tail latency.

  • If 99 requests take 10ms and 1 request takes 1,000ms:
  • Mean = 19.9ms (looks healthy).
  • P99 = 1,000ms (unacceptable 1-second delay for 1 in 100 users).
  • Nearest-Rank Percentile Formula:

$$\text{Rank} = \frac{P}{100} \times (N - 1)$$

Linear interpolation between $\lfloor \text{Rank} \rfloor$ and $\lceil \text{Rank} \rceil$ provides accurate tail latency curves.

  • In Prometheus, histogram_quantile(0.99, sum(rate(http_duration_bucket[5m])) by (le)) uses linear interpolation across pre-aggregated exponential or explicit bucket bounds.

3. LeetCode #355: Fan-out on Read vs Fan-out on Write

  • Fan-out on Read (Pull):
  • Tweets are stored per user. When generating a feed, query all followees and perform a $k$-way merge using a min/max-heap.
  • Pros: Instant $O(1)$ post tweet; inactive users consume zero background compute.
  • Cons: Heavy read latency when following hundreds of users ($O(F \log F)$).
  • Fan-out on Write (Push):
  • When a user tweets, push the tweet ID into the Redis timeline cache of every follower.
  • Pros: Extremely fast $O(1)$ feed reads.
  • Cons: "Celebrity problem" — a user with 50 million followers triggers 50 million Redis writes per tweet!
  • Hybrid Production Architecture (Twitter / X):
  • Normal users: Fan-out on write (push to followers).
  • Celebrities (>25k followers): Fan-out on read (merged dynamically into the feed at read time).

10 Senior / Staff-Level Interview Questions with In-Depth Answers:
Q1 Why are averages (means) considered an antipattern for monitoring service latencies, and why are percentiles (P95, P99) preferred?
▼

Answer:

Averages conceal outliers in skewed distributions. A microservice handling 10,000 req/sec might have an average latency of 25ms, while the 99th percentile is 3,500ms. In modern web architectures where an incoming user request fan-outs to 50 downstream microservices:

$$\text{Probability of hitting a P99 dependency} = 1 - (0.99)^{50} \approx 39.5\%$$

Nearly 40% of all user requests will experience a P99 tail latency! Relying on percentiles like P90, P95, and P99 guarantees SLA observability for the users experiencing degraded performance.

Q2 What is the mathematical and architectural difference between RED and USE metrics?
▼

Answer:

  • RED (Rate, Errors, Duration): Formulated for request-driven software services (HTTP APIs, gRPC, microservices). It measures what the user/consumer experiences. Rate = load; Errors = availability; Duration = responsiveness.
  • USE (Utilization, Saturation, Errors): Formulated for hardware and infrastructure resources (CPU, RAM, disk I/O, network sockets, thread pools). Utilization = percent busy time; Saturation = queued backlog waiting to be serviced; Errors = low-level driver or device faults.
  • Rule of thumb: When investigating an alert, look at RED metrics to identify which service is degraded, then look at USE metrics to identify which resource bottleneck is causing it.
Q3 How does Prometheus calculate `histogram_quantile(0.99, ...)` from discrete histogram buckets?
▼

Answer:

Prometheus histograms record cumulative counts in pre-defined buckets (le = less than or equal to).

  1. Prometheus aggregates the bucket counters across the specified time window via rate().
  2. It identifies the target rank: $0.99 \times \text{Total Count}$.
  3. It finds the specific bucket $[le_1, le_2]$ that contains this rank.
  4. It performs linear interpolation within that bucket assuming uniform distribution of observations between $le_1$ and $le_2$.
  • Implication: If bucket boundaries are poorly spaced (e.g. jumping from 100ms to 5,000ms), the computed percentile will be an imprecise mathematical approximation.
Q4 What is an OpenTelemetry Exemplar and how does it bridge Metrics and Traces?
▼

Answer:

An Exemplar is an exact trace ID and span ID attached to a specific metric measurement observation in a histogram bucket.

  • When an unusually slow request of 2,400ms is recorded into the [1000, 5000] bucket, OpenTelemetry attaches trace_id = "abc123xyz" to that histogram sample.
  • In Grafana, when viewing a spike in P99 latency, clicking on the data point displays the linked Exemplar. Clicking it instantly opens the exact trace in Jaeger, eliminating manual searching through millions of log lines.
Q5 In `System.Diagnostics.Metrics`, what is the difference between `Counter<T>`, `Histogram<T>`, and `ObservableGauge<T>`?
▼

Answer:

  • Counter<T>: Monotonically increasing value (only positive deltas, e.g. requests processed, bytes received). Cannot decrease.
  • Histogram<T>: Measures distributions of values (e.g. durations, payload sizes). The SDK aggregates these into statistical buckets, counts, and sums.
  • ObservableGauge<T>: Asynchronous callback-based metric polled by the SDK at scraping intervals. Used for instantaneous values that fluctuate up and down (e.g. CPU percentage, current memory in use, queue length).
Q6 How do you design an observability pipeline to prevent metric cardinality explosion?
▼

Answer:

High cardinality occurs when metric tags have unbounded unique values (e.g., user_id, order_id, email, timestamp).

  • Storing 1,000,000 distinct user_id tags multiplies time series in Prometheus TSDB memory exponentially, leading to an OOM crash.
  • Rules:
  1. Only use discrete, bounded enums for metric tags: http.method, http.status_code, http.route (templated /orders/{id}, never raw /orders/12345).
  2. Put high-cardinality identifiers (order_id, user_id) in Traces (Spans) and Logs, where columnar databases (Loki, ClickHouse, Jaeger) handle high cardinality efficiently.
Q7 Explain the trade-offs between "Push" (OTLP/StatsD) vs "Pull" (Prometheus scraping) metric architectures.
▼

Answer:

  • Pull (Prometheus):
  • Prometheus periodically scrapes /metrics HTTP endpoints.
  • Pros: Centralized rate control (scraping cannot overwhelm the server); easy liveness detection (if scrape fails, service is down); no state in client services.
  • Cons: Difficult to scrape short-lived ephemeral batch jobs or serverless functions (requires Pushgateway); complex firewall traversal across VPCs.
  • Push (OTLP to OTel Collector):
  • Applications push telemetry batches to a local collector daemon.
  • Pros: Uniform across metrics, traces, and logs; supports serverless/lambda environments; easy NAT/firewall egress.
  • Cons: Risk of overwhelming downstream telemetry backends during traffic bursts if collector queues overflow.
Q8 In LeetCode #355 (Design Twitter), how does the $K$-way merge algorithm operate for `GetNewsFeed`?
▼

Answer:

Each user has a chronologically sorted list of their own tweets.

  1. When generating the feed for user $U$, identify all followed users $F_1, F_2, \dots, F_k$ plus $U$.
  2. For each user who has posted at least one tweet, enqueue their most recent tweet into a Max-Heap along with their user ID and tweet index. The heap size is at most $|F| + 1$.
  3. Dequeue the root tweet (the globally newest across all feeds) and add to the result feed.
  4. Advance that user's index to their next newest tweet and enqueue it into the heap.
  5. Repeat until 10 tweets have been harvested or the heap is empty.
  • Time Complexity: $O(F \log F + 10 \log F) = O(F \log F)$.
Q9 How would you scale the Twitter news feed system for a celebrity with 100 million followers?
▼

Answer:

Using pure Fan-out on Write would require inserting 100,000,000 timeline entries into Redis whenever the celebrity tweets, causing massive write amplification and lag.

  • Solution (Hybrid Fan-out):
  1. Categorize users into standard users and celebrities (e.g. followers $> 50,000$).
  2. For standard users: Fan-out on Write to follower timeline caches.
  3. For celebrities: Do not fan out on write. Instead, when a follower opens their feed, do a fast parallel fetch of the recent tweets from celebrities they follow and dynamically merge them (fan-out on read) with their pre-computed inbox timeline in RAM.
Q10 How does OpenTelemetry Collector act as a pipeline buffer and aggregator in enterprise deployments?
▼

Answer:

Rather than having hundreds of microservice pods directly connect to Prometheus, Jaeger, and Datadog:

  1. Microservices send OTLP over localhost/mesh to an OTel Collector agent or daemonset.
  2. The Collector pipeline has three stages:
  • Receivers: Accept OTLP (gRPC/HTTP), Zipkin, Jaeger.
  • Processors: memory_limiter, batch (coalesce into bulk network requests), filter (drop unwanted metrics), and tail_sampling (keep only slow or failed traces).
  • Exporters: Fan out identical telemetry data to multiple targets simultaneously (e.g., Prometheus for metrics, Jaeger for tracing, AWS CloudWatch for auditing).

using System.Diagnostics;
using System.Diagnostics.Metrics;

namespace Day35.ObservabilityStack;

public record LatencyPercentiles(double P50, double P90, double P95, double P99, int TotalCount, double Mean);

public record HistogramBucket(double UpperBound, int CumulativeCount);

public class ObservabilityMetricsManager : IDisposable
{
    public const string MeterName = "Day35.ObservabilityStack";
    public const string Version = "1.0.0";
    public static readonly Meter Meter = new(MeterName, Version);

    // RED Metrics
    public readonly Counter<long> RequestCounter;
    public readonly Counter<long> ErrorCounter;
    public readonly Histogram<double> RequestDurationHistogram;

    // USE Metrics
    public double SimulatedCpuUtilization { get; set; } = 42.5;
    public long SimulatedThreadPoolQueueLength { get; set; } = 12;
    public readonly Counter<long> HardwareErrorCounter;

    private readonly MeterListener _listener;
    private readonly List<double> _observedDurations = new();
    private long _totalRequests = 0;
    private long _totalErrors = 0;
    private readonly object _lock = new();

    public long TotalRequests => Interlocked.Read(ref _totalRequests);
    public long TotalErrors => Interlocked.Read(ref _totalErrors);
    public IReadOnlyList<double> ObservedDurations
    {
        get
        {
            lock (_lock) return _observedDurations.ToList();
        }
    }

    public ObservabilityMetricsManager()
    {
        RequestCounter = Meter.CreateCounter<long>("http.server.requests.count", "requests", "Total incoming HTTP requests");
        ErrorCounter = Meter.CreateCounter<long>("http.server.requests.errors", "errors", "Total HTTP requests resulting in 5xx errors");
        RequestDurationHistogram = Meter.CreateHistogram<double>("http.server.request.duration.ms", "ms", "HTTP request processing duration in milliseconds");

        Meter.CreateObservableGauge("system.cpu.utilization", () => SimulatedCpuUtilization, "%", "Simulated CPU Utilization");
        Meter.CreateObservableGauge("threadpool.queue.saturation", () => SimulatedThreadPoolQueueLength, "items", "ThreadPool queued work items");
        HardwareErrorCounter = Meter.CreateCounter<long>("system.hardware.errors", "errors", "Hardware / disk / network drop errors");

        _listener = new MeterListener
        {
            InstrumentPublished = (instrument, listener) =>
            {
                if (instrument.Meter.Name == MeterName)
                {
                    listener.EnableMeasurementEvents(instrument);
                }
            }
        };

        _listener.SetMeasurementEventCallback<long>((instrument, measurement, tags, state) =>
        {
            if (instrument.Name == "http.server.requests.count")
            {
                Interlocked.Add(ref _totalRequests, measurement);
            }
            else if (instrument.Name == "http.server.requests.errors")
            {
                Interlocked.Add(ref _totalErrors, measurement);
            }
        });

        _listener.SetMeasurementEventCallback<double>((instrument, measurement, tags, state) =>
        {
            if (instrument.Name == "http.server.request.duration.ms")
            {
                lock (_lock)
                {
                    _observedDurations.Add(measurement);
                }
            }
        });

        _listener.Start();
    }

    public void RecordRequest(double durationMs, bool isError = false, string route = "/api/v1/resource", int statusCode = 200)
    {
        var tagList = new TagList
        {
            { "http.route", route },
            { "http.status_code", statusCode }
        };

        RequestCounter.Add(1, tagList);
        RequestDurationHistogram.Record(durationMs, tagList);

        if (isError)
        {
            ErrorCounter.Add(1, tagList);
        }
    }

    /// <summary>
    /// Computes P50, P90, P95, P99 percentiles from a collection of recorded latencies.
    /// Uses the standard Nearest-Rank percentile method.
    /// </summary>
    public static LatencyPercentiles CalculatePercentiles(IEnumerable<double> latencies)
    {
        var list = latencies.OrderBy(x => x).ToList();
        if (list.Count == 0)
        {
            return new LatencyPercentiles(0, 0, 0, 0, 0, 0);
        }

        double p50 = GetPercentile(list, 50);
        double p90 = GetPercentile(list, 90);
        double p95 = GetPercentile(list, 95);
        double p99 = GetPercentile(list, 99);
        double mean = list.Average();

        return new LatencyPercentiles(p50, p90, p95, p99, list.Count, Math.Round(mean, 2));
    }

    private static double GetPercentile(List<double> sorted, double percentile)
    {
        if (sorted.Count == 1) return sorted[0];
        double rank = (percentile / 100.0) * (sorted.Count - 1);
        int lower = (int)Math.Floor(rank);
        int upper = (int)Math.Ceiling(rank);
        if (lower == upper) return sorted[lower];
        double weight = rank - lower;
        return Math.Round(sorted[lower] * (1 - weight) + sorted[upper] * weight, 2);
    }

    /// <summary>
    /// Simulates Prometheus-style cumulative histogram buckets.
    /// Standard Prometheus boundaries: 5ms, 10ms, 25ms, 50ms, 100ms, 250ms, 500ms, 1000ms, +Inf.
    /// </summary>
    public static List<HistogramBucket> BuildPrometheusBuckets(IEnumerable<double> latencies, double[]? boundaries = null)
    {
        boundaries ??= [5.0, 10.0, 25.0, 50.0, 100.0, 250.0, 500.0, 1000.0, double.PositiveInfinity];
        var list = latencies.ToList();
        var buckets = new List<HistogramBucket>();

        foreach (var boundary in boundaries)
        {
            int count = list.Count(v => v <= boundary);
            buckets.Add(new HistogramBucket(boundary, count));
        }

        return buckets;
    }

    /// <summary>
    /// Correlates telemetry by generating structured log payloads with trace_id and span_id.
    /// </summary>
    public static string FormatStructuredLog(string message, string traceId, string spanId, string logLevel = "Information")
    {
        return $"{{\"timestamp\":\"{DateTime.UtcNow:O}\",\"level\":\"{logLevel}\",\"trace_id\":\"{traceId}\",\"span_id\":\"{spanId}\",\"message\":\"{message}\"}}";
    }

    public void Dispose()
    {
        _listener.Dispose();
    }
}

namespace Day35.ObservabilityStack;

public class TwitterFeedSolver
{
    private static int _globalTimestamp = 0;

    public record Tweet(int TweetId, int Timestamp);

    private readonly Dictionary<int, List<Tweet>> _userTweets = new();
    private readonly Dictionary<int, HashSet<int>> _following = new();

    public TwitterFeedSolver()
    {
    }

    /// <summary>
    /// Composes a new tweet with ID tweetId by the user userId.
    /// Time Complexity: O(1).
    /// </summary>
    public void PostTweet(int userId, int tweetId)
    {
        if (!_userTweets.ContainsKey(userId))
        {
            _userTweets[userId] = new List<Tweet>();
        }

        var timestamp = Interlocked.Increment(ref _globalTimestamp);
        _userTweets[userId].Add(new Tweet(tweetId, timestamp));
    }

    /// <summary>
    /// Retrieves the 10 most recent tweet IDs in the user's news feed (from self and followees).
    /// Ordered from most recent to least recent.
    /// Uses Max-Heap (k-way merge) over sorted tweet lists.
    /// Time Complexity: O(F * log F + 10 * log F) where F = number of followees, Space: O(F).
    /// </summary>
    public IList<int> GetNewsFeed(int userId)
    {
        var result = new List<int>(10);

        // Gather all users contributing to this user's feed: self + followed users
        var relevantUsers = new HashSet<int> { userId };
        if (_following.TryGetValue(userId, out var followees))
        {
            foreach (var f in followees)
            {
                relevantUsers.Add(f);
            }
        }

        // Max-heap of (Tweet, user, indexInUserList).
        // PriorityQueue in .NET is min-heap by default, so use -timestamp as priority for max-heap behavior.
        var maxHeap = new PriorityQueue<(Tweet Tweet, int UserId, int Index), int>();

        foreach (var u in relevantUsers)
        {
            if (_userTweets.TryGetValue(u, out var tweets) && tweets.Count > 0)
            {
                int lastIdx = tweets.Count - 1;
                var latestTweet = tweets[lastIdx];
                maxHeap.Enqueue((latestTweet, u, lastIdx), -latestTweet.Timestamp);
            }
        }

        while (maxHeap.Count > 0 && result.Count < 10)
        {
            var (tweet, u, idx) = maxHeap.Dequeue();
            result.Add(tweet.TweetId);

            int nextIdx = idx - 1;
            if (nextIdx >= 0)
            {
                var nextTweet = _userTweets[u][nextIdx];
                maxHeap.Enqueue((nextTweet, u, nextIdx), -nextTweet.Timestamp);
            }
        }

        return result;
    }

    /// <summary>
    /// Follower starts following followee.
    /// A user cannot follow themselves.
    /// </summary>
    public void Follow(int followerId, int followeeId)
    {
        if (followerId == followeeId) return;

        if (!_following.ContainsKey(followerId))
        {
            _following[followerId] = new HashSet<int>();
        }

        _following[followerId].Add(followeeId);
    }

    /// <summary>
    /// Follower unfollows followee.
    /// </summary>
    public void Unfollow(int followerId, int followeeId)
    {
        if (followerId == followeeId) return;

        if (_following.TryGetValue(followerId, out var followees))
        {
            followees.Remove(followeeId);
        }
    }
}

📝 Part 1: Deep-Dive Architectural & Engineering Notes

Deep Dive Notes: Observability Stack & Metric Architectures

1. RED vs USE Methodologies

  • RED Method (Tom Wilkie):
  • Focused on Services (Request-driven architectures, HTTP / gRPC).
  • Rate: Number of requests per second.
  • Errors: Number of failing requests per second.
  • Duration: Distribution of time taken by requests.
  • USE Method (Brendan Gregg):
  • Focused on Resources (Hardware, OS, CPUs, Disks, Network interfaces, ThreadPools).
  • Utilization: The average time that the resource was busy servicing work (e.g., 85% CPU).
  • Saturation: The degree to which extra work is queued waiting for the resource (e.g., Run Queue length > Core count).
  • Errors: Count of error events (e.g., dropped packets, disk drive I/O retries).

2. Percentiles & Histogram Quantile Math

Averages (means) are dangerously misleading in distributed systems due to multimodal distributions and long tail latency.

  • If 99 requests take 10ms and 1 request takes 1,000ms:
  • Mean = 19.9ms (looks healthy).
  • P99 = 1,000ms (unacceptable 1-second delay for 1 in 100 users).
  • Nearest-Rank Percentile Formula:

$$\text{Rank} = \frac{P}{100} \times (N - 1)$$

Linear interpolation between $\lfloor \text{Rank} \rfloor$ and $\lceil \text{Rank} \rceil$ provides accurate tail latency curves.

  • In Prometheus, histogram_quantile(0.99, sum(rate(http_duration_bucket[5m])) by (le)) uses linear interpolation across pre-aggregated exponential or explicit bucket bounds.

3. LeetCode #355: Fan-out on Read vs Fan-out on Write

  • Fan-out on Read (Pull):
  • Tweets are stored per user. When generating a feed, query all followees and perform a $k$-way merge using a min/max-heap.
  • Pros: Instant $O(1)$ post tweet; inactive users consume zero background compute.
  • Cons: Heavy read latency when following hundreds of users ($O(F \log F)$).
  • Fan-out on Write (Push):
  • When a user tweets, push the tweet ID into the Redis timeline cache of every follower.
  • Pros: Extremely fast $O(1)$ feed reads.
  • Cons: "Celebrity problem" — a user with 50 million followers triggers 50 million Redis writes per tweet!
  • Hybrid Production Architecture (Twitter / X):
  • Normal users: Fan-out on write (push to followers).
  • Celebrities (>25k followers): Fan-out on read (merged dynamically into the feed at read time).

💡 Part 3: Senior & Staff-Level Interview Scenarios (10 Questions)

Q1 Why are averages (means) considered an antipattern for monitoring service latencies, and why are percentiles (P95, P99) preferred?
▼

Answer:

Averages conceal outliers in skewed distributions. A microservice handling 10,000 req/sec might have an average latency of 25ms, while the 99th percentile is 3,500ms. In modern web architectures where an incoming user request fan-outs to 50 downstream microservices:

$$\text{Probability of hitting a P99 dependency} = 1 - (0.99)^{50} \approx 39.5\%$$

Nearly 40% of all user requests will experience a P99 tail latency! Relying on percentiles like P90, P95, and P99 guarantees SLA observability for the users experiencing degraded performance.

Q2 What is the mathematical and architectural difference between RED and USE metrics?
▼

Answer:

  • RED (Rate, Errors, Duration): Formulated for request-driven software services (HTTP APIs, gRPC, microservices). It measures what the user/consumer experiences. Rate = load; Errors = availability; Duration = responsiveness.
  • USE (Utilization, Saturation, Errors): Formulated for hardware and infrastructure resources (CPU, RAM, disk I/O, network sockets, thread pools). Utilization = percent busy time; Saturation = queued backlog waiting to be serviced; Errors = low-level driver or device faults.
  • Rule of thumb: When investigating an alert, look at RED metrics to identify which service is degraded, then look at USE metrics to identify which resource bottleneck is causing it.
Q3 How does Prometheus calculate `histogram_quantile(0.99, ...)` from discrete histogram buckets?
▼

Answer:

Prometheus histograms record cumulative counts in pre-defined buckets (le = less than or equal to).

  1. Prometheus aggregates the bucket counters across the specified time window via rate().
  2. It identifies the target rank: $0.99 \times \text{Total Count}$.
  3. It finds the specific bucket $[le_1, le_2]$ that contains this rank.
  4. It performs linear interpolation within that bucket assuming uniform distribution of observations between $le_1$ and $le_2$.
  • Implication: If bucket boundaries are poorly spaced (e.g. jumping from 100ms to 5,000ms), the computed percentile will be an imprecise mathematical approximation.
Q4 What is an OpenTelemetry Exemplar and how does it bridge Metrics and Traces?
▼

Answer:

An Exemplar is an exact trace ID and span ID attached to a specific metric measurement observation in a histogram bucket.

  • When an unusually slow request of 2,400ms is recorded into the [1000, 5000] bucket, OpenTelemetry attaches trace_id = "abc123xyz" to that histogram sample.
  • In Grafana, when viewing a spike in P99 latency, clicking on the data point displays the linked Exemplar. Clicking it instantly opens the exact trace in Jaeger, eliminating manual searching through millions of log lines.
Q5 In `System.Diagnostics.Metrics`, what is the difference between `Counter<T>`, `Histogram<T>`, and `ObservableGauge<T>`?
▼

Answer:

  • Counter<T>: Monotonically increasing value (only positive deltas, e.g. requests processed, bytes received). Cannot decrease.
  • Histogram<T>: Measures distributions of values (e.g. durations, payload sizes). The SDK aggregates these into statistical buckets, counts, and sums.
  • ObservableGauge<T>: Asynchronous callback-based metric polled by the SDK at scraping intervals. Used for instantaneous values that fluctuate up and down (e.g. CPU percentage, current memory in use, queue length).
Q6 How do you design an observability pipeline to prevent metric cardinality explosion?
▼

Answer:

High cardinality occurs when metric tags have unbounded unique values (e.g., user_id, order_id, email, timestamp).

  • Storing 1,000,000 distinct user_id tags multiplies time series in Prometheus TSDB memory exponentially, leading to an OOM crash.
  • Rules:
  1. Only use discrete, bounded enums for metric tags: http.method, http.status_code, http.route (templated /orders/{id}, never raw /orders/12345).
  2. Put high-cardinality identifiers (order_id, user_id) in Traces (Spans) and Logs, where columnar databases (Loki, ClickHouse, Jaeger) handle high cardinality efficiently.
Q7 Explain the trade-offs between "Push" (OTLP/StatsD) vs "Pull" (Prometheus scraping) metric architectures.
▼

Answer:

  • Pull (Prometheus):
  • Prometheus periodically scrapes /metrics HTTP endpoints.
  • Pros: Centralized rate control (scraping cannot overwhelm the server); easy liveness detection (if scrape fails, service is down); no state in client services.
  • Cons: Difficult to scrape short-lived ephemeral batch jobs or serverless functions (requires Pushgateway); complex firewall traversal across VPCs.
  • Push (OTLP to OTel Collector):
  • Applications push telemetry batches to a local collector daemon.
  • Pros: Uniform across metrics, traces, and logs; supports serverless/lambda environments; easy NAT/firewall egress.
  • Cons: Risk of overwhelming downstream telemetry backends during traffic bursts if collector queues overflow.
Q8 In LeetCode #355 (Design Twitter), how does the $K$-way merge algorithm operate for `GetNewsFeed`?
▼

Answer:

Each user has a chronologically sorted list of their own tweets.

  1. When generating the feed for user $U$, identify all followed users $F_1, F_2, \dots, F_k$ plus $U$.
  2. For each user who has posted at least one tweet, enqueue their most recent tweet into a Max-Heap along with their user ID and tweet index. The heap size is at most $|F| + 1$.
  3. Dequeue the root tweet (the globally newest across all feeds) and add to the result feed.
  4. Advance that user's index to their next newest tweet and enqueue it into the heap.
  5. Repeat until 10 tweets have been harvested or the heap is empty.
  • Time Complexity: $O(F \log F + 10 \log F) = O(F \log F)$.
Q9 How would you scale the Twitter news feed system for a celebrity with 100 million followers?
▼

Answer:

Using pure Fan-out on Write would require inserting 100,000,000 timeline entries into Redis whenever the celebrity tweets, causing massive write amplification and lag.

  • Solution (Hybrid Fan-out):
  1. Categorize users into standard users and celebrities (e.g. followers $> 50,000$).
  2. For standard users: Fan-out on Write to follower timeline caches.
  3. For celebrities: Do not fan out on write. Instead, when a follower opens their feed, do a fast parallel fetch of the recent tweets from celebrities they follow and dynamically merge them (fan-out on read) with their pre-computed inbox timeline in RAM.
Q10 How does OpenTelemetry Collector act as a pipeline buffer and aggregator in enterprise deployments?
▼

Answer:

Rather than having hundreds of microservice pods directly connect to Prometheus, Jaeger, and Datadog:

  1. Microservices send OTLP over localhost/mesh to an OTel Collector agent or daemonset.
  2. The Collector pipeline has three stages:
  • Receivers: Accept OTLP (gRPC/HTTP), Zipkin, Jaeger.
  • Processors: memory_limiter, batch (coalesce into bulk network requests), filter (drop unwanted metrics), and tail_sampling (keep only slow or failed traces).
  • Exporters: Fan out identical telemetry data to multiple targets simultaneously (e.g., Prometheus for metrics, Jaeger for tracing, AWS CloudWatch for auditing).

using System.Diagnostics;
using System.Diagnostics.Metrics;

namespace Day35.ObservabilityStack;

public record LatencyPercentiles(double P50, double P90, double P95, double P99, int TotalCount, double Mean);

public record HistogramBucket(double UpperBound, int CumulativeCount);

public class ObservabilityMetricsManager : IDisposable
{
    public const string MeterName = "Day35.ObservabilityStack";
    public const string Version = "1.0.0";
    public static readonly Meter Meter = new(MeterName, Version);

    // RED Metrics
    public readonly Counter<long> RequestCounter;
    public readonly Counter<long> ErrorCounter;
    public readonly Histogram<double> RequestDurationHistogram;

    // USE Metrics
    public double SimulatedCpuUtilization { get; set; } = 42.5;
    public long SimulatedThreadPoolQueueLength { get; set; } = 12;
    public readonly Counter<long> HardwareErrorCounter;

    private readonly MeterListener _listener;
    private readonly List<double> _observedDurations = new();
    private long _totalRequests = 0;
    private long _totalErrors = 0;
    private readonly object _lock = new();

    public long TotalRequests => Interlocked.Read(ref _totalRequests);
    public long TotalErrors => Interlocked.Read(ref _totalErrors);
    public IReadOnlyList<double> ObservedDurations
    {
        get
        {
            lock (_lock) return _observedDurations.ToList();
        }
    }

    public ObservabilityMetricsManager()
    {
        RequestCounter = Meter.CreateCounter<long>("http.server.requests.count", "requests", "Total incoming HTTP requests");
        ErrorCounter = Meter.CreateCounter<long>("http.server.requests.errors", "errors", "Total HTTP requests resulting in 5xx errors");
        RequestDurationHistogram = Meter.CreateHistogram<double>("http.server.request.duration.ms", "ms", "HTTP request processing duration in milliseconds");

        Meter.CreateObservableGauge("system.cpu.utilization", () => SimulatedCpuUtilization, "%", "Simulated CPU Utilization");
        Meter.CreateObservableGauge("threadpool.queue.saturation", () => SimulatedThreadPoolQueueLength, "items", "ThreadPool queued work items");
        HardwareErrorCounter = Meter.CreateCounter<long>("system.hardware.errors", "errors", "Hardware / disk / network drop errors");

        _listener = new MeterListener
        {
            InstrumentPublished = (instrument, listener) =>
            {
                if (instrument.Meter.Name == MeterName)
                {
                    listener.EnableMeasurementEvents(instrument);
                }
            }
        };

        _listener.SetMeasurementEventCallback<long>((instrument, measurement, tags, state) =>
        {
            if (instrument.Name == "http.server.requests.count")
            {
                Interlocked.Add(ref _totalRequests, measurement);
            }
            else if (instrument.Name == "http.server.requests.errors")
            {
                Interlocked.Add(ref _totalErrors, measurement);
            }
        });

        _listener.SetMeasurementEventCallback<double>((instrument, measurement, tags, state) =>
        {
            if (instrument.Name == "http.server.request.duration.ms")
            {
                lock (_lock)
                {
                    _observedDurations.Add(measurement);
                }
            }
        });

        _listener.Start();
    }

    public void RecordRequest(double durationMs, bool isError = false, string route = "/api/v1/resource", int statusCode = 200)
    {
        var tagList = new TagList
        {
            { "http.route", route },
            { "http.status_code", statusCode }
        };

        RequestCounter.Add(1, tagList);
        RequestDurationHistogram.Record(durationMs, tagList);

        if (isError)
        {
            ErrorCounter.Add(1, tagList);
        }
    }

    /// <summary>
    /// Computes P50, P90, P95, P99 percentiles from a collection of recorded latencies.
    /// Uses the standard Nearest-Rank percentile method.
    /// </summary>
    public static LatencyPercentiles CalculatePercentiles(IEnumerable<double> latencies)
    {
        var list = latencies.OrderBy(x => x).ToList();
        if (list.Count == 0)
        {
            return new LatencyPercentiles(0, 0, 0, 0, 0, 0);
        }

        double p50 = GetPercentile(list, 50);
        double p90 = GetPercentile(list, 90);
        double p95 = GetPercentile(list, 95);
        double p99 = GetPercentile(list, 99);
        double mean = list.Average();

        return new LatencyPercentiles(p50, p90, p95, p99, list.Count, Math.Round(mean, 2));
    }

    private static double GetPercentile(List<double> sorted, double percentile)
    {
        if (sorted.Count == 1) return sorted[0];
        double rank = (percentile / 100.0) * (sorted.Count - 1);
        int lower = (int)Math.Floor(rank);
        int upper = (int)Math.Ceiling(rank);
        if (lower == upper) return sorted[lower];
        double weight = rank - lower;
        return Math.Round(sorted[lower] * (1 - weight) + sorted[upper] * weight, 2);
    }

    /// <summary>
    /// Simulates Prometheus-style cumulative histogram buckets.
    /// Standard Prometheus boundaries: 5ms, 10ms, 25ms, 50ms, 100ms, 250ms, 500ms, 1000ms, +Inf.
    /// </summary>
    public static List<HistogramBucket> BuildPrometheusBuckets(IEnumerable<double> latencies, double[]? boundaries = null)
    {
        boundaries ??= [5.0, 10.0, 25.0, 50.0, 100.0, 250.0, 500.0, 1000.0, double.PositiveInfinity];
        var list = latencies.ToList();
        var buckets = new List<HistogramBucket>();

        foreach (var boundary in boundaries)
        {
            int count = list.Count(v => v <= boundary);
            buckets.Add(new HistogramBucket(boundary, count));
        }

        return buckets;
    }

    /// <summary>
    /// Correlates telemetry by generating structured log payloads with trace_id and span_id.
    /// </summary>
    public static string FormatStructuredLog(string message, string traceId, string spanId, string logLevel = "Information")
    {
        return $"{{\"timestamp\":\"{DateTime.UtcNow:O}\",\"level\":\"{logLevel}\",\"trace_id\":\"{traceId}\",\"span_id\":\"{spanId}\",\"message\":\"{message}\"}}";
    }

    public void Dispose()
    {
        _listener.Dispose();
    }
}

namespace Day35.ObservabilityStack;

public class TwitterFeedSolver
{
    private static int _globalTimestamp = 0;

    public record Tweet(int TweetId, int Timestamp);

    private readonly Dictionary<int, List<Tweet>> _userTweets = new();
    private readonly Dictionary<int, HashSet<int>> _following = new();

    public TwitterFeedSolver()
    {
    }

    /// <summary>
    /// Composes a new tweet with ID tweetId by the user userId.
    /// Time Complexity: O(1).
    /// </summary>
    public void PostTweet(int userId, int tweetId)
    {
        if (!_userTweets.ContainsKey(userId))
        {
            _userTweets[userId] = new List<Tweet>();
        }

        var timestamp = Interlocked.Increment(ref _globalTimestamp);
        _userTweets[userId].Add(new Tweet(tweetId, timestamp));
    }

    /// <summary>
    /// Retrieves the 10 most recent tweet IDs in the user's news feed (from self and followees).
    /// Ordered from most recent to least recent.
    /// Uses Max-Heap (k-way merge) over sorted tweet lists.
    /// Time Complexity: O(F * log F + 10 * log F) where F = number of followees, Space: O(F).
    /// </summary>
    public IList<int> GetNewsFeed(int userId)
    {
        var result = new List<int>(10);

        // Gather all users contributing to this user's feed: self + followed users
        var relevantUsers = new HashSet<int> { userId };
        if (_following.TryGetValue(userId, out var followees))
        {
            foreach (var f in followees)
            {
                relevantUsers.Add(f);
            }
        }

        // Max-heap of (Tweet, user, indexInUserList).
        // PriorityQueue in .NET is min-heap by default, so use -timestamp as priority for max-heap behavior.
        var maxHeap = new PriorityQueue<(Tweet Tweet, int UserId, int Index), int>();

        foreach (var u in relevantUsers)
        {
            if (_userTweets.TryGetValue(u, out var tweets) && tweets.Count > 0)
            {
                int lastIdx = tweets.Count - 1;
                var latestTweet = tweets[lastIdx];
                maxHeap.Enqueue((latestTweet, u, lastIdx), -latestTweet.Timestamp);
            }
        }

        while (maxHeap.Count > 0 && result.Count < 10)
        {
            var (tweet, u, idx) = maxHeap.Dequeue();
            result.Add(tweet.TweetId);

            int nextIdx = idx - 1;
            if (nextIdx >= 0)
            {
                var nextTweet = _userTweets[u][nextIdx];
                maxHeap.Enqueue((nextTweet, u, nextIdx), -nextTweet.Timestamp);
            }
        }

        return result;
    }

    /// <summary>
    /// Follower starts following followee.
    /// A user cannot follow themselves.
    /// </summary>
    public void Follow(int followerId, int followeeId)
    {
        if (followerId == followeeId) return;

        if (!_following.ContainsKey(followerId))
        {
            _following[followerId] = new HashSet<int>();
        }

        _following[followerId].Add(followeeId);
    }

    /// <summary>
    /// Follower unfollows followee.
    /// </summary>
    public void Unfollow(int followerId, int followeeId)
    {
        if (followerId == followeeId) return;

        if (_following.TryGetValue(followerId, out var followees))
        {
            followees.Remove(followeeId);
        }
    }
}

        twitter.PostTweet(userId: 1, tweetId: 5);
        twitter.PostTweet(userId: 2, tweetId: 6);

        // User 1 follows User 2
        twitter.Follow(followerId: 1, followeeId: 2);

        var feed = twitter.GetNewsFeed(userId: 1);

        // Tweet 6 was posted after Tweet 5
        Assert.Equal([6, 5], feed);
    }

    [Fact]
    public void Twitter_Unfollow_StopsShowingUnfollowedTweets()
    {
        var twitter = new TwitterFeedSolver();
        twitter.PostTweet(userId: 1, tweetId: 11);
        twitter.PostTweet(userId: 2, tweetId: 22);

        twitter.Follow(1, 2);
        Assert.Equal([22, 11], twitter.GetNewsFeed(1));

        twitter.Unfollow(1, 2);
        Assert.Equal([11], twitter.GetNewsFeed(1));
    }

    [Fact]
    public void Twitter_GetNewsFeed_CapsAt10MostRecentTweets()
    {
        var twitter = new TwitterFeedSolver();

        // User posts 15 tweets
        for (int i = 1; i <= 15; i++)
        {
            twitter.PostTweet(userId: 42, tweetId: i);
        }

        var feed = twitter.GetNewsFeed(userId: 42);

        Assert.Equal(10, feed.Count);
        // Most recent should be 15 down to 6
        Assert.Equal([15, 14, 13, 12, 11, 10, 9, 8, 7, 6], feed);
    }

    [Fact]
    public void Twitter_SelfFollowAndUnfollow_DoesNotCorruptSelfTweetsInFeed()
    {
        var twitter = new TwitterFeedSolver();
        twitter.PostTweet(userId: 7, tweetId: 701);

        twitter.Follow(followerId: 7, followeeId: 7); // Self-follow attempt
        twitter.Unfollow(followerId: 7, followeeId: 7); // Self-unfollow attempt

        var feed = twitter.GetNewsFeed(userId: 7);

        Assert.Single(feed);
        Assert.Equal(701, feed[0]);
    }
